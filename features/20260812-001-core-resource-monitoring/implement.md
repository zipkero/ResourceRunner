- [x] task-001: CPU·Memory 시스템 지표 한 tick 수집
  - 승인 근거: HEAD `bf0d186`의 현재 미커밋 CPU Collector·SystemMetricsSampleSource 및 직접 테스트 diff에서 독립 verify approved. 새 epoch의 첫 CPU 기준점 갱신, 구 epoch 폐기, 같은 epoch의 5초 → 1초 정상 차분과 정확히 10초 경계를 두 테스트 suite로 확인했고, 기존 Memory·실기기 경로 suite도 통과. 첫 verify의 주기 변경 테스트 누락은 시도 2/3에서 보완함.
  - 목적: 한 번의 수집으로 전체 CPU 사용률, User·System·Idle 비율, 논리 코어별 사용률, Load Average,
    전체 물리 메모리, 사용 중 메모리, App·Wired·Compressed·Cached, Swap 사용량, Memory Pressure 단계가
    같은 시각에 묶인 결과 하나로 나오고,
    CPU와 Memory 중 한쪽 조회가 실패해도 다른 쪽 값이 그 시각의 결과에 그대로 남습니다.
    명시적 중지 뒤 첫 CPU tick은 중지 길이에 관계없이 새 기준점만 잡습니다.
  - 접근: CPU Collector가 `host_processor_info(PROCESSOR_CPU_LOAD_INFO)`로 논리 코어별 tick을 읽어
    직전 tick 원본과의 차이로 사용률을 만들고 Load Average는 `getloadavg`로 읽습니다.
    Memory Collector가 `host_statistics64(HOST_VM_INFO64)`, `host_page_size`, `ProcessInfo.physicalMemory`,
    `sysctl(VM_SWAPUSAGE)`, `sysctlbyname("kern.memorystatus_vm_pressure_level")`을 한 tick에 함께 읽고,
    「사용 중」은 구성 항목의 합이 아니라 Activity Monitor와 같은 정의를 씁니다.
    두 Collector를 소유한 actor source가 CPU와 Memory 각각을 `Result`로 담은 샘플 하나를 반환하고,
    지표별 실패는 던지지 않고 값으로 전달합니다.
    직전 tick 원본이 없거나 직전 tick과의 간격이 허용 간격을 넘으면 사용률을 만들지 않고 기준점만 갱신합니다.
    허용 간격은 유효 주기마다 다시 계산하지 않고 가장 느린 수집 주기(lowPower·팝오버 닫힘 5초)의 두 배인 10초로 고정합니다.
    Collector는 일정을 알지 못하고, 주기가 5초에서 1초로 바뀌는 tick에서 유효 주기 기준으로 판정하면 정상 값을 버리게 됩니다.
    시스템 지표 source는 마지막 처리 `collectionEpoch`를 기억하고 더 큰 epoch의 첫 호출 전에 CPU Collector의 직전 원본을 폐기합니다.
    이미 처리한 epoch보다 오래된 호출은 Collector 상태를 건드리지 않고 폐기하며, Memory 순간값의 기준점은 초기화하지 않습니다.
  - 검증 조건:
    - 결과: 코어별 사용률 개수가 `ProcessInfo.activeProcessorCount`와 같고 각 값이 0~100% 범위이며,
      전체 사용률은 코어별 tick 합에서 계산되어 항상 0~100% 범위이고 User·System·Idle의 합이 100%에 수렴합니다.
      첫 tick은 기준점만 잡고 CPU 사용률을 만들지 않으며 두 번째 tick부터 값이 나옵니다.
      새 epoch의 첫 tick도 중지 시간이 10초 이내여도 CPU 사용률을 만들지 않고, 같은 epoch의 다음 정상 tick부터 값을 만듭니다.
      오래된 epoch의 늦은 호출은 새 기준점을 되돌리지 않습니다.
      직전 tick과의 간격이 허용 간격을 넘으면 값 없이 기준점만 갱신됩니다.
      Memory는 순간값 조회이므로 첫 tick부터 값이 나오고, 사용 중 메모리가 전체 물리 메모리를 넘지 않습니다.
      Memory Pressure 원시값 `0x01`·`0x02`·`0x04`만 `normal`·`warning`·`critical`로 해석되고 그 밖의 값은 실패입니다.
      CPU 조회가 실패한 tick의 샘플에도 Memory 성공값이 그대로 담기고 그 반대도 같으며,
      실패한 지표가 0이나 빈 값으로 바뀌지 않습니다.
      두 지표가 하나의 샘플 시각을 공유해 카드 사이에 시점 차이가 생기지 않습니다.
    - 확인: Swift Testing으로 tick 원본과 시각을 주입한 차분 계산을 검증합니다 —
      첫 tick의 값 부재, 정상 간격에서의 사용률 산출, 허용 간격 초과에서의 기준점 전용 갱신,
      5초 내외 중지에 해당하는 새 epoch 첫 tick의 값 부재와 그다음 tick의 사용률 산출,
      새 epoch 처리 뒤 도착한 구 epoch 호출의 상태 불변,
      중지 없는 5초 → 1초 주기 변경과 정확히 10초 간격의 정상 차분,
      코어별 값과 전체 값의 관계, User·System·Idle 합을 각각 단언합니다.
      「사용 중」 계산식은 원시값을 주입한 테스트가 고정하며, 전체 물리 메모리를 넘지 않는 성질도 그 자리에서 단언합니다.
      Memory Pressure 원시값 매핑은 세 유효값과 무효값 표본으로 전수 검증합니다.
      실패 격리는 실패를 반환하는 가짜 Collector를 주입해 확인하며,
      이 테스트가 고정하는 것은 "한 지표의 실패가 같은 tick의 다른 지표 값을 함께 없애지 않는다"입니다 —
      source가 실패를 던지도록 되돌리면 이 테스트가 실패해야 합니다.
      실제 시스템 호출 경로는 macOS 26.5 Apple silicon에서 연속 두 tick을 수집해
      코어 수 일치와 값 범위를 단언하는 테스트로 확인합니다.

- [x] task-002: 주기 변경에서 살아남는 최근 10분 이력
  - 승인 근거: HEAD `bf0d186`의 현재 미커밋 MonitoringSampleStore 및 직접 테스트 diff에서 독립 verify approved. 짧은 중지의 이력 epoch 0·1 보존, 재개 첫 CPU nil tick 미추가, 기존 10분 창·고정 링·주기 변경·최신 stream 조건을 MonitoringSampleStoreTests·CircularBufferTests·HistoryCapacityTests로 확인했고 `git diff --check`도 통과.
  - 목적: 팝오버 열림·닫힘이나 저전력 모드로 수집 주기가 바뀌어도 이미 쌓인 최근 10분 이력이 사라지지 않고,
    사용률을 만들지 못한 tick은 이력에 남지 않으며,
    표시로 넘어가는 구간이 최신 샘플 시각 기준 10분 창으로 한정됩니다.
    명시적 중지 전후의 유효 이력 점은 서로 다른 수집 구간으로 구별됩니다.
  - 접근: 샘플 저장소를 최신 스냅샷 하나와 시각·전체 CPU 사용률·Swap 사용 바이트만 담는 이력 링으로 나누고,
    링 용량을 이 feature가 쓸 수 있는 가장 짧은 주기 기준으로 고정해 resize 경로를 제거합니다.
    저장소는 `MonitoringSampleSink` 계약을 구현하고 `MonitoringScheduler`는 저장 대상을 구체 타입 대신 이 계약으로 받습니다.
    표시용 값을 내보낼 때 최신 샘플 시각에서 10분을 뺀 시점 이후의 항목만 선별합니다.
    `TimestampedSample`과 유효한 `SystemMetricsHistoryPoint`에 `collectionEpoch`를 전달·보관합니다.
    기준점만 잡은 재개 첫 tick은 기존처럼 링에 넣지 않고, 이후 첫 유효 점에 새 epoch를 남깁니다.
    저장소가 `SystemMetricsSample` 전용이 되면서 자리표시 source와 타입이 맞지 않으므로
    코디네이터 배선을 실제 시스템 지표 source로 바꾸고, `MonitoringSampleSink` 제네릭 파라미터는
    Scheduler를 보유하는 타입까지 전파됩니다. 자리표시 심볼 제거는 task-014에 남깁니다.
  - 검증 조건:
    - 결과: 수집 주기가 1초에서 2초, 5초로 바뀌어도 링 용량이 그대로이고 이미 담긴 항목의 값과 순서가 변하지 않습니다.
      CPU 사용률과 Swap 값이 모두 있는 tick만 링에 추가되고, 사용률을 만들지 못한 tick은 링에 들어가지 않아
      그 시각이 이력에서 비어 있게 됩니다.
      중지 전 점은 보존되고 재개 뒤 첫 유효 점은 새 epoch를 가지며, 별도 빈 점이나 가짜 값은 추가되지 않습니다.
      최신 스냅샷은 매 tick 교체되어 코어별 사용률과 Memory 세부 구성처럼 현재값만 필요한 지표를 담습니다.
      중지 구간을 사이에 둬서 10분보다 오래된 항목이 링에 남아 있어도 표시용 값에는 포함되지 않으며,
      10분 창의 경계가 창을 짧게 자르지 않습니다.
      저장소 밖으로 나가는 경로는 표시용 값 stream과 snapshot뿐이고 가변 버퍼 참조는 노출되지 않으며,
      stream은 최신 조합 하나만 보존해 소비가 밀려도 오래된 조합이 쌓이지 않습니다.
      주기 기반 `resize` API는 남지 않습니다.
    - 확인: Swift Testing으로 시각을 직접 준 샘플 시퀀스를 사용합니다.
      이 테스트가 고정하는 것은 M1의 resize 회귀입니다 —
      1초 주기로 이력을 채운 뒤 주기를 2초·5초로 바꾸고 저장된 값 배열 전체를 비교해
      한 항목도 사라지지 않았음을 단언하며, 용량을 유효 주기로 재계산하도록 되돌리면 이 테스트가 실패해야 합니다.
      값이 없는 tick의 링 미추가, 10분 창 선별(창 경계 직전·정각·직후 항목), 링 용량 초과 시 가장 오래된 항목만 교체,
      1시간 중지를 시각으로 재현한 뒤의 표시용 값이 빈 목록이 되는 것을 각각 단언합니다.
      5초 내외 중지 전후의 유효 점을 서로 다른 epoch로 주입해 링과 표시용 값에서 epoch가 보존되는지,
      재개 첫 값 없는 tick은 링에 없고 다음 유효 점에는 새 epoch가 있는지 확인합니다.
      가변 참조 미노출과 `resize` 부재는 API 시그니처와 소스 검색으로 확인합니다.

- [x] task-003: 두 수집 축의 일정과 화면을 볼 수 없는 상태
  - 승인 근거: HEAD `bf0d186`의 현재 미커밋 Scheduler·source 및 관련 테스트 diff에서 독립 verify approved. 실제 running→paused의 epoch 전진, 중복 pause·정상 주기 변경 불변, source·저장 epoch 일치와 이전 generation 결과 폐기를 수동 clock·지연 source로 확인했고 관련 여섯 suite와 `git diff --check`가 통과. 첫 verify의 정상 주기 변경 전파 단언 누락은 시도 2/3에서 보완함.
  - 목적: 팝오버 열림·닫힘과 저전력 모드에 따라 시스템 지표와 프로세스 조사의 주기가 각각 정해진 값으로 바뀌고,
    화면 잠금·디스플레이 슬립·빠른 사용자 전환 중 하나라도 성립하면 두 수집이 모두 멈춰 새 샘플이 쌓이지 않습니다.

  - 접근: `SystemLifecycleSnapshot`과 `SystemLifecycleFieldChange`에 디스플레이 슬립과 세션 활성 필드를 더하고,
    `NSWorkspaceScreensDidSleep`·`ScreensDidWake`·`SessionDidResignActive`·`SessionDidBecomeActive` 알림을 등록하며
    초기값은 화면이 켜져 있고 세션이 활성인 상태로 둡니다.
    `CollectionSchedulePolicy`가 두 일정을 묶은 `CollectionSchedulePlan`을 계산하고,
    `MonitoringLifecycleStore`가 `CollectionScheduleTarget` 계약으로 두 Scheduler를 보유해
    각 축의 결과가 바뀔 때만 그 축에 적용합니다.
    Scheduler별 epoch를 단조 증가시키고 실제 `.running` → `.paused` 전이에만 전진시킵니다.
    `ScheduledSampleSource` 호출과 `TimestampedSample`에 epoch를 전달합니다.
    프로세스 source는 공통 호출 계약을 따르되 조사값과 정체성별 이력 계산에는 epoch를 사용하지 않습니다.
    기존 `generation`은 취소된 결과의 저장을 막는 용도로 유지합니다.
  - 검증 조건:
    - 결과: normal 열림은 시스템 1초·프로세스 2초, normal 닫힘은 2초·5초,
      lowPower 열림은 2초·4초, lowPower 닫힘은 5초·10초입니다.
      화면 잠금 `locked`, 잠금 `unknown`, 디스플레이 슬립, 세션 비활성 각각이 단독으로 두 일정을 모두 `paused`로 만들고,
      중지 동안 두 축의 누적 샘플 수가 늘지 않으며 재개 시 놓친 실행을 따라잡지 않습니다.
      디스플레이 슬립과 세션 활성의 초기값은 알림이 오지 않아도 앱이 수집을 시작할 수 있는 값이고,
      이후 알림으로 교정됩니다.
      같은 결과를 만드는 이벤트가 반복 도착해도 해당 축의 `apply(_:)`가 다시 호출되지 않고 실행 중인 작업이 재시작되지 않습니다.
      실제 중지 한 번에 시스템 지표 epoch가 한 번만 전진하고, 중복 중지 알림·재개·중지 없는 주기 변경에서는 전진하지 않습니다.
      재개한 실행의 source 호출과 저장 샘플에 같은 새 epoch가 실리며, 취소된 구 generation의 결과는 저장되지 않습니다.
      한 축의 일정만 바뀌면 다른 축의 실행 중 작업은 취소되지 않습니다.
      M1의 revision 거부, 단일 Task·generation, 기준 deadline 전진 규칙은 축마다 그대로 유지됩니다.
    - 확인: 메모리 생명주기 source와 수동 clock, 주입 sample source로 Swift Testing 검증을 작성합니다.
      팝오버 2 × 전력 2 × 잠금 3 × 디스플레이 슬립 2 × 세션 활성 2 조합에서 `CollectionSchedulePlan`의 두 값을 전수 단언합니다.
      이 테스트가 고정하는 것은 두 가지입니다 —
      "새로 더한 두 신호 각각이 단독으로 수집을 멈춘다"(두 필드 중 하나를 판정에서 빼면 실패),
      "한 축의 일정 변경이 다른 축을 재시작하지 않는다"(축별 `apply(_:)` 호출 횟수와 시계 전진 후 누적 샘플 수로 관찰).
