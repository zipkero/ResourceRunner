# 개인 사용 성능 개선 설계

## 근거

현재 [SPEC](./spec.md), [조사 입력](./evidence/intake/README.md), 루트 ROADMAP·제품 정의·기술 설계를 따른다.
기준은 HEAD69842e14e920e95da179f525055b22dd75c56b74와 정적 메뉴바/포커스의 미커밋 변경이다.
analyzer의 읽기 전용 원본 조사 후보를 main이 검토하여 적용한다. 원인 확정과 성능 통과는 아직 수행하지 않았다.

StatusBarController는 hosting을 보유하고 ApplicationCoordinator와 DashboardPresentationStore는 창이 숨겨져도
표시 자료를 갱신한다. CPU 및 ResourceRateGraphView에는 독립적인 1초 TimelineView가 있고,
viewport에는 지연 보정 작업이 있다. 설정 hosting은 생성 후 보유되며 ApplicationIconCache는 용량 제한과
실패 캐시를 갖는다. 각각은 조사 후보이며 실제 비용의 원인이라는 판정은 대조 측정 후에 한다.

## 1. 구조

### 1.1 책임 분리

외부 측정 도구 → 고정 원본 baseline → 요소별 진단 → 제품 최적화 → 기능/성능 검증 → 실제 설치 순서다.
외부 도구는 이 기능의 tools/ 아래 두며 앱 target에 포함하지 않는다. Release에 상시 기록을 추가하지 않는다.
evidence/ 아래 각 실행의 환경·설정·창 상태·워밍업·기간·PID/시작 시각·URL·실행 파일 SHA·빌드 구성·서명·
소스/도구 해시, 원시 시계열·상태 이벤트·오류·유효성·집계 결과를 보관한다. sample/vmmap은 안정 측정과 별도다.
관련 조건: SPEC §5.1, §5.8.

### 1.2 원본 고정

제품 수정 전에 현재 소스·미커밋 변경·설정·Release artifact를 불변 baseline으로 보관한다.
실행 파일 SHA만으로 소스 출처를 확정하지 않는다. 설치 바이너리의 출처를 증명할 수 없으면 현재 소스를
동결하여 다시 빌드한 원본을 공식 비교에 사용하고 기존 장기 실행 관찰은 운영 입력으로 구별한다.
역패치로 추정한 원본이나 서로 다른 설정을 비교하지 않는다. 관련 조건: SPEC §5.1.

### 1.3 요소별 원인 조사

진단 복사본에서 한 번에 한 요소만 바꾼다: 숨긴 그래프 clock, 숨긴 화면으로의 관찰 publication,
dashboard hosting 보유, viewport 중복/지연 작업, settings hosting 보유, 그래프·아이콘·순위 계산.
수집·최신 캐시를 유지한 채 요소를 분리하고 원본/후보를 같은 조건에서 세 쌍 비교한다.
baseline 변동을 넘어선 차이와 실행/할당 흔적, 기능 보존 근거로 채택 여부를 설명한다.
더미 데이터·TOP5 숨김·수집 지연·목록 축소는 제품 최적화로 채택하지 않는다.
조사 Task는 재현 가능한 원인 분류와 근거 확보로 판정한다. 목표 달성을 조사 Task에 미리 요구하지 않는다.
유효한 개선을 찾지 못하면 관련 설계로 반환하며 성능 통과로 처리하지 않는다. 관련 조건: SPEC §5.1, §5.7.

### 1.4 제품 경계

수집/이력·epoch/admission → 최신 자료 캐시 → 표시 중인 화면 전달 → display session → 그리기를 구분한다.
숨긴 동안 최신 자료는 계속 유지하고 화면 작업만 줄일 수 있다. 화면 표시 여부는 실제 AppKit delegate가
결정하며 generation으로 이전 지연 작업이 새 화면을 갱신하지 못하게 한다.
표시 중에는 원래 1초 시간 흐름·peak·gap·설정 반영을 보존한다. 관련 조건: SPEC §5.2, §5.3, §5.7.

## 2. 데이터 흐름

### 2.1 화면 생명주기

열기: 최신 캐시/설정 준비 → hosting 연결 → viewport 계산 → 활성화/show/key → 실제 didShow 확인.
닫기: 실제 didClose 확인 → 해당 session의 clock/관찰 작업/지연 보정 해제.
재열림의 상세 선택은 원본 동작을 먼저 기록하여 보존하고 최신 자료 표시를 새 수집 완료까지 지연하지 않는다.
메뉴바 CPU 색상·툴팁·접근성 갱신은 팝오버 생명주기와 독립이다. 관련 조건: SPEC §5.6, §5.7.

### 2.2 고정 성능 프로토콜

기본 설정은 네 카드·TOP5 표시, 최근10분, 표준 수집, 시스템 제외, 상세20개, 자동닫기 켜짐이다.
환경은 같은 Mac/OS·전원/저전력·디스플레이/배율·외관·네트워크/디스크 대상·백그라운드 부하로 기록한다.
관찰 환경은 Mac15,11/M3 Max/14논리코어/36GiB, macOS26.6.2(25G83)다.
Xcode26.6(17F113)/SDK26.5/deployment26.5와 실행 OS를 구별하며 실제 측정 때 다시 기록한다.

상태는 모두 닫힘, 본체만 열림, CPU/Memory/Network/Disk 각 상세와 본체 열림, 설정창만 열림의 7개다.
새 프로세스600초 워밍업, 상태 전환60초 안정화, 상태별300초 안정 측정·1초 간격·3회 반복을 원본/후보에 동일 적용한다.
안정 구간에는 빌드·테스트·프로파일러·sample/vmmap을 함께 실행하지 않는다. 사용자 설정 원본을 보존/복원한다.

CPU는 누적 user/system 시간의 차분을 실제 monotonic 경과 시간으로 나눈다. Mach tick은 검증된
mach_timebase_info로 환산하고 ps 누적 CPU 시간과 별도 교차 확인한다. 100%는 논리 코어 하나이며 코어 수로 나누지 않는다.
외부 proc_pid_rusage의 RSS·Physical Footprint와 실행 최고 Footprint를 별도 기록한다.
각 상태의 세 유효 반복 모두 CPU 평균이 닫힘1%, 다른 상태3% 미만이어야 한다.
모든 안정 구간 유효 샘플의 Footprint가100,000,000bytes 미만이어야 하며 평균이나 RSS로 대신하지 않는다.
시작/전환 peak와 실행 최고값을 별도 보고하고 1초 사이의 모든 peak를 포착했다고 주장하지 않는다.
별도 추적에서 안정 구간 초과가 확인되면 통과를 취소한다. 그래픽 resident/heap/Footprint를 합산하지 않는다.

예정 시각 대비250ms 초과 지연, 누락/API 오류, PID·시작 시각 변경, 잠금/절전/비활성 세션,
설정·창 상태 변경이 있으면 해당300초 전체를 무효로 보존하고 재측정한다. 좋은 일부 구간만 선택하지 않는다.
관련 조건: SPEC §5.1, §5.2, §5.3, §5.4.

### 2.3 격리와 실제 앱 비교

조사/구현 중 기존 설치 앱의 장기 실행을 유지한다. 원본/후보 진단 앱은 동일한 별도 bundle ID·설정 namespace로
순차 실행하고 진단 앱끼리 중복 실행하지 않는다. 기존 앱의 공통 백그라운드 부하와 경로/ID 차이를 기록한다.
진단 앱의 통과를 실제 설치 앱 통과로 대체하지 않는다.
개선 후보의 사전 검증 후에만 기존 세션을 종료하고 동결 원본과 개선본을 같은 실제 설치 URL/ID에서
§2.2의 새 실행 비교로 검증한다. 마지막에는 검증된 개선본을 남긴다. 관련 조건: SPEC §5.1, §5.8.

### 2.4 반복과 반응 시간

600초 워밍업 후5회 준비 사이클,20회 측정 사이클을 실행한다. 사이클은 본체 → 네 상세(각2초) → 닫기다.
사이클 뒤60초 닫힘 중 마지막30초의 RSS/Footprint 중앙값·최대와 hosting/clock/지연 작업 보유를 기록한다.
5회씩4묶음의 같은 닫힘 상태를 비교하여 지속 증가와 용량 제한 캐시/해제 자원을 설명한다.
이 시험으로24시간 이상 누수 없음을 주장하지 않는다.

반응 시간은 별도 측정한다. 실제 메뉴바 mouse-up 전달이 시작, 새 앱 소유 팝오버가 화면에 나타남이
클릭 처리 종료, 최신 카드/그래프/접근성 값이 완전히 표시됨이 팝오버 표시 종료다.
완전 표시는 애니메이션 종료나 최종 크기·불투명도가 아니라, 네 카드 값·TOP5 행·그래프가 팝오버 프레임에서 처음 모두 식별되는 시점이다.
새 프로세스 첫 열림3회와 준비 후 재열림20회 모두100ms/200ms 이내여야 한다.
외부 관찰 주기·오차를 기록하며 자동화 지연을 임의 공제하지 않는다. 정확한 경계 확인이 불가능하면 미검증이다.
임시 진단 instrumentation은 보조 근거이며 실제 Release 외부 관찰을 대체하지 않는다.
관련 조건: SPEC §5.5, §5.6.

## 3. 인터페이스

### 3.1 외부 측정 계약

입력은 PID/시작 식별자·URL·실행 SHA·창 상태·워밍업·기간·간격·출력 상한이다.
단일 실행은 최대1800초/32MiB로 제한하고 종료 이유를 남긴다. 도구가 앱 종료/실행이나 설정 변경을 하지 않는다.
원시 행에는 sequence·예정/실제 시각·원시 CPU/timebase·환산 CPU·RSS·Footprint·실행 최고값·상태·유효성을 기록한다.
전환/누락/오류는 event로 보존한다. 관련 조건: SPEC §5.1.

### 3.2 표시·캐시 계약

실제 delegate 기반 가시성, 열기 전 최신 자료 전달, 닫힌 generation 작업 무효화와 실패/epoch 정보를 보존한다.
그래프 캐시를 도입하면 history revision·범위·geometry/scale·현재 시간·segment를 반영하고 용량을 제한한다.
timestamp마다 무한 항목을 만들지 않는다. 원본의 peak/gap/downsample·placeholder·접근성 의미를 유지한다.
아이콘 실패 캐시·순위 동률·앱/하위 프로세스 집계·PID 재사용·설정 키/revision·로그인 정책을 보존한다.
구체 타입/파일 선택은 확인된 원인에 따른 구현 재량이다. 관련 조건: SPEC §5.5, §5.6, §5.7.

## 4. 영향 범위

SPEC §5.1은 외부 도구/원본 고정/진단, §5.2~§5.4는 제품 개선과 실제 성능,
§5.5는 반복 자원 회수, §5.6은 열림/반응 시간, §5.7은 회귀, §5.8은 빌드/설치 검증에 매핑한다.
화면 전달·viewport·StatusBarController·SettingsWindowController와 관련 테스트를 직접 영향으로 본다.
그래프 수정 시 CPU/ResourceRateGraph의 범위·peak/gap·시간 흐름 검증, 아이콘 수정 시 캐시/실패/AX 검증을 추가한다.
수집 경로까지 영향이 있으면 scheduler/lifecycle/admission/store/집계/PID 재사용 검증까지 확장한다.
현재 전체 단위 테스트와 영향 UI 검증·원본 Debug/Release 빌드를 수행하고 과거 통과 수치로 대신하지 않는다.
실제 설치는 백업·설정/로그인 보존·URL/SHA/PID/단일 실행·화면 접근과 실제 성능을 확인한다.
실패하면 원본으로 복구하고 미완료를 보고한다. 새 로그아웃/로그인 등록을 하지 않으며 다음 로그인 재시험을 주장하지 않는다.

## 5. Decision Points

main 채택: 외부 도구/진단/제품/실제 설치의 분리, 불변 baseline 출처,7상태 고정 프로토콜,
Mach 시간 교차 검증, 안정 Footprint 최대 기준, 누락 구간 전체 무효화, 요소별 세 쌍 대조,
최신 캐시와 표시 작업의 분리, 최종 단계의 실제 경로 비교, 반복/반응 경계, 미달 시 소유 단계 반환.
미확정 사용자 결정은 없다. 구체 원인은 Task 조사 결과이며 설계 완료를 원인 확정으로 해석하지 않는다.
요구사항 변경은 spec-init, 구조/측정 계약 변경은 design-init, Task 변경은 implement-init에서 main이 처리한다.
실제 SPEC §5.2~§5.8이 충족되기 전 IMPLEMENT와 M5 전체를 완료 처리하지 않는다.
