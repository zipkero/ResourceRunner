### 렌더로 확인한 것

- 새 타입 스케일과 새 면을 얹은 본체를 라이트·다크로 렌더해 카드가 두 모드 모두에서 바탕 위로 떠오르는 것, 테두리 없이도 카드 경계가 갈리는 것, 초점 값이 나머지와 한눈에 갈리는 것을 확인했습니다(`SPEC §5.1`, `SPEC §5.5`).
- 코어 14개 중 두 개(92%·88%)만 75% 이상인 격자를 E안 색으로 라이트·다크 렌더해, 값을 하나씩 읽지 않고도 그 둘이 즉시 집히는 것을 확인했습니다(`SPEC §5.7`). 막대 18pt와 20pt 모두에서 성립하며, 높이는 판정에 결정적이지 않았습니다.
- 현재 Memory 상세를 렌더해 도넛 범례의 이름과 값이 좌우 끝으로 벌어지는 것을 확인했습니다(`SPEC §5.10`).

- `cardTopApplicationsHeading(count:)`의 소비자는 `CPUCardPresentation.topApplicationsHeading` 하나이고, Memory는 그것을 그대로 가리킵니다(`DashboardPresentation.swift:1128`). 그 문자열이 카드 화면 머리글과 두 카드의 접근성 이름에 함께 쓰입니다.

### 추정으로 남는 것

- 본체 고정 높이의 최종 값은 실측 절차가 정합니다. 산술은 601(프레임 627)이고, 직전 feature에서 산술 509가 실측 508로 나온 것과 같은 1pt 차가 재현되면 600(프레임 626)입니다. 어느 값인지는 IMPLEMENT가 `SPEC §5.14`의 절차로 확정합니다(§5 DP12).
- `NSPopover`의 화살표와 26pt chrome은 시스템 재질이 남습니다. 이 설계가 불투명 면을 까는 범위는 콘텐츠 사각형 안이며, 화살표 색까지 맞춘 결과는 실행 중인 앱에서 확인해야 합니다.
- Network·Disk 카드의 조립은 `docs/product.md`의 항목에서 투영한 것이고 M3가 확정하기 전까지는 가정입니다. 모델 1의 212pt는 그 가정 위의 값입니다.
- 기준 기기보다 작은 화면에서 M3 네 카드가 한 열로 들어가는지는 이 설계가 보증하지 않습니다. 그 자리는 `ROADMAP.md` M3가 이미 배치 구조 변경 의무로 지고 있습니다.
- 「90년대 같다」가 해소되었는지는 지각 판정이라 실측이 아니라 실행 중인 앱의 화면 확인 몫입니다.

## 1. 구조

새 모듈이나 레이어를 만들지 않습니다.
표시 계층 안에서 **시각 규칙을 소유하는 자리 하나(`DashboardStyle`)와 색을 소유하는 자리 하나(`DashboardColorPalette`)의 내부 모양**을 다시 정하고, 그 둘을 본체와 상세가 똑같이 소비하게 만듭니다.
뷰 트리 모양(본체 → 두 `Button` → 카드 뷰 → 자식 팝오버 → 상세 뷰)과 수집·조립 경로는 그대로입니다.

### 타이포 경계 — `DashboardStyle.TypographyRole`

네 역할이 **크기로 갈리는 집합**이 됩니다(`SPEC §5.1`).
역할 이름과 소비 지점은 그대로 두고 각 역할이 가리키는 글꼴만 바꾸므로, 이 자리 하나를 고치면 본체와 상세가 함께 따라갑니다.
`Typography.pointSize`는 「선언한 크기」가 아니라 「그 글꼴의 실제 pt」를 담는 필드로 뜻을 고정하고, 단위 테스트가 실측 pt와 견주어 어긋나지 않게 합니다.

### 여백 경계 — `DashboardStyle.Spacing`

단계 집합(2 / 4 / 8 / 16)은 그대로 두고 **어느 자리가 어느 단계를 쓰는지**만 바꿉니다(`SPEC §5.6`).
카드 안 구역 사이가 `betweenGroups`(8)에서 `betweenSections`(16)로 올라가면서, 상세가 이미 쓰던 구역 간격과 같은 값이 됩니다 — 두 화면이 같은 여백 단계를 쓴다는 사실이 상수 수준에서 성립합니다(`SPEC §5.9`).

### 표면 경계 — `DashboardStyle.CardSurface`와 팔레트의 두 면

카드는 「테두리를 그리는 상자」에서 「면을 가진 판」이 됩니다(`SPEC §5.5`).
`CardSurface`는 안쪽 여백·모서리 반경·채울 색을 소유하고 테두리 관련 값을 갖지 않습니다.
면 색 자체는 다른 색과 마찬가지로 `DashboardColorPalette`가 소유합니다 — 대비 검증이 그 값을 「실제로 놓이는 면」으로 읽어야 하기 때문입니다(`SPEC §5.11`).

### 그래프 판 경계 — `HistoryGraphLayout`·`HistoryGraphGridline`

판 높이와 슬롯 높이는 그대로 `HistoryGraphLayout`이 소유하고, 축 라벨 줄 높이만 새 `label` 역할의 실측 줄 높이로 올라갑니다(`SPEC §5.13`).
`HistoryGraphGridline`은 「눈금 값 집합」과 「실제로 그리는 기준선」을 나눠 갖습니다 — 코어 단계 경계 25 / 50 / 75%는 spec.md §3이 고정했고, 화면에 그리는 가로선은 그중 하나뿐이기 때문입니다(`SPEC §5.2`).
세로 눈금과 판 테두리는 이 자리에서 사라집니다.

### 코어 채움 색 경계 — 팔레트의 세 번째 색 집합

코어 막대 채움이 CPU 램프에서 떨어져 나와 **자기 색 집합**을 갖습니다(`SPEC §5.7`).
직전 feature DP6이 확정한 「표시 자리가 자기 색 집합을 소유하고 집합 사이의 색조 중복은 실격이 아니다」를 그대로 적용한 세 번째 집합입니다.
CPU 램프는 두 밴드와 요약 줄 스와치 전용으로 남습니다.

### 구역 머리글 경계 — `DashboardStyle.Section`

「머리글 역할 + 머리글과 내용 사이 간격 + 구역 사이 간격」 세 값을 한 자리에 모읍니다(`SPEC §5.9`).
카드의 순위 묶음, 상세의 코어 격자·증가량 순위·앱 목록이 모두 이 자리를 소비하므로, 본체와 상세가 「같은 구역 머리글 방식」을 쓴다는 것이 조립 코드가 아니라 상수 참조로 표현됩니다.

### 카드 조립

- CPU 카드는 제목 묶음(머리글·초점 값·계열 요약) / 그래프 묶음 / 순위 묶음 세 덩어리이고, 덩어리 사이가 `betweenSections`입니다(`SPEC §5.6`).
- Memory 카드는 제목 묶음(머리글·초점 줄) / Pressure·구성 묶음 / 순위 묶음 세 덩어리입니다. 초점 줄은 「사용 중(초점 역할) + / 전체(본문 값 역할) + 구성 누적 바」 한 줄이고, 표시하는 값은 그대로입니다(`SPEC §5.1`).
- 상세 두 화면은 같은 역할 집합과 같은 구역 간격을 쓰고, 직접 글꼴 지정이 남지 않습니다(`SPEC §5.9`).

## 2. 데이터 흐름

이 feature는 상태를 더하지 않고 새 입력·새 통합 지점·새 실패 경로도 만들지 않습니다.
수집 → 조립 → 표시 경로는 그대로입니다.

`MonitoringScheduler` tick → `ApplicationCoordinator` → `DashboardPresentationStore.updateCPUCard`·`updateMemoryCard` → `ResourceCardState<Presentation>` → `CPUCardView`·`MemoryCardView`(그리고 선택된 카드의 자식 팝오버 → `CPUDetailView`·`MemoryDetailView`).

이 feature가 닿는 곳은 마지막 한 칸, **표시 값이 화면 그림과 문자열이 되는 자리**뿐입니다.

1. 본체 루트가 팝오버 바탕 면을 깔고, 그 위에 두 카드가 각각 자기 면을 깝니다. 상세 팝오버 루트는 카드 면과 같은 값을 깝니다(`SPEC §5.5`, `SPEC §5.11`).
2. `HistoryGraphView`의 `Canvas`는 **기준선 하나 → 두 밴드 채움 → 두 밴드 경계선** 순으로 그립니다. 세로 눈금·미수집 빗금·판 테두리 레이어가 사라지므로 그리기 순서가 다섯 레이어로 줄고, 기준선을 맨 처음 그려 반투명 밴드 사이로 비치게 하는 기존 이유는 그대로입니다(`SPEC §5.2`, `SPEC §5.3`).
3. 값이 없으면 자리표시가 **같은 기준선 하나만** 같은 높이·같은 좌표에 그립니다. 점도 선도 그리지 않는 계약이 그대로이고, 값 있음 경로와 자리표시 경로가 같은 레이어 하나에서 갈라지므로 두 그림이 어긋날 자리가 없습니다(`SPEC §5.13`).
4. `HistoryGraphTimeAxis`는 그대로 세 문자열과 미수집 비율을 내놓습니다. 비율의 소비자가 그리기에서 사라지고 **수집 진행 문구를 만드는 계산으로만** 남습니다 — 「아직 수집 중이라는 사실과 얼마나 모였는지」는 축 아래 문구가 계속 나릅니다(`SPEC §5.3`).
5. 코어 칸은 `CPUCoreUsageStep.step(for:)`이 고른 네 단계 중 하나를 코어 채움 색 집합의 세 값 중 하나로 옮겨 칠합니다. tick마다 하는 일은 정수 비교 최대 세 번과 이미 확정된 상수 선택뿐입니다(`SPEC §5.15`).
6. Memory 구성 바·도넛·두 범례는 그대로 `MemoryCompositionCategory` 하나를 색 진입점에 넘깁니다. 도넛 범례는 같은 행 안에서 이름 열과 값 열이 붙어 배치됩니다(`SPEC §5.10`).
7. 색의 라이트·다크 선택은 `NSColor(name:)` 클로저 안에서 AppKit이 appearance를 판정해 결정하므로 갱신 주기와 무관합니다. 새로 더하는 두 면도 같은 형태입니다.

상태 전이는 그대로입니다 — `collecting` / `normal` / `failure(lastKnown)` / `stopped(lastKnown)` 넷과 `DashboardSelection`의 `none` / `cpu` / `memory` 셋.
네 상태가 같은 슬롯 집합을 그린다는 계약이 유지되고, 값이 없는 초점 줄의 높이는 숨긴 초점 역할 한 글자가 계속 맡습니다 — 초점 역할이 커져도 네 상태의 카드 높이는 하나입니다(`SPEC §5.13`).

## 3. 인터페이스

경계를 가로지르는 계약만 둡니다.

- **`DashboardStyle.TypographyRole`** — 네 역할이 서로 다른 pt를 갖는 `Typography` 값을 내놓습니다. `focus`는 `value`의 두 배를 넘고, `pointSize` 필드는 그 글꼴의 실제 pt와 같습니다(`SPEC §5.1`).
- **`DashboardStyle.Spacing`** — 단계 집합 2 / 4 / 8 / 16 그대로입니다. 구역 사이를 쓰는 자리는 `betweenSections`를, 묶음 안 작은 무리(코어 칸 사이·카드 안쪽 여백)는 `betweenGroups`를 참조합니다(`SPEC §5.6`).
- **`DashboardStyle.Section`** — 구역 머리글의 역할, 머리글과 내용 사이 간격, 구역 사이 간격을 내놓습니다. 카드와 상세가 같은 값을 씁니다(`SPEC §5.9`).
- **`DashboardStyle.CardSurface`** — 안쪽 여백·모서리 반경·채울 색을 내놓고 테두리 값을 내놓지 않습니다(`SPEC §5.5`).
- **`DashboardStyle.ValueColumn`** — 여섯 폭을 새 역할 실측값으로 내놓습니다. 숫자 열은 `value` 역할, 단위 열은 `label` 역할로 재는 기존 계약 그대로입니다(`SPEC §5.1`).
- **`DashboardColorPalette`의 면 두 개** — `popoverBackground`와 `cardSurface`를 라이트·다크 각각 확정한 값으로 내놓습니다. 대비 검증 테스트가 배경 리터럴 대신 이 값을 appearance별로 풀어 쓸 수 있도록, `Color`와 함께 appearance별 `NSColor`를 얻는 경로를 공개합니다(`SPEC §5.11`).
- **`DashboardColorPalette`의 코어 채움 집합** — `CPUCoreUsageStep`의 단계를 받아 세 값 중 하나를 돌려주는 진입점 하나만 공개합니다. CPU 램프 진입점(`cpu(_:)`)과 값을 공유하지 않습니다(`SPEC §5.7`).
- **`HistoryGraphLayout`** — 판 높이 100, 축 간격 4, 축 라벨 줄 높이(새 `label` 역할 실측), 슬롯 높이를 내놓습니다. 값 있음 경로와 자리표시 경로, 카드 높이를 재는 단위 테스트가 소비합니다(`SPEC §5.13`).
- **`HistoryGraphGridline`** — 눈금 값 집합 `[25, 50, 75]`(코어 단계 경계의 출처)와 **실제로 그리는 기준선 집합**(그 가운데 값 하나에서 유도), 선 두께, 값→세로 좌표 변환을 내놓습니다. 세로 눈금 관련 진입점은 사라집니다(`SPEC §5.2`).
- **`CPUCoreUsageStep`** — 사용률을 받아 네 단계 중 하나를 돌려주는 순수 함수와 경계값 `[25, 50, 75]`입니다. 경계는 `HistoryGraphGridline`의 눈금 값 집합에서 유도되고 값이 바뀌지 않습니다(spec.md §3).
- **`ApplicationRankingSampling`** — 카드 머리글은 정원과 제외 규칙이 빠진 짧은 이름표를, 카드 접근성 이름용 문구는 정원과 제외 사실을 담은 문자열을, 상세 목록 안내는 기존 `topApplicationsCaption(count:)`를 각각 내놓습니다. 세 문자열이 서로 다른 진입점을 갖습니다(`SPEC §5.4`, `SPEC §5.12`).
- **접근성 계약** — 아래를 변경 전과 같은 범위로 유지합니다(`SPEC §5.12`).
  카드의 `.ignore` + `.accessibilityLabel` + `.isButton` + `CPUCard`·`MemoryCard` 식별자,
  코어 칸의 `.ignore` + `.isStaticText` + `"코어 N"` 라벨 + `"N%"` 값 + `CPUCore-N` 식별자,
  하위 프로세스 행의 `AppRow-<앱 키>` 식별자와 그 아래 정확히 두 개의 `StaticText`,
  상세 콘텐츠의 `DashboardDetail` 식별자, 본체의 `DashboardContainer` 식별자.

## 4. 영향 범위

### production 파일

- `ResourceRunner/DashboardStyle.swift` — 네 역할의 글꼴과 `pointSize`, 여백 사용처를 담은 새 `Section` 자리, `CardSurface`의 테두리 제거와 면 채움, `ValueColumn` 여섯 폭.
- `ResourceRunner/DashboardColorPalette.swift` — 팝오버 바탕·카드 면 두 값, 코어 채움 색 집합과 진입점, `cpuCoreFill(_:)`의 유도 변경.
- `ResourceRunner/DashboardPresentation.swift` — `HistoryGraphLayout.axisLabelHeight`, `HistoryGraphGridline`의 그리는 기준선과 세로 눈금 제거, 카드 접근성 이름의 기준선 문구와 순위 안내 문구.
- `ResourceRunner/DashboardView.swift` — 본체·상세 루트의 면, 두 카드의 표면과 구역 간격, Memory 초점 줄 조립, 그래프 그리기 레이어 목록과 세 그리기 함수(세로 눈금·판 테두리·미수집 빗금), 자리표시 레이어 목록, 코어 칸의 막대 높이와 채움 색 진입점·코어 번호 글꼴, 도넛 범례 행의 열 구성, 상세 전반의 직접 글꼴 지정, 상세 앱 목록 머리글 묶음, 고정 크기 두 상수.
- `ResourceRunner/ApplicationRanking.swift` — 카드 머리글 문구와 접근성용 문구의 분리.

새 파일을 만드는 경우 `.xcodeproj` 수정은 필요하지 않습니다 — 이 프로젝트는 `PBXFileSystemSynchronizedRootGroup`을 씁니다.

표시 값의 정의·계산·수집 주기·이력 링 용량이 그대로이므로 `SystemMetrics`·`CPUSystemMetricsCollector`·`MemorySystemMetricsCollector`·`ProcessSurveyCollector`·`MonitoringSampleStore`·`ProcessHistoryStore`·`ApplicationCoordinator`·`StatusBarController`에는 변경이 없습니다.
`ApplicationRowIcon.swift`의 아이콘 자리 크기는 spec.md §4가 제외한 범위라 건드리지 않습니다 — 카드 행 아이콘 12pt가 새 행 높이 15pt보다 작아 행 높이를 정하지도 않습니다.

### 기준을 갱신할 테스트

갱신 원칙은 §5 DP15에 두고, 요구가 남아 있는 단언은 지우거나 완화하지 않습니다.

- `DashboardColorPaletteTests` — 배경 리터럴 두 개를 팔레트의 면 값으로 바꾸고, `cpuCoreFill(step) == cpu(step)` 단언을 코어 채움 집합의 새 요구를 잠그는 형태로 다시 씁니다. CPU 램프·Memory 구성·밴드 합성 단언은 기준면만 바뀌고 그대로 성립합니다.
- `DashboardCardLayoutTests` — 카드 높이 기준값 290 / 171과 M3 상한 334, 자리표시 픽셀 영역 리터럴 셋, 「카드 안쪽 채움 잉크 0 · 테두리 잉크 > 0」 단언이 모두 새 값·새 형태로 바뀝니다. 마지막 단언은 「카드 면 잉크 > 0이고 그 면이 팝오버 바탕과 다르다」로 방향이 뒤집힙니다.
- `CPUCoreGridVerticalBudgetTests` — 14코어 172→176, 56코어 446→476, 57코어 이상 초과 유지.
- `CPUCoreUsageGridTests` — 칸 안 잉크 띠 세 개와 격자 높이 공식은 그대로이고, 「단계 경계 앞뒤에서 채움 색이 갈린다」는 색이 실제로 갈리는 경계(50 / 75)로 다시 씁니다.

## 5. Decision Points

### DP1. 네 글자 역할을 무엇에 매핑하는가

`SPEC §5.1`은 네 역할이 서로 다른 크기를 갖고 초점 값이 본문 값의 두 배 이상일 것, 색과 굵기를 지워도 크기만으로 위계가 읽힐 것을 요구합니다.
시안은 30 / 12 / 11 / 10을 썼습니다.

macOS 의미 글꼴이 실제로 내놓는 pt는 26 / 22 / 17 / 15 / 13 / 12 / 11 / 10 여덟 계단뿐이고, 네 역할을 그 안에서 골라야 「두 배 이상」과 「넷이 서로 다름」이 동시에 성립합니다.

- 옵션 A — 고정 pt를 쓴다(시안 값 30 / 12 / 11 / 10 그대로). 대가: 사용자의 시스템 텍스트 크기 설정을 따라가지 못하고, `Typography.pointSize` 필드와 실제가 어긋나는 지금 문제가 그대로 남는다. 30pt는 의미 글꼴 계단에 없어 위계가 시스템 다른 화면과 갈린다.
- 옵션 B — focus `.title`(22) / value `.subheadline`(11) / label `.caption`(10) / heading `.headline`(13). pt 비는 22 / 11 = 2.00으로 딱 맞는다. 대가: 렌더 줄 높이 비가 26 / 14 = 1.86으로 **높이로 재면 두 배에 못 미치고**, 머리글이 본문 값보다 커져 시안의 위계와 뒤집힌다.
- 옵션 C — focus `.largeTitle`(26) / value `.callout`(12) / label `.subheadline`(11) / heading `.caption`(10, semibold). pt 비 2.17, 렌더 높이 비 31 / 15 = 2.07. 대가: 초점 값이 커져 Memory 초점 줄의 폭이 빠듯해지고(§DP12), 카드·본체·M3 예산이 모두 커진다.

**채택: C.**

- 「두 배 이상」을 pt로 재든 렌더 줄 높이로 재든 **두 방식 모두에서 성립하는 유일한 조합**입니다. 옵션 B는 재는 방식에 따라 판정이 갈리므로, 완료 조건이 재는 방식에 의존하게 됩니다.
- 시안의 30 / 12 / 11 / 10에서 초점만 의미 글꼴의 가장 가까운 계단(26)으로 내린 것이고 나머지 셋은 시안 값과 같습니다. 시안의 위계 모양(머리글이 가장 작고 굵음)이 그대로 유지됩니다.
- 의미 글꼴을 쓰면 시스템 텍스트 크기 설정이 네 역할에 함께 적용되고, `Dynamic Type`이 바뀔 때 역할 사이 비가 시스템이 정한 관계를 따릅니다. 고정 pt는 그 관계를 이 앱이 혼자 정하게 됩니다.
- 색과 굵기를 지워도 13 / 14 / 15 / 31의 네 줄 높이가 남습니다. 라이트·다크 렌더에서 초점 값이 나머지와 한눈에 갈리는 것을 확인했습니다.

**`pointSize` 필드의 뜻을 고칩니다.** 지금 `.caption`의 선언값 11은 실측 10과 다릅니다.
이 필드는 「그 글꼴의 실제 pt」를 뜻하는 것으로 못 박고, 단위 테스트가 `NSFont.preferredFont(forTextStyle:)`의 실측 pt와 견주어 어긋나면 잡습니다 — 선언값이 틀린 채로 「네 역할의 크기가 다르다」를 단언하면 그 단언이 거짓을 지키게 됩니다.

**값 열 폭 여섯 개를 새 역할로 다시 잽니다**(26 / 39 / 45 / 13 / 19 / 61 → 31 / 45 / 53 / 14 / 21 / 67).
이 폭들은 리터럴이지만 근거는 실측이며, 기존 테스트가 같은 역할로 다시 재서 지키는 형태가 그대로입니다.
다시 재지 않으면 순위 행의 숫자가 열 폭을 넘어 두 줄로 접히고, 그 순간 행 높이가 15에서 30으로 뛰어 카드 높이 계약(`SPEC §5.13`)이 깨집니다 — 실제로 실측 도중 이 현상을 관측했습니다.

### DP2. 구역 사이 여백을 어떤 단계로 올리는가

`SPEC §5.6`은 구역 사이 여백이 이전보다 넓어지고, 여백 단계가 이전보다 위쪽 단계를 실제로 쓸 것을 요구합니다.
시안의 구역 간 값은 18pt이고, 현재 단계 집합은 2 / 4 / 8 / 16이며 카드 안 구역 사이는 8을 씁니다.

- 옵션 A — 새 단계 18을 더한다. 대가: 2 / 4 / 8 / 16의 배수 관계가 깨지고, 단계가 다섯이 되면 「어느 자리가 어느 단계인가」의 판단 지점이 늘어난다.
- 옵션 B — 새 단계 12를 더한다. M3 예산에 24pt의 여유가 생긴다. 대가: A와 같은 이유로 배수 관계가 깨지고, 12는 시안 값도 기존 값도 아니어서 근거가 「예산에 맞으니까」뿐이다.
- 옵션 C — 시안의 18을 기존 `betweenSections`(16)로 흡수한다. 대가: M3 모델 1 예산의 여유가 1pt만 남는다(§DP12).

**채택: C.**

- `betweenSections`(16)는 이미 존재하는 **위쪽 단계**이고, 8에서 16으로 올리는 것이 `SPEC §5.6`의 「위쪽 단계를 실제로 쓴다」를 글자 그대로 만족합니다. 새 단계를 더하면 그 문장이 요구한 것(쓰지 않던 단계를 쓰기 시작)이 아니라 다른 것(단계를 늘리기)이 됩니다.
- **상세가 이미 구역 사이에 16을 쓰고 있습니다.** 카드도 16을 쓰면 `SPEC §5.9`의 「같은 여백 단계」가 조립 관례가 아니라 **같은 상수 참조**로 성립합니다. 옵션 A·B는 카드와 상세가 서로 다른 값을 쓰게 만들어 그 조건을 다시 조립 관례에 맡깁니다.
- 18과 16의 차 2pt는 시각적으로 구분되지 않는 반면, 그 2pt를 얻으려고 단계를 늘리는 대가는 영구적입니다.

`betweenGroups`(8)는 사라지지 않습니다 — 카드 안쪽 여백(`CardSurface.contentPadding`)과 코어 격자 칸 사이 간격이 계속 이 단계를 씁니다.
카드 사이 간격도 `betweenSections`(16) 그대로 둡니다. 카드 안 구역 사이와 같은 값이 되지만, 카드 경계는 이제 간격이 아니라 **면**이 만들므로 두 경계의 세기가 뒤집히지 않습니다(§DP3).

카드 안쪽 여백을 8에서 10 이상으로 키우는 변형은 접습니다 — 실측에서 10pt는 M3 모델 1 프레임을 1099pt로, 12pt는 1115pt로 만들어 기준 기기를 넘깁니다(§DP12).

### DP3. 바탕과 카드의 면을 무슨 값으로 두고 누가 소유하는가

spec.md §3이 라이트는 바탕을 시스템 흰색보다 낮추고 카드를 흰색으로, 다크는 어두운 바탕 위에 밝은 카드로 두라고 정했고, `SPEC §5.5`는 두 모드에서 카드가 **같은 방향으로** 떠오를 것을, `SPEC §5.11`은 바탕과 카드 면 자체도 서로 구분될 만큼 갈릴 것을 요구합니다.

- 옵션 A — 시스템 색만 조합한다(바탕 `windowBackgroundColor`, 카드 `controlBackgroundColor` 등). 대가: spec.md §1이 확인한 대로 라이트 `windowBackgroundColor`가 이미 `#FFFFFF`라 카드를 더 밝게 만들 수 없다. 방향을 맞추려면 시스템이 정한 값을 벗어나야 한다.
- 옵션 B — 라이트·다크 각각 값을 확정한다. 바탕 `#ECECEC` / `#1E1E1E`, 카드 `#FFFFFF` / `#2E2E2E`. 대가: 시스템이 나중에 창 배경을 바꿔도 이 앱만 따라가지 않는다.
- 옵션 C — B에 더해 카드에 그림자를 깔아 부양감을 강화한다. 대가: spec.md §3이 「갱신 주기마다 하는 일이 늘지 않는다」를 걸었고, 그림자는 카드마다 매 렌더 패스에서 합성된다. 면만으로 조건이 성립하면 치를 이유가 없다.

**채택: B.**

- 두 값은 임의로 고른 것이 아니라 **직전 feature가 대비 검증의 근사 배경으로 쓰던 값**입니다. 라이트 `#ECECEC`와 다크 `#2E2E2E`가 그것이고, 이 결정은 그 근사를 **이 앱이 소유하는 실제 면**으로 승격시킵니다. 그 결과 `SPEC §5.11`의 「근사 배경이 아니라 실제로 놓이는 면」이 값을 새로 만들지 않고 성립합니다.
- 다크 카드 면이 근사 배경과 같은 값이므로 **다크 팔레트 전체가 재검증 없이 그대로 통과**하고, 라이트는 기준면이 `#ECECEC`에서 `#FFFFFF`로 올라가 어두운 색들의 대비가 모두 **올라갑니다**(CPU 램프 라이트 3.07~9.76 → 3.63~11.53). 값이 모자라 다른 조건에 기대는 색이 생기지 않습니다.
- 방향이 두 모드에서 같습니다 — 라이트 `ΔL*` 6.6, 다크 `ΔL*` 7.7로 **둘 다 카드가 바탕보다 밝습니다**. spec.md §2가 말한 「한쪽에서만 카드가 가라앉는 인상」이 생기지 않습니다.
- 불투명 면을 깔면 팝오버 재질 뒤 화면에 따라 합성 배경이 달라지던 불확실성이 콘텐츠 사각형 안에서 사라집니다. 직전 feature가 「추정으로 남는 것」에 적어 둔 항목이 이 결정으로 닫힙니다.

**상세 팝오버의 바탕은 본체 바탕이 아니라 카드 면과 같은 값을 씁니다.**
상세는 카드 하나를 펼친 화면이고, 그 안의 색(코어 채움, 도넛 구간, 두 밴드 스와치)이 본체 카드 안의 같은 색과 **같은 면 위에 놓여야** 대비 기준이 하나로 유지되기 때문입니다(`SPEC §5.11`).
상세 안에 다시 카드를 얹는 구성은 접습니다 — spec.md §4가 상세에 새 구역을 더하지 않는다고 정했고, 구역마다 면을 두면 그 자체가 새 구조입니다.

면 색의 소유자는 `DashboardStyle`이 아니라 `DashboardColorPalette`입니다.
대비 검증 테스트가 기준면을 **다른 색과 같은 경로로** 읽어야 하고, 팔레트가 이미 라이트·다크를 각각 확정해 내놓는 자리이기 때문입니다.

### DP4. 카드 표면의 테두리를 어떻게 할 것인가

`SPEC §5.5`는 카드 테두리를 그리지 않고도 카드 경계가 갈릴 것을 요구합니다.
현재 `CardSurface`는 `borderWidth = 1`과 `borderColor`를 갖고 두 카드가 `strokeBorder`만 그립니다.

- 옵션 A — 테두리 상수를 남겨 두고 값만 0으로 만든다. 대가: 「테두리를 그리지 않는다」가 값 하나에 걸려 있어, 나중에 되살리는 변경이 조용히 통과한다. 테두리 잉크를 세던 기존 테스트도 0을 세는 형태로 남아 무엇을 지키는지 알 수 없게 된다.
- 옵션 B — 테두리 상수를 없애고 `CardSurface`가 채울 색만 갖는다. 대가: 고대비 설정처럼 면 대비가 시스템에 의해 다르게 처리되는 환경에서 기댈 보조 수단이 없다.
- 옵션 C — 면과 테두리를 함께 둔다. 대가: spec.md §2가 지적한 「선이 과하다」가 카드 경계에서 그대로 남고, `SPEC §5.5`의 「선이 아니라 면」과 정면으로 어긋난다.

**채택: B.**
`CardSurface`에서 `borderWidth`·`borderColor`를 없애고 채울 색을 둡니다.
상수가 사라지면 테두리를 되살리는 변경이 반드시 새 상수를 만들어야 하므로 눈에 띕니다.
모서리 반경 8과 `contentPadding` 8, `.contentShape(RoundedRectangle)`(탭 영역)은 그대로입니다 — 반경은 면의 모양이지 테두리의 속성이 아니고, 탭 영역은 표면 표현과 무관합니다.

고대비 환경의 보조 수단은 면 대비 자체입니다. 라이트 `ΔL*` 6.6 / 다크 7.7은 시스템이 대비를 올릴 때 함께 벌어지는 방향이며, 카드 경계를 잃는 방향이 아닙니다.

### DP5. 그래프 판의 보조 표시를 어디까지 걷어내는가

`SPEC §5.2`는 가로 기준선이 하나만 남고 세로 눈금이 없을 것, 판이 여러 칸으로 갈라져 보이지 않을 것, 값의 높이를 어림하는 일이 남은 기준선 하나로 계속 될 것을 요구합니다.
현재 판에는 가로 기준선 셋(25 / 50 / 75) + 세로 눈금 넷 + 판 테두리 한 겹이 같은 색·같은 두께로 그려집니다.

- 옵션 A — 세로 눈금만 지우고 가로 기준선 셋과 테두리를 남긴다. 대가: 「기준선이 하나만 남는다」를 만족하지 않는다.
- 옵션 B — 세로 눈금과 가로 기준선 둘을 지우고 50%선과 판 테두리를 남긴다. 대가: 테두리는 판을 사각형으로 닫아 두므로 「판이 여러 칸으로 갈라져 보이지 않는다」는 만족하지만, spec.md §2가 「기준선·세로 눈금·판 테두리·미수집 빗금이 겹쳐」를 함께 문제로 지목했다. 남은 선이 데이터보다 강한 상태가 이어진다.
- 옵션 C — 세로 눈금·가로 기준선 둘·판 테두리를 모두 지우고 50% 가로선 하나만 남긴다. 대가: 판의 위·아래 끝(0%·100%)을 나타내는 선이 사라져, 값이 100%에 가까울 때 「어디가 천장인지」가 선으로는 표시되지 않는다.

**채택: C.**

- 남는 기준선을 50%로 고르는 이유는 셋입니다 — ① 세로 범위의 한가운데라 위·아래 어느 쪽으로도 같은 거리에서 어림이 됩니다 ② 코어 단계 경계 25 / 50 / 75 중 가운데 값이라 두 표현이 여전히 같은 눈금 위에 있습니다 ③ 값이 낮은 구간(대부분의 시간)에서 밴드가 선을 덮지 않습니다.
- 0%·100% 경계는 선이 아니라 **판의 높이 자체**가 나타냅니다. 판 높이 100pt에서 1%p가 정확히 1pt이고(직전 feature DP2), 축 라벨 줄이 판 바로 아래에 붙어 판의 아래끝을 표시합니다. 위끝을 선으로 표시하지 않는 대가는 값이 100%에 닿는 드문 구간에 한정되며, 그 구간의 실제 값은 카드 초점 값이 26pt로 함께 보여 줍니다.
- 직전 feature DP3이 판 테두리를 채택한 근거는 「자리표시 상태에서 그래프 자리를 같은 크기로 나타낸다」였습니다. 그 역할은 이제 `HistoryGraphLayout`의 고정 슬롯 높이와 축 라벨 줄이 맡고, `SPEC §5.13`은 크기·위치 불변만 요구하므로 선이 그 일을 할 필요가 없습니다.

`HistoryGraphGridline`에서 `verticalDivisionCount`와 `verticalTickNormalizedXPositions(timeRange:)`를 없앱니다.
「눈금 값 집합 `[25, 50, 75]`」는 남습니다 — spec.md §3이 코어 단계 경계를 고정했고 그 출처가 이 배열이기 때문입니다.
그리는 대상은 그 배열의 가운데 값 하나에서 유도하며, 새 리터럴 50을 두지 않습니다.

**카드 접근성 이름의 기준선 문구는 화면과 같은 값으로 맞춥니다** — 「기준선 25%·50%·75%」가 「기준선 50%」가 됩니다.
`SPEC §5.12`가 요구하는 것은 항목이 빠지지 않는 것이고, 기준선 항목은 남습니다.
화면에 없는 기준선 둘을 계속 낭독하면 접근성 계층이 화면보다 **없는 것을 더** 말하게 되어 두 계층이 어긋납니다.

### DP6. 값이 없는 자리표시는 무엇으로 그래프 자리를 나타내는가

지금 자리표시는 격자·세로 눈금·판 테두리 셋으로 자리를 표시합니다. DP5가 그 셋 중 둘을 없애므로 자리표시가 기댈 것이 달라집니다(`SPEC §5.13`).

- 옵션 A — 판 전체에 카드 면보다 한 단 낮은 면을 깔아 그래프 자리를 면으로 표시한다. 대가: 면 단계가 바탕·카드에 이어 셋이 되고, 값이 있을 때도 그 면을 깔지 않으면 두 경로의 그림이 갈린다. 값이 있을 때도 깔면 spec.md §2가 없애려는 「보조 표시가 데이터보다 강한 상태」를 면으로 되살린다.
- 옵션 B — 자리표시에만 「수집 중」 문구를 판 가운데 둔다. 대가: 같은 사실을 축 라벨 줄의 진행 문구가 이미 말하고 있어 같은 정보가 두 번 나온다. 값이 있을 때 그 문구가 사라지므로 두 경로의 조립이 갈린다.
- 옵션 C — 값 있음 경로와 똑같이 **기준선 하나만** 그리고, 그래프 자리는 고정 슬롯 높이와 축 라벨 줄이 나타낸다.

**채택: C.**

- 두 경로가 **같은 레이어 목록의 첫 항목**을 공유하고, 값이 있을 때만 그 위에 밴드가 얹히는 구조가 됩니다. 한쪽 경로에서 요소가 빠지면 레이어 배열 단언이 잡습니다.
- 「여기가 그래프 자리」를 말하는 것은 판 바로 아래 붙는 축 라벨 줄입니다 — 「10분 전」과 「지금」이 양끝에, 수집 진행 문구가 가운데에 있어 시간 축이 있는 자리임이 화면에서 읽힙니다. 이 줄은 네 상태에서 모두 같은 높이로 남습니다.
- 크기·위치 불변은 선이 아니라 `HistoryGraphLayout.slotHeight`가 보증합니다. 옵션 A·B는 그 보증에 아무것도 더하지 않으면서 두 경로를 갈라 놓습니다.

### DP7. 아직 수집되지 않은 구간을 무엇으로 바꾸는가

`SPEC §5.3`은 미수집 구간이 자기 경계를 가진 면으로 보이지 않을 것, 그 구간에 점도 선도 그리지 않는 것은 그대로일 것, 수집 중이라는 사실과 진행은 축 아래 문구로 계속 확인될 것, 창이 다 찬 뒤에는 그 자리에 아무 표시도 남지 않을 것을 요구합니다.
현재는 간격 8pt 대각 빗금이 그 구간을 덮습니다.

- 옵션 A — 빗금을 더 옅게 한다. 대가: 여전히 빗금이 덮인 구간이 자기 경계를 갖는 면으로 읽힌다. 옅게 할수록 그 구간이 무엇인지도 덜 읽혀 두 조건을 함께 잃는다.
- 옵션 B — 빗금을 지우고 수집 시작 지점에 세로 구분선 하나를 긋는다. 대가: DP5가 세로선을 판에서 모두 걷어낸 직후에 세로선 하나를 되돌리는 것이라, 「그래프 판에 세로 눈금이 없다」(`SPEC §5.2`)와 화면에서 구분되지 않는다.
- 옵션 C — 빗금을 지우고 그 구간에 아무것도 그리지 않는다. 사실과 진행은 축 라벨 줄 가운데의 「데이터 수집 중 · 00:42 / 10:00」이 계속 나른다.

**채택: C.**

- `SPEC §5.3`의 네 문장이 모두 이 선택에서 성립합니다. 특히 「창이 다 찬 뒤에는 아무 표시도 남지 않는다」는 그리는 대상 자체가 없어 자동으로 성립하고, 빗금 시절처럼 「선분 수가 0이 된다」에 기대지 않습니다.
- 값 0으로 읽히지 않는 것은 그대로입니다 — 그 구간에 점도 선도 없고, 데이터가 시작하는 자리는 밴드 채움이 시작되는 자리로 화면에 그대로 드러납니다.
- 데이터 시작점을 따로 표시하지 않는 근거는 **밴드의 왼쪽 끝이 이미 그 자리**라는 것입니다. 표시를 더하면 같은 사실을 두 수단이 말하게 되고, 그중 하나는 DP5가 방금 걷어낸 세로선입니다.

`CPUUncollectedRegionHatch`와 `drawCPUUncollectedRegion`, 두 레이어 목록의 `.uncollectedRegion` 항목을 없앱니다.
`HistoryGraphTimeAxis.uncollectedNormalizedWidth`는 남깁니다 — 수집 진행 문구를 만드는 계산이고, 「표본이 없는 구간을 0으로 그리지 않는다」를 단위 테스트가 잡는 자리이기 때문입니다.

### DP8. 코어 색 E안을 네 단계 위에 어떻게 얹는가

`SPEC §5.7`은 75% 이상 코어가 한눈에 찾아지고 75% 미만은 서로 비슷한 톤으로 가라앉을 것을, `SPEC §5.8`은 색을 지워도 어느 코어가 얼마나 바쁜지 그대로 읽힐 것을 요구합니다.
spec.md §3이 코어 단계 경계 25 / 50 / 75%를 고정했으므로 **단계 수와 경계는 바꿀 수 없고**, 갈리는 것은 그 넷 위에 색을 어떻게 배정하느냐입니다.
시안 E안의 색은 사실상 셋입니다 — 가라앉은 톤 둘과 뜨는 톤 하나.

- 옵션 A — 네 단계에 네 색을 배정하되 75% 미만 셋을 서로 가깝게 둔다. 대가: 세 색이 가까울수록 「가라앉음」은 얻지만, 셋 다 3:1을 통과해야 하므로 명도 폭이 좁아지고 25 / 50 두 경계에서 색이 갈린다는 사실이 화면에서 읽히지 않는다. 읽히지 않는 구분을 색으로 유지하는 셈이다.
- 옵션 B — 단계 타입을 셋으로 줄인다. 대가: **spec.md §3이 고정한 경계 25 / 50 / 75%를 깬다.** 채택할 수 없습니다.
- 옵션 C — 네 단계를 그대로 두고 색을 세 값으로 배정한다. 25% 미만과 25~50%가 같은 색(`quiet`), 50~75%가 한 단 진한 같은 색조(`elevated`), 75% 이상이 다른 색조(`busy`).

**채택: C.**

- 단계 경계는 spec.md §3이 고정한 대로 남고, `CPUCoreUsageStep`와 그 유도식(`HistoryGraphGridline`의 눈금 값 집합)도 그대로입니다. 바뀌는 것은 **단계를 색으로 옮기는 배정 하나**입니다.
- 색이 갈리는 자리를 50%와 75% 둘로 좁힌 근거는 「조용하다 한 번만 튐」입니다. 25% 경계에서 색을 갈라 봐야 두 색이 비슷해 읽히지 않고, 그 구분은 이미 칸 안 수치와 채움 높이가 맡습니다(`SPEC §5.8`).
- 25% 미만과 25~50%가 같은 색이 되면서 **쉬고 있는 코어 대부분이 한 톤으로 평평해집니다.** 14코어 렌더에서 75% 이상 둘(92%·88%)만 주황으로 떠오르고 나머지 열둘이 배경처럼 가라앉는 것을 라이트·다크 모두에서 확인했습니다.

**확정 값과 검증 결과** — 기준면은 카드 면(라이트 `#FFFFFF` / 다크 `#2E2E2E`)입니다.

| 배정 | 라이트 | 대비 / `L*` / `C*` / `h` | 다크 | 대비 / `L*` / `C*` / `h` |
| --- | --- | ---: | --- | ---: |
| `quiet`(50% 미만) | `#7d869e` | 3.64 / 56.0 / 14.0 / 278.5 | `#7b849c` | 3.64 / 55.2 / 14.1 / 278.5 |
| `elevated`(50~75%) | `#576482` | 5.91 / 42.4 / 18.5 / 278.4 | `#9faccc` | 5.98 / 70.3 / 17.9 / 277.6 |
| `busy`(75% 이상) | `#c77036` | 3.62 / 56.1 / 54.8 / 57.1 | `#f29c66` | 6.29 / 72.0 / 49.3 / 57.0 |

- 여섯 값 모두 3:1을 넘습니다(`SPEC §5.11`).
- 가라앉음은 **채도**가 만듭니다 — `quiet`·`elevated`의 `C*`는 14~18.5로 CPU 램프(43~48)의 3분의 1 수준이고, `busy`만 `C*` 49~55입니다. 밝기가 아니라 채도로 갈리므로 「밝은 것이 위험」 같은 오독이 생기지 않습니다.
- 방향이 두 모드에서 뒤집히지 않습니다 — 라이트는 `quiet`(L\* 56)보다 `elevated`(L\* 42)가 어둡고, 다크는 `quiet`(55)보다 `elevated`(70)가 밝습니다. 「바쁠수록 배경에서 멀어진다」가 양쪽에서 같은 뜻입니다.
- `busy`의 색조(h 57)가 Memory 구성의 Compressed·Cached(h 55)와 겹칩니다. 직전 feature DP6이 「집합 사이의 색조 중복은 실격 사유가 아니다」를 확정했고, 두 자리는 다른 카드의 다른 화면입니다.
- 라이트에서 `quiet`와 `busy`의 `L*`가 56으로 같아 **회색조에서는 둘이 갈리지 않습니다.** spec.md §3이 명시적으로 허용한 상태이며, 그 자리는 칸 안 정수 퍼센트와 채움 높이가 맡습니다(`SPEC §5.8`).

**주황이 「위험」으로 읽히지 않는 근거**는 직전 feature DP9의 근거를 그대로 잇습니다.
이 앱에서 정상·경고·위험 세 단계를 나타내는 Memory Pressure는 색을 전혀 쓰지 않고 기호(`checkmark.circle`·`exclamationmark.triangle`·`xmark.octagon`)와 라벨로만 구분합니다.
코어 격자의 주황은 단계가 셋이 아니라 하나의 문턱(75%)이고, 빨강이 아니며, 같은 칸 안에 정수 퍼센트가 함께 있습니다(`docs/product.md` 「접근성」).

코어 채움 색은 CPU 램프에서 떨어져 나와 자기 집합이 되므로 `cpuCoreFill(step) == cpu(step)` 단언은 대상을 잃습니다.
그 자리를 메우는 것은 「세 값 모두 카드 면 대비 3:1 이상」, 「`busy`의 색조가 나머지 둘과 갈린다」, 「나머지 둘의 채도가 `busy`보다 낮다」입니다(§DP15).
트랙(`cpuCoreTrack`)은 구분 대상이 아닌 배경 대비 요소이므로 시스템 색 그대로입니다.

### DP9. 코어 막대 높이를 얼마로 키우는가

시안은 26pt이고 현재는 18pt입니다.
spec.md §3은 「논리 코어 56개가 CPU 상세 첫 화면에 들어오는 현재 상한을 낮추지 않는다. 코어 칸 크기를 키우려면 이 상한을 지키는 범위 안에서만 키운다」고 정했습니다.

새 타입 스케일에서 칸 높이는 `막대 + 2 + 값 줄 15 + 2 + 코어 번호 13`이고, 56코어는 8열 × 7행이며 격자 위 조립은 64pt입니다.
실측 결과 56코어 격자의 아래끝은 막대 18에서 462, **20에서 476**, 21에서 483입니다.

- 옵션 A — 18pt 그대로 둔다. 대가: 값 줄이 13에서 15로 커지는데 막대만 그대로라 칸 안에서 막대의 비중이 줄어든다. 「코어 칸 크기를 키우려면」을 아예 쓰지 않는다.
- 옵션 B — 20pt로 키운다. 480pt 안에 드는 최댓값이다. 대가: 시안의 26pt에 못 미쳐 막대의 인상 변화가 작다.
- 옵션 C — 26pt로 키우고 상세 팝업 높이를 525pt 이상으로 올린다. 대가: spec.md §3이 「이 상한을 지키는 범위 안에서만」이라고 쓴 문장은 상한이 제약으로 **작동할 것**을 전제한다. 상한을 옮겨 제약을 없애는 것은 그 문장이 요구한 판단을 회피하는 것이다. 두 상세의 고정 높이가 함께 커져 `DetailPopoverValuelessStateTests`·`DashboardDetailPopoverUITests`의 기준이 근거 없이 움직인다.

**채택: B(20pt).**

- 480pt 안에서 56코어를 지키는 **최댓값**이고, 21pt에서 483으로 넘칩니다. 「지키는 범위 안에서만 키운다」를 끝까지 쓴 값입니다.
- 상한 자체는 그대로 56입니다 — 20pt에서 57코어는 8행이 되어 아래끝이 536pt로 480을 넘습니다. 「현재 상한을 낮추지 않는다」가 성립하고, 올리지도 않습니다.
- 14코어 격자 아래끝은 166에서 **176**으로, 56코어는 446에서 **476**으로 바뀝니다.
- 시안 26pt를 포기하는 대가는 렌더로 확인했습니다 — 18pt와 26pt 렌더 모두에서 75% 이상 두 코어가 즉시 집혔고, `SPEC §5.7`의 판정을 가르는 것은 막대 높이가 아니라 **색조**였습니다. 높이는 그 판정에 결정적이지 않습니다.

코어 번호 줄의 글꼴을 `.caption2` 직접 지정에서 `heading` 역할로 바꿉니다(`SPEC §5.9`). 렌더 줄 높이는 13으로 같아 위 계산에 영향이 없습니다.
`CPUCoreGridLayout`의 열 상한 8과 칸 간격 8, `rows(coreCount:)`의 분할 규칙은 그대로입니다.

### DP10. 카드 순위 머리글에서 무엇을 빼고 제외 사실을 어디에 두는가

`SPEC §5.4`는 카드 순위 머리글이 정원과 제외 규칙을 늘어놓지 않을 것, 시스템 프로세스가 순위에서 빠진다는 사실은 상세 팝업에서 계속 확인될 것을 요구합니다.
현재 머리글은 「앱 TOP 5 · 시스템 프로세스 제외」이고, 같은 문자열이 두 카드의 접근성 이름에도 들어갑니다.
상세에서 그 사실을 말하는 문구는 **Memory 상세의 증가량 순위 한 자리에만** 있습니다.

- 옵션 A — 머리글을 지우고 목록만 남긴다. 대가: 목록이 무엇의 순위인지 화면에서 사라진다. 상세의 목록들은 모두 머리글을 갖는데 카드만 갖지 않게 되어 `SPEC §5.9`와 어긋난다.
- 옵션 B — 머리글을 「앱 TOP 5」로 줄인다. 대가: 정원을 여전히 늘어놓는다. 다섯 줄이 화면에 보이므로 숫자 5는 화면이 이미 말하고 있다.
- 옵션 C — 머리글을 「상위 앱」으로 줄이고, 제외 사실은 **두 상세의 앱 목록 머리글 아래 안내 줄**로 옮긴다.

**채택: C.**

- 「상위 앱」은 목록의 이름표이고 정원도 제외 규칙도 담지 않습니다. 실측 폭 29pt로 카드 콘텐츠 폭 232pt의 8분의 1입니다.
- 제외 사실을 **두 상세 모두**에 두는 것이 이 결정의 핵심입니다. 지금은 Memory 상세에만 있어 CPU 상세에서는 도달하지 않고, `SPEC §5.4`의 「상세 팝업에서 계속 확인됩니다」가 CPU 쪽에서 성립하지 않습니다. 문구는 이미 있는 `topApplicationsCaption(count:)`를 그대로 씁니다 — 새 문자열을 만들지 않습니다.
- 안내 줄은 상세 앱 목록의 기존 머리글 묶음 안에 「머리글(heading 역할) + 안내(label 역할)」 두 줄로 들어갑니다. 새 구역이 아니라 기존 구역의 머리글 묶음이 두 줄이 되는 것이라 spec.md §4의 「상세에 새 구역을 더하지 않는다」 안입니다.

**카드 접근성 이름은 정원과 제외 사실을 그대로 유지합니다.**
`SPEC §5.12`가 접근성으로 도달하는 정보가 하나도 줄지 않을 것을 요구하는데, 카드는 `children: .ignore`로 닫혀 있어 그 안의 목록을 훑어 정원을 세는 경로가 없기 때문입니다.
화면 사용자는 다섯 줄을 눈으로 세지만 접근성 사용자에게는 이름이 유일한 경로이므로, 두 문구가 갈리는 것이 도달 범위를 같게 유지하는 방법입니다.
그래서 `ApplicationRankingSampling`의 진입점을 화면용과 접근성용으로 나눕니다 — 한 문자열을 두 자리가 나눠 쓰던 구조가 이 결정으로 닫힙니다.

### DP11. Memory 상세 도넛 범례의 네 줄을 어떻게 정렬하는가

`SPEC §5.10`은 네 구간의 이름·값·단위가 한 줄에 정렬되고, 도넛을 보지 않고 범례만 읽어도 네 구간의 크기를 비교할 수 있을 것을 요구합니다.
현재 행은 `[스와치][이름] Spacer(minLength: 8) [값]`이고 범례 열이 `.frame(maxWidth: .infinity)`라, 렌더에서 이름은 왼쪽 끝에 값은 오른쪽 끝에 붙어 둘이 한 줄로 묶여 읽히지 않습니다.

- 옵션 A — `Spacer`의 최소 길이만 키운다. 대가: 범례 열 폭이 남을 때 여전히 이름과 값이 양끝으로 벌어진다. 폭에 따라 결과가 달라진다.
- 옵션 B — 이름 열을 네 이름의 실측 최댓값으로 고정하고, 값 열을 그 바로 뒤에 붙인다. 남는 폭은 행의 오른쪽에 남긴다. 대가: 이름이 길어지면(현지화·새 구간) 열 폭을 다시 재야 한다.
- 옵션 C — 이름과 값을 각각 다른 줄에 둔다. 대가: 범례가 여덟 줄이 되어 도넛 높이를 넘고, 「한 줄에 정렬」을 만족하지 않는다.

**채택: B.**

- 이름 열 폭은 네 이름의 이상적 폭 최댓값에서 유도합니다 — 실측은 App 22 / Wired 31 / **Compressed 67** / Cached 40이라 67이 기준입니다. 리터럴이 아니라 「네 이름 중 최댓값」이라는 유도식으로 두고, 단위 테스트가 네 이름을 다시 재서 열 폭 안에 드는지 확인합니다. `ValueColumn`이 이미 쓰는 방식과 같습니다.
- 값 열은 기존 `DashboardAlignedValueView`를 그대로 씁니다 — 숫자는 오른쪽, 단위는 왼쪽 맞춤이라 네 줄의 소수점과 단위 시작선이 이미 고정됩니다. 이름 열이 고정되면 **네 줄의 숫자 열이 같은 가로 위치에서 시작**해 크기 비교가 줄 사이에서 바로 됩니다.
- 폭 예산은 상세 콘텐츠 폭 368pt 안입니다 — 도넛 140 + 구역 간격 16 + (스와치 + 이름 열 67 + 값 열)로 남는 폭 안에 듭니다. 남는 폭을 행 오른쪽에 남기므로 도넛과 범례의 세로 중앙 정렬도 그대로입니다.

### DP12. 본체·상세 고정 크기와 M3 세로 예산을 어떻게 다시 확정하는가

**이 결정이 이 설계를 막을 수 있는 가장 큰 위험입니다.**
`SPEC §5.14`는 본체 팝오버와 두 상세의 고정 크기가 새 조립 기준으로 다시 확정되고, 카드 넷을 가정한 세로 합계가 갱신된 카드 높이로 다시 산출되며 기준 기기에서 성립함이 확인될 것을 요구합니다.
spec.md §3이 기준 기기를 `visibleFrame` 1084pt로 못 박았습니다.

**절차** — 직전 feature DP12의 옵션 B를 그대로 재사용합니다.
① 본체 `.frame(height:)` 제약을 임시로 걷는다 ② XCUITest로 팝오버를 열어 수집 중·정상 두 상태의 `app.popovers.element.frame.size.height`를 읽는다(두 값이 갈리면 슬롯 고정이 깨진 것이다) ③ 읽은 값에서 `NSPopover` chrome 26pt를 빼 `bodyHeight`에 넣고, 제약을 되건 뒤 같은 값이 다시 나오는지 확인한다.
산술로 값을 박는 옵션은 접습니다 — 직전 feature에서 산술 509가 실측 508로 나왔고, 어림값을 박아 하단 여백을 눌렀던 전례가 있습니다.

**새 조립의 산술**

| 카드 | 산술 | 실측 |
| --- | --- | ---: |
| CPU | 16 + 63 + 16 + 118 + 16 + 100 | **329** |
| Memory | 16 + 46 + 16 + 30 + 16 + 100 | **224** |
| Network·Disk(투영) | 16 + 62 + 16 + 118 | **212** |

본체 콘텐츠 = `32 + 329 + 16 + 224` = **601**, 팝오버 프레임 **627**.
착수 전 508 / 534에서 93pt 커졌고, 기준 기기 높이의 58%입니다.
실측이 직전 feature와 같은 1pt 차를 재현하면 600 / 626이 되며, **어느 값인지는 위 절차가 정합니다.**

**M3 카드 넷 예산** — 모델 1(Network·Disk는 초점 줄·보조 줄·그래프이고 순위 묶음이 없다)을 직전 feature DP1 그대로 기준으로 삼습니다.

그래프 묶음 높이를 `S`라 하면 CPU = `211 + S`, Network·Disk = `94 + S`, Memory = 224이고,
본체 콘텐츠 = `32 + 16 × 3 + (211 + S) + 224 + 2 × (94 + S)` = **`703 + 3S`**입니다.

| | 콘텐츠 | 프레임 | 기준 기기 1084 |
| --- | ---: | ---: | --- |
| 모델 1, `S = 118` | 1057 | **1083** | 성립(여유 1pt) |
| 모델 2(네 카드 모두 순위 묶음), `S = 118` | 1289 | 1315 | 초과 |

프레임 ≤ 1084를 만족하는 범위는 `S ≤ 118`, 곧 **판 ≤ 100pt**입니다.
직전 feature가 확정한 판 100pt가 새 타입 스케일에서 **모델 1 예산의 정확한 상한**이 되었습니다.

**채택: 모델 1을 기준으로 삼고 판 100pt·타입 스케일 C·구역 간격 16을 유지합니다.**

- 기준 기기에서 성립합니다(1083 ≤ 1084). spec.md §3이 요구한 조건이 충족됩니다.
- 여유가 133pt에서 1pt로 줄어든 것은 이 feature가 만든 결과가 아니라 **드러낸 결과**입니다. 카드를 넷으로 쌓는 고정 높이 배치는 이미 기준 기기 아래 모든 화면에서 성립하지 않았고(직전 feature DP1), `ROADMAP.md` M3가 그 해소를 배치 구조 변경(세로 스크롤·아코디언·2열) 의무로 지고 있습니다. 이 결정은 그 의무가 기준 기기에서도 사실상 필수가 되었다는 사실을 예산 수치로 기록합니다.
- 여유를 되찾으려고 타입 스케일을 낮추거나(DP1 옵션 B) 구역 간격을 12로 두거나(DP2 옵션 B) 카드 사이 간격을 12로 줄이는 변형은 접습니다. 셋 다 `SPEC §5.1`·`§5.6`이 요구한 변화를 「예산에 맞추려고」 되돌리는 것이고, 카드 넷 배치는 M3가 어차피 바꿀 배치입니다.
- 카드마다 그래프 높이를 다르게 두어 맞추는 방식도 그대로 접습니다 — `ROADMAP.md` M3 전환 기준의 「네 카드의 구조, 단위와 상호작용이 일관됩니다」와 충돌합니다.

**상세 크기는 400×480을 유지하고 새 조립으로 재확인합니다.**
근거는 셋입니다 — ① 코어 막대 20pt에서 56코어 격자 아래끝 476 ≤ 480이고 57코어는 536으로 넘칩니다(§DP9) ② 상세에는 그래프가 없어 타입 스케일이 늘리는 세로가 카드보다 작습니다 ③ 폭 368pt 안에 도넛 140 + 16 + 범례가 듭니다.
확인 수단은 직전 feature와 같습니다 — 단위 테스트(가장 넓은 행의 이상적 폭이 368pt 안, 격자 아래끝이 480pt 안)와 XCUITest(네 상태·펼침 전후·스크롤 전후의 `DashboardDetail` 프레임).

**`ROADMAP.md`와 `docs/design.md`의 세로 예산 수치를 새 값으로 갱신합니다**(`SPEC §5.14`) — 카드 산술 `173 + S` / `171`을 `211 + S` / `224`로, 모델 1 프레임 951pt를 1083pt로, 판 상한 서술을 새 계산으로 바꿉니다.

### DP13. 본체와 상세가 같은 언어를 쓰게 하는 공유 지점을 어디에 두는가

`SPEC §5.9`는 두 상세가 본체 카드와 같은 글자 역할 집합·같은 여백 단계·같은 구역 머리글 방식을 쓰고, 상세에만 있는 별도 규칙이 남지 않을 것을 요구합니다.
지금 상세에는 `.caption`·`.caption2`·`.caption.bold()` 직접 지정이 아홉 자리 남아 있습니다.

- 옵션 A — 직접 지정을 모두 `TypographyRole`로 바꾸는 것으로 끝낸다. 대가: 글자 역할은 통일되지만 「구역 머리글 방식」이 여전히 각 뷰의 조립에 흩어져 있어, 다음에 구역이 생길 때 같은 방식을 쓸 근거가 코드에 없다.
- 옵션 B — A에 더해 구역 머리글의 세 값(머리글 역할·머리글과 내용 사이 간격·구역 사이 간격)을 `DashboardStyle` 안 한 자리에 모으고, 카드와 상세의 모든 구역이 그 자리를 참조한다.
- 옵션 C — 구역을 그리는 공용 뷰(`SectionView` 같은 것)를 만들어 모든 구역이 그것을 쓴다. 대가: 구역마다 내용 조립이 크게 달라(격자·목록·도넛·그래프) 공용 뷰가 받는 인자가 늘어나고, 조립을 감싸는 층이 하나 더 생긴다. 지금 필요한 것은 값의 일치이지 조립의 일치가 아니다.

**채택: B.**

- 「같은 글자 역할 집합」은 직접 지정을 없애는 것으로, 「같은 여백 단계」는 DP2가 카드 구역 간격을 상세와 같은 `betweenSections`로 올린 것으로 이미 성립합니다. 남는 것은 「같은 구역 머리글 방식」이고, 그것을 값으로 표현하는 가장 작은 수단이 상수 한 자리입니다.
- 소비자는 카드의 순위 묶음, 상세의 코어 격자 구역, 증가량 순위 구역, 앱 목록 구역입니다. 네 자리가 같은 세 값을 참조하면 「상세에만 있는 별도 규칙」이 남을 자리가 사라집니다.
- M3에서 Network·Disk 카드가 생길 때 참조할 자리가 코드에 이미 있게 됩니다 — spec.md §2가 이 feature의 목적으로 적은 「M3에서 적용할 기준을 먼저 세운다」가 여기에 걸립니다.

바꿀 아홉 자리 — `TopApplicationsView`의 행과 캡션, 두 상세의 값 없음 문구, 코어 번호, 도넛 센터 라벨·값, 도넛 범례 행, 앱 행, 하위 프로세스 행.
도넛 센터 값의 `.caption.bold()`는 `focus`가 아니라 `value` 역할로 갑니다 — 도넛 가운데 수치는 카드의 초점 값과 같은 위계가 아니라 그 구역의 본문 값이고, 초점 역할 31pt는 지름 140pt 도넛 안에 들어가지 않습니다.

### DP14. 대비 검증의 기준 배경을 어디서 가져오는가

`SPEC §5.11`은 대비를 근사 배경이 아니라 그 색이 실제로 놓이는 면을 기준으로 잴 것을 요구합니다.
현재 `DashboardColorPaletteTests`는 배경을 `0xececec` / `0x2e2e2e` 리터럴로 들고 있습니다.

- 옵션 A — 리터럴을 새 면 값으로 바꾼다. 대가: 팔레트의 면 값과 테스트의 리터럴이 두 자리에 따로 있어, 한쪽만 바뀌면 검증이 조용히 다른 면을 기준으로 돌아간다.
- 옵션 B — 테스트가 `DashboardColorPalette`의 면 값을 appearance별로 풀어 그대로 기준으로 쓴다.

**채택: B.**
테스트가 이미 `NSAppearance.performAsCurrentDrawingAppearance`로 색을 푸는 경로를 갖고 있으므로(`resolvedSRGB`), 같은 경로로 면 값을 풀면 기준이 production 값과 한 자리에서 나옵니다.
면 값이 바뀌면 모든 대비 단언이 그 자리에서 함께 움직이고, 어떤 색이 3:1을 잃으면 즉시 드러납니다.

기준면의 배정은 「그 색이 실제로 놓이는 면」 그대로입니다 — 카드 안 요소(CPU 램프, Memory 구성, 코어 채움)는 **카드 면**, 상세 안 요소도 상세 바탕이 카드 면과 같은 값이므로 같은 면입니다(§DP3).
바탕 위에만 놓이는 색은 현재 없습니다. 바탕과 카드 면 자체가 서로 갈리는지는 별도 단언으로 둡니다(`SPEC §5.11`).

### DP15. 기준값·픽셀 단언 테스트를 어떤 원칙으로 갱신하는가

- 옵션 A — 깨지는 단언을 지우거나 완화한다. 대가: `SPEC §5.1`·`§5.6`·`§5.13`·`§5.14`를 지키는 수단이 없어진다. 채택하지 않습니다.
- 옵션 B — 리터럴을 새 숫자로 갈아 끼운다. 대가: 어떤 단언이 요구사항이고 어떤 단언이 우연한 스냅샷인지 구분이 남지 않는다.
- 옵션 C — 직전 feature DP13의 세 형태(유도형 / 불변형 / 기준값형)를 그대로 재사용한다.

**채택: C.**

- **유도형** — 순수 상수나 기준 조립의 측정값과 견줍니다. 리터럴을 쓰지 않습니다. 네 역할의 실측 pt(`NSFont.preferredFont`와 견줌), 값 열 여섯 폭(후보 문자열의 이상적 폭과 견줌), 그래프 슬롯 높이(판 + 간격 + 라벨 줄), 축 라벨 줄 높이(`label` 역할 실측 줄 높이), 코어 단계 경계(눈금 값 집합), 도넛 범례 이름 열 폭(네 이름의 최댓값), 격자 높이 공식이 여기에 듭니다.
- **불변형** — 숫자와 무관하게 성립해야 하는 관계입니다. 「네 역할의 크기가 서로 다르다」와 「초점 ≥ 본문 × 2」(`SPEC §5.1`), 「카드 안 구역 간격 > 착수 전 8pt」(`SPEC §5.6`), 「카드 면과 팝오버 바탕이 두 모드 모두에서 같은 방향으로 갈린다」(`SPEC §5.5`), 「팔레트의 모든 색이 카드 면 대비 3:1 이상」(`SPEC §5.11`), 「값 있음·없음 두 경로의 그래프 슬롯 높이가 같다」와 「여섯 상태에서 카드 높이가 하나」(`SPEC §5.13`), 「`busy`의 색조가 나머지 둘과 갈리고 나머지 둘의 채도가 더 낮다」(`SPEC §5.7`), 「사용률 50·75 경계 앞뒤에서 채움 색이 다르다」(`SPEC §5.7`)가 여기에 듭니다.
- **기준값형** — 숫자 자체가 요구사항인 자리만 리터럴로 둡니다. 본체 601(또는 절차가 고른 값) / 팝오버 627, 상세 400×480, 카드 높이 329 / 224, M3 모델 1 프레임 1083, 14코어 격자 아래끝 176, 56코어 476이 여기에 듭니다.

대상을 잃는 단언을 자리별로 못 박습니다.

- **세로 눈금 정규화 x 위치**(`DashboardPresentationTests`) — 잠그던 요구를 `SPEC §5.2`가 철회했습니다. 그 자리를 메우는 것은 「그리는 기준선이 하나다」와 「그 값이 눈금 값 집합의 가운데 값이다」입니다.
- **`cpuCoreFill(step) == cpu(step)`**(`DashboardColorPaletteTests`) — 코어 채움이 자기 집합을 갖게 되어 대상을 잃습니다. 그 자리를 메우는 것은 §DP8의 세 단언입니다. `cpuUser == cpu(.step3)`·`cpuSystem == cpu(.step1)`은 그대로입니다.
- **카드 테두리 잉크 > 0**(`DashboardCardLayoutTests`) — `SPEC §5.5`가 테두리를 없애라고 요구하므로 대상을 잃습니다. 그 자리를 메우는 것은 「카드 면 잉크 > 0」과 「카드 면이 팝오버 바탕과 다르다」입니다. 이 교체는 옵션 A의 「요구가 남아 있는데 단언만 지운다」와 다른 자리입니다.
- **`RampStep`가 넷**(`CPUCoreUsageGridTests`)은 그대로입니다 — CPU 램프는 두 밴드와 스와치 전용으로 네 단계를 유지합니다.
- **Memory 범례 이름이 스와치마다 붙는다**(`MemoryCompositionTests`)는 그대로 유지합니다 — 네 구간이 회색조에서 두 쌍으로 붙는 상태를 허용하는 조건이 이 이름이라는 직전 feature의 근거가 그대로입니다.

### DP16. 접근성·동작 줄이기·자체 부하가 새 표현에서 성립하는 근거

**접근성 (`SPEC §5.12`)** — 도달 경로를 바꾸지 않고 범위를 좁히지 않습니다.

- 카드는 `.accessibilityElement(children: .ignore)` + `.accessibilityLabel` + `.isButton` 조합과 두 식별자를 유지합니다. 카드 면이 생기고 여백이 벌어져도 접근성 계층에 새 노드가 생기지 않습니다.
- 카드 이름의 항목은 그대로입니다 — 초점 수치·상태·두 계열·기준선·순위 안내·시간 창·수집 진행·단축키. 기준선 문구의 **값**만 화면과 같게 하나로 줄고(§DP5), 순위 안내는 화면 머리글이 짧아져도 정원과 제외 사실을 유지합니다(§DP10).
- 코어 칸은 `.ignore` + `.isStaticText` + 이름/값 분리와 `CPUCore-N` 식별자를 유지합니다. 채움 색 집합이 바뀌고 막대가 2pt 높아져도 칸의 접근성 값은 같은 서식 함수의 결과입니다. 코어 번호가 1부터인 것도 그대로입니다(spec.md §4).
- 하위 프로세스 행은 `AppRow-<앱 키>` 아래 두 `StaticText`와 이름 줄의 소속 앱 접두를 유지합니다. 이 feature는 그 행의 글꼴만 역할로 바꿉니다.
- 그래프 판에서 사라지는 세로 눈금·테두리·빗금은 `Canvas` 안의 그림이라 접근성 노드가 없었습니다. 지워도 접근성 계층에서 잃는 것이 없습니다.
- 상세 앱 목록에 더해지는 안내 줄은 `Text` 하나라 접근성 계층에 정적 텍스트로 도달합니다 — 도달 범위가 **늘어나는** 방향입니다(CPU 상세에는 지금 없는 문구).

**동작 줄이기 (`SPEC §5.15`)** — 새 표현이 애니메이션을 전제하지 않습니다.
더하는 것은 면 채움 셋(팝오버 바탕·카드 둘)과 조정된 글꼴·여백·색 상수뿐이고, 빼는 것은 선분 여럿입니다.
모두 정적이며 `withAnimation`·`transition`·암시적 애니메이션을 새로 걸지 않습니다.
기존 `TimelineView(.periodic(from:by:))`는 그래프 가로축을 시계에 맞추는 재그리기이지 애니메이션이 아닙니다.

**자체 CPU 부하 (`SPEC §5.15`)** — 갱신 주기마다 하는 일이 **줄어듭니다.**

- 없어지는 일: 세로 눈금 4선분, 판 테두리 1경로, 미수집 빗금 최대 41선분(앱을 켠 뒤 최대 10분), 가로 기준선 2선분.
- 남거나 새로 드는 일: 가로 기준선 1선분, 코어 칸당 정수 비교 최대 3회와 상수 선택, 면 채움 셋(뷰 배경이라 매 tick 다시 계산되지 않습니다).
- 새 타이머·새 관찰자·새 이미지 생성·색 보간이 없고, 색은 `NSColor(name:)` 클로저 안에서 appearance가 바뀔 때만 해석되므로 tick과 무관합니다.
- 다운샘플 버킷 수는 판 **폭**에서 나오고 폭이 232pt로 그대로이므로 그리는 선분 수가 늘지 않습니다.
- 검증은 직전 feature와 같은 절차 — 팝오버를 열어 둔 채 앱 자신의 CPU 사용량을 관찰해 변경 전과 견주는 것입니다.

**크기·위치 불변 (`SPEC §5.13`)** — 고정 슬롯 계약이 그대로입니다.
값 없는 초점 줄은 숨긴 초점 역할 한 글자가 31pt를 맡고, 그래프 슬롯은 값 유무와 무관하게 `HistoryGraphLayout.slotHeight`를 씁니다.
순위 슬롯은 정원 5줄을 항상 그리고, Memory 구성 범례 줄은 수집 상태와 무관하게 네 이름을 그립니다.
값 열 폭을 새 역할로 다시 재는 것(§DP1)이 이 조건의 전제입니다 — 열이 좁으면 숫자가 두 줄로 접혀 값에 따라 행 높이가 갈립니다.
