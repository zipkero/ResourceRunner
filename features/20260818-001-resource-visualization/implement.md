## Section: 순위 정원과 목록 통합

- [ ] task-001: 카드 정원과 상세 정원 분리
  - 목적: 앱 순위 계산이 상위 20개까지 만들고, 카드의 순위 자리는 그중 앞 5개만 5줄 고정 슬롯으로 보여주며,
    상세 목록과 증가량 순위는 20개까지 받습니다.
    정원을 정하는 판단이 뷰 본문에 남지 않습니다.
  - 접근: `ApplicationRankingSampling`의 단일 상수 `topCount`를 카드 표시 정원(5)과 순위 계산·상세 표시 정원(20) 두 상수로 나누고,
    `ApplicationRanking.topEntries`의 `prefix`가 계산 정원을 쓰게 합니다.
    `ApplicationProcessGroupOrdering.displayedGroups`에 정원 인자를 더해 순서를 고정한 뒤 그 결과를 자르는 한 함수로 만들고
    기본값을 상세 표시 정원으로 둡니다.
    두 `assemble`에서 카드 순위 배열은 카드 정원으로, 증가량 순위는 상세 정원으로 각각 자르고,
    `CardRankingSlotView`의 고정 슬롯 정원은 카드 정원 상수를 참조합니다.
    평활화 창·앱 키 합산·값 내림차순·앱 키 사전순 tie-break·그룹 내부 프로세스 정렬은 건드리지 않습니다.
  - 검증 조건:
    - 결과: 앱이 20개보다 많은 입력에서 `topEntries`가 20개를 돌려주고,
      카드 표시 값의 순위 배열은 5개이며 그 5개가 계산 결과의 앞 5개와 같은 항목·같은 순서입니다.
      증가량 순위 배열은 20개까지 담깁니다.
      `displayedGroups`는 정원보다 많은 그룹을 받으면 정원만큼만 돌려주고, 그 순서는 자르기 전 정렬 결과의 앞부분과 같습니다.
      펼친 행이 있는 상태에서 새 그룹이 들어오면 그 그룹은 고정 순서 뒤에 붙어 정원 밖에 머물고,
      이미 표시되던 그룹의 순서와 위치가 바뀌지 않습니다.
      정원 상수 두 개 밖에서 정원 숫자를 직접 쓰는 자리가 남지 않습니다.
    - 확인: Swift Testing 단위 테스트로 `ApplicationRankingTests`에 다음을 단언합니다.
      계산 정원을 카드 정원(5)으로 되돌리면 「`topEntries`가 20개를 돌려준다」가 실패해야 하고,
      카드 조립에서 카드 정원 자르기를 지우면 「카드 순위 배열이 5개」가 실패해야 합니다.
      `displayedGroups`에서 정원 자르기를 순서 고정보다 **먼저** 적용하도록 바꿔치기하면
      「펼친 행이 있는 동안 표시 그룹의 순서와 구성이 그대로」가 실패해야 합니다.
      정원 인자를 무시하고 전체를 돌려주도록 바꾸면 개수 단언이 실패해야 합니다.
      정원 숫자의 중복 정의 부재는 `grep`으로 소스에서 확인합니다.
  - 참조: SPEC §5.1, ANALYSIS §1 「상세 순위 경계 — 목록 하나가 순위를 겸함」, ANALYSIS §2 「순위 정원과 통합된 목록」,
    ANALYSIS §3 「이력과 표시 값」, ANALYSIS §5 DP2

- [ ] task-002: 상세 앱 목록이 순위를 겸하도록 통합
  - 목적: CPU 상세와 Memory 상세를 열면 앱 사용량 순위 목록이 각각 하나만 있고,
    그 목록에서 각 앱의 하위 프로세스를 펼쳐 확인할 수 있으며, 같은 지표의 순위가 한 화면에 두 번 나타나지 않습니다.
    Memory 상세에서는 현재 사용량 목록과 최근 증가량 순위가 서로 다른 지표임이 머리글로 구분됩니다.
  - 접근: `MemoryCardDetail`에서 현재 사용량 순위 전용 필드를 제거하고 앱 목록 필드가 그 역할을 겸하게 하며,
    `CPUCardDetail`에도 순위 전용 필드를 만들지 않습니다.
    `MemoryDetailView`의 「현재 사용량 순위」 섹션(`TopApplicationsView` 호출)을 없애고
    `TopApplicationsView`는 증가량 순위 한 자리에서만 쓰이게 남깁니다.
    `ApplicationProcessGroupListView`의 머리글 문구를 그 목록이 어떤 지표의 순위이고 정원이 얼마인지 알리는 문구로 바꾸고,
    Memory 쪽 문구에는 「현재 사용량」을 넣습니다. 목록에 정원 인자를 넘깁니다.
    순서 고정 규칙·행 구조·`AppRow-<앱 키>` 식별자·라벨 전체 탭 히트 영역·왼쪽 8pt 여백은 그대로 둡니다.
    Memory 상세를 「현재 사용량 순위」로 찾던 UI 테스트 세 파일과 목록을 「전체 프로세스」로 찾던 한 파일의
    조회 문자열을 새 머리글에 맞춰 함께 고칩니다.
  - 검증 조건:
    - 결과: Memory 상세 표시 값에 현재 사용량 순위를 담는 필드가 존재하지 않고, 앱 목록 필드 하나만 그 지표를 담습니다.
      CPU 상세 표시 값에도 순위 전용 필드가 없습니다.
      Memory 상세 화면에는 현재 사용량을 담은 목록이 하나, 증가량 순위가 하나이고 두 머리글의 지표 문구가 서로 다릅니다.
      두 상세의 앱 목록 행은 여전히 펼쳐서 하위 프로세스를 보여주고, 펼침 상태에서 목록 구성이 흔들리지 않습니다.
      목록 머리글이 정원을 밝혀 목록이 전체가 아님을 알립니다.
      기존 UI 테스트가 새 머리글 문자열로 Memory 상세와 목록의 존재를 판정합니다.
    - 확인: Swift Testing 단위 테스트로 `DashboardPresentationTests`에서
      「Memory 상세 값이 현재 사용량 순위를 두 자리에 담지 않는다」를 단언합니다 —
      현재 사용량 순위 필드를 되살려 앱 목록과 같은 값을 담게 하는 mutation이 이 단언에서 실패해야 하고,
      기존 「두 순위가 서로 다른 목록으로 나타난다」 단언은 「앱 목록과 증가량 순위가 서로 다른 지표를 담는다」로 옮겨 유지합니다.
      머리글 문구는 순수 문자열 조립을 단위 테스트로 고정하고, 지표 문구를 지우거나 두 목록에 같은 문구를 넣으면 실패해야 합니다.
      펼침 유지는 task-001에서 더한 `displayedGroups` 단언이 계속 담당합니다.
      UI 테스트는 `DashboardCardSelectionUITests`·`DashboardDetailPopoverUITests`·`DashboardProcessListDisplayUITests`를
      실행해 조회가 새 문자열로 성립하는지 확인하며, 이때 상세 팝업 프레임이 400×480 고정으로 남는지 함께 확인합니다.
  - 참조: SPEC §5.1, SPEC §5.8, ANALYSIS §1 「상세 팝업 구성」, ANALYSIS §3 「이력과 표시 값」,
    ANALYSIS §4 「표시에서 사라지는 정보」, ANALYSIS §5 DP1

- [ ] task-003: 카드 순위와 상세 목록 순서 일치 테스트 확장
  - 목적: 카드에 보이는 상위 5개 앱과 그 순서가 같은 시점 상세 목록의 상위 5개와 항상 같고,
    정원 경계 앞뒤 항목의 순서도 두 계산 사이에서 어긋나지 않습니다.
  - 접근: 단위 테스트 계층. `ApplicationRankingTests`의 기존 순서 일치 테스트 둘(순간값과 평활화 값이 갈리는 입력, 동률 입력)을
    정원보다 많은 앱을 넣은 입력으로 확장해 상위 5개와 정원 경계 앞뒤 항목까지 함께 비교합니다.
    두 계산(`compute`, `sortedForDisplay`)의 구조와 공유 평활화 자리는 바꾸지 않습니다.
  - 검증 조건:
    - 결과: 정원보다 많은 앱이 있는 입력에서 `compute` 결과의 앞 5개 표시 이름 배열이 `sortedForDisplay` 결과의 앞 5개와 같고,
      정원 경계 직전·정각·직후 항목의 순서도 두 결과에서 같습니다.
      동률 입력과 순간값·평활화 값이 갈리는 입력 모두에서 성립합니다.
      기존 순서 고정·tie-break·그룹 정렬 단언은 그대로 통과합니다.
    - 확인: 확장된 테스트를 로컬에서 실행해 통과를 확인하고, 다음 mutation이 각각 실패로 잡히는지 확인합니다 —
      한쪽 계산의 평활화를 순간값으로 바꾸면, 한쪽의 tie-break를 앱 키 사전순에서 다른 기준으로 바꾸면,
      한쪽만 정렬 방향을 뒤집으면, 정원 경계에서 한쪽만 다른 개수로 자르면 실패해야 합니다.
      두 계산의 공유 평활화 자리를 분리하는 mutation도 이 테스트가 잡아야 합니다.
  - 참조: SPEC §5.2, ANALYSIS §2 「순위 정원과 통합된 목록」, ANALYSIS §5 DP3

## Section: CPU 그래프

- [ ] task-004: CPU 카드 그래프의 User·System 2계열 표현
  - 목적: CPU 카드 그래프가 부하를 User와 System으로 나눠 쌓아 보여주고, 두 계열의 합이 그 시각의 전체 CPU 사용률과 같으며,
    색을 지운 화면에서도 어느 쪽이 User이고 어느 쪽이 System인지 구분됩니다.
  - 접근: `SystemMetricsHistoryPoint`에 User 비율 필드를 더하고 `historyPoint(from:)`이 그 값을 채웁니다 —
    항목을 만드는 조건(CPU 값과 Memory 값이 모두 있는 tick)과 링 용량·축출·10분 창 선별은 그대로입니다.
    `HistoryPoint`에 선택적 하위 계열 값을 더하고 CPU 조립 경로가 항상 채웁니다.
    연속 구간 분리·버킷 다운샘플링·가로축 정규화의 시그니처와 대표 표본 선택 규칙은 전체 사용률 기준 그대로 두고,
    고른 표본의 하위 계열 값이 그 표본에 딸려 나가게 합니다.
    위 밴드 값을 「전체 사용률 − 하위 계열 값, 0에서 자름」으로 만드는 순수 함수를 뷰 밖에 두고,
    뷰는 0~User를 아래 밴드, User~전체를 위 밴드로 반투명 채우며 두 밴드의 채움 밀도를 다르게 하고
    경계선을 서로 다른 선 모양으로 긋습니다.
    카드 요약 둘째 줄의 User·System 수치 앞에 밴드와 같은 모양의 스와치를 두고, 그 스와치 크기는 그 줄의 텍스트 높이를 넘지 않게 잡습니다.
    `SystemMetricsHistoryPoint`를 참조하는 저장소 밖 네 자리(두 `assemble`, 테스트 생성 도우미 둘)를 함께 고칩니다.
  - 검증 조건:
    - 결과: 이력 항목이 시각·전체 CPU 사용률·Swap과 함께 User 비율을 담고, 값이 없는 tick은 여전히 이력에 들어가지 않습니다.
      다운샘플링 뒤 남은 각 점의 하위 계열 값이 그 점의 전체 사용률과 같은 표본에서 나온 값입니다.
      위 밴드 값이 음수가 되지 않고, 아래 밴드와 위 밴드의 합이 그 시각의 전체 사용률과 같습니다.
      버킷당 남는 점 수와 최소 간격 기준(버킷 폭 4pt, 선 두께 1.0)이 변경 전과 같습니다.
      기존 스파이크·dip 보존, 전역 최소·최대 보존, 구간을 먼저 끊고 버킷을 묶는 순서 단언이 그대로 통과하고 기대값이 바뀌지 않습니다.
      요약 둘째 줄에 두 계열 스와치와 User·System 수치가 함께 있고 카드 높이가 그 때문에 늘지 않습니다.
    - 확인: Swift Testing 단위 테스트로 `DashboardPresentationTests`에 단언을 더합니다.
      다음 mutation이 각각 실패로 잡혀야 합니다 —
      대표 표본과 짝이 아닌 시각의 User 값을 붙이면(예: 버킷의 User 최댓값을 따로 골라 붙이면),
      위 밴드를 0에서 자르지 않아 음수가 나오게 하면, 두 밴드의 합이 전체 사용률과 달라지게 밴드 값 계산을 바꾸면,
      하위 계열 값을 최신 스냅샷의 User 비율로 전체 구간에 씌우면, 이력 항목에서 User 필드를 채우지 않고 0으로 두면 실패해야 합니다.
      기존 다운샘플링 회귀 그물은 대상 값(전체 사용률)의 선택 규칙을 그대로 두었으므로
      기대값을 수정하지 않고 통과해야 하며, 기대값을 손대야 통과한다면 선택 규칙이 바뀐 것으로 보고 되돌립니다.
      스와치 줄의 높이 불변은 `NSHostingController.sizeThatFits(in:)` 렌더 높이 측정으로 확인하고,
      스와치를 지우는 mutation은 접근성 이름 단언(task-012)과 요약 줄 문자열 단언이 잡습니다.
  - 참조: SPEC §5.5, SPEC §5.3, ANALYSIS §1 「CPU 그래프 경계」, ANALYSIS §2 「CPU 그래프 2계열」,
    ANALYSIS §3 「이력과 표시 값」, ANALYSIS §5 DP7, ANALYSIS §5 DP8, ANALYSIS §5 DP9

- [ ] task-005: CPU 카드 그래프의 기준선 격자
  - 목적: CPU 카드 그래프에 25·50·75% 높이의 기준선이 깔려 값의 높이를 어림할 수 있고,
    부하가 높아 밴드가 그 자리를 덮는 구간에서도 기준선이 보이며, 값이 없는 상태에서도 같은 높이에 격자가 남습니다.
  - 접근: 기준선 값 목록을 상수로, 값을 그래프 높이 안의 세로 비율로 바꾸는 변환을 순수 함수로 뷰 밖에 둡니다.
    뷰는 그 결과로 격자를 밴드보다 **먼저**(뒤에) 그리고, 밴드 채움은 반투명으로 유지합니다.
    라벨은 두지 않고 기준선 값은 카드 접근성 이름에 담습니다(task-012).
    값이 없는 자리표시 상태에도 같은 격자를 같은 높이로 그립니다.
  - 검증 조건:
    - 결과: 기준선 값이 25·50·75%이고, 값→세로 좌표 변환이 0%를 그래프 바닥, 100%를 그래프 천장에 대응시키며
      60pt 높이에서 세 선이 15pt 간격으로 놓입니다.
      격자가 밴드 뒤에 깔리고 밴드 채움이 불투명이 아니어서 사용률 100% 구간에서도 세 선이 남습니다.
      값이 없는 상태의 그래프 자리가 격자만 그린 채 값이 있을 때와 같은 높이를 차지합니다.
      격자 때문에 없는 값이 점이나 선으로 그려지지 않습니다.
    - 확인: Swift Testing 단위 테스트로 기준선 값 목록과 좌표 변환을 단언합니다.

    아이콘이 없으면 같은 크기의 중립 기호를 그리고, 값이 없는 줄과 조사 실패 줄에도 같은 크기 자리를 둡니다.
    행 구조·행 식별자·라벨 전체 탭 히트 영역·목록 왼쪽 8pt 여백은 그대로 두고, 아이콘은 접근성 계층에서 감춥니다.
  - 검증 조건:
    - 결과: 아이콘이 있는 행과 없는 행의 앞쪽 자리 크기가 같고, 두 경우의 행 높이와 텍스트 시작 위치가 같습니다.
      아이콘을 얻지 못한 행에 중립 기호가 보이고 빈 자리로 남지 않습니다.
      카드 순위 자리는 아이콘이 더해진 뒤에도 5줄이고 Memory·CPU 카드의 렌더 높이가 아이콘 전 실측값과 같습니다.
      값 없음 줄과 조사 실패 줄에도 같은 크기의 자리가 남아 줄 높이가 같습니다.
      상세 목록 행의 `AppRow-<앱 키>` 식별자와 라벨 전체 탭이 그대로 동작하고 삼각형 히트 영역이 스크롤 클립 경계를 넘지 않습니다.
      아이콘이 접근성 계층에 독립 요소로 나타나지 않아 행마다 중복 낭독이 생기지 않습니다.
    - 확인: `DashboardCardLayoutTests`에 아이콘 있는 경우·없는 경우·조사 실패 경우의 렌더 높이가 서로 같고
      아이콘 전 기준값과도 같은지 단언합니다(`NSHostingController.sizeThatFits(in:)`).
      다음 mutation이 각각 실패로 잡혀야 합니다 —
      아이콘이 있는 행에만 자리를 두어 정렬이 어긋나게 하면, 중립 기호를 지워 자리가 사라지게 하면,
      카드 아이콘 크기를 그 줄 텍스트 높이보다 크게 잡으면, 값 없음·실패 줄에서 자리를 빼면 실패해야 합니다.
      아이콘을 행에서 통째로 지우는 mutation은 아이콘 자리 크기가 두 경우에 같은지 확인하는 단언만으로는 잡히지 않으므로,
      행 조립이 캐시를 조회하고 그 결과를 반영하는지를 가짜 캐시로 확인하는 단언을 함께 둡니다 —
      캐시가 이미지를 돌려주는 입력에서 아이콘 표시와 중립 기호 표시가 구분되어야 합니다.
      행 식별자와 탭 동작은 기존 `DashboardProcessListDisplayUITests`·`DashboardDetailExpansionUITests`가 계속 판정합니다.
      아이콘의 접근성 감춤은 카드·상세 접근성 요소 수가 아이콘 추가 전과 같은지 단언해 확인합니다.
  - 참조: SPEC §5.7, SPEC §5.8, ANALYSIS §1 「아이콘 경계」, ANALYSIS §2 「앱 아이콘」,
    ANALYSIS §5 DP11, ANALYSIS §5 DP12

- [ ] task-011: 새 표시 요소가 모두 있는 상태에서의 크기 불변
  - 목적: 그래프 2계열·격자, 구성 바·범례, 병합 줄, 행 아이콘이 모두 들어간 뒤에도

    각 상태에서 실제로 적용되는지 확인하고, 빠진 자리가 있으면 그 자리에 자리표시를 채웁니다.

- [ ] task-012: 새 표시 요소의 접근성 도달
  - 목적: 카드를 접근성으로 읽으면 그래프의 두 계열 수치와 기준선 값, 구성 네 항목의 수치와 구성 합계가 이름에 담겨 도달되고,

- [ ] task-013: 새 표시 요소 추가 뒤 자기 CPU 사용량 확인
  - 목적: 새 표시 요소가 모두 들어간 뒤에도 팝오버를 열어 둔 채 관찰한 이 앱 자신의 CPU 사용량이
    변경 전과 비교해 지속적으로 상승하지 않습니다.
  - 접근: 먼저 반복 비용이 실제로 없는지를 자동 검증으로 확인합니다 —
    정상 상태에서 같은 앱 키 집합이 반복 조회될 때 아이콘 로더 호출이 0으로 유지되는지,
    상세 목록에 그려지는 행 수가 정원(20)으로 한정되는지를 단위 테스트로 단언합니다.
    그 뒤 자동으로 대체할 수 없는 부분만 실기기 관찰로 확인합니다.
  - 검증 조건:
    - 결과: 초기 조회 뒤 정상 상태에서 아이콘 로더 호출 횟수가 0으로 유지되고,
      상세 앱 목록과 증가량 순위가 각각 최대 20행만 그립니다(통합 전 관측 381행에서 줄어듦).
      팝오버를 10분 열어 둔 관찰에서 이 앱의 CPU 사용량이 단조 상승 없이 일정 범위에서 오르내리고,
      같은 조건의 변경 전 기준값과 비교해 평균이 뚜렷하게 올라가지 않습니다.
    - 확인: 자동 부분 — 가짜 로더를 주입한 단위 테스트로 「캐시가 채워진 뒤 추가 조회에서 로더 호출 0」을 단언하고,
      부정 결과 캐시를 지우거나 캐시를 매 tick 비우는 mutation이 이 단언에서 실패해야 합니다.
      행 수 상한은 task-001의 `displayedGroups` 정원 단언이 담당하며, 정원 자르기를 지우는 mutation이 그 단언에서 실패해야 합니다.
      사람 관찰 부분 — 변경 전 커밋으로 빌드한 앱과 변경 후 앱을 각각 Release 구성으로 실행하고,
      Activity Monitor의 CPU 탭에서 `ResourceRunner` 프로세스를 찾아
      팝오버를 열어 둔 상태로 10분간 1분 간격으로 `%CPU` 값을 10회씩 기록합니다.
      두 표본을 비교해 (a) 후반 5회 평균이 전반 5회 평균보다 지속적으로 크지 않은지,
      (b) 변경 후 10회 평균이 변경 전 10회 평균을 뚜렷하게 넘지 않는지 두 항목을 판정하고 기록한 수치를 함께 남깁니다.
      관찰 중 화면 잠금·디스플레이 슬립·빠른 사용자 전환은 수집을 멈추므로 발생시키지 않습니다.
      상승이 관찰되면 캐시 이미지 크기와 행 그리기 비용을 줄이는 방향으로 좁히고,
      행 수를 더 줄이는 방향은 정원과 행별 아이콘 요구가 정한 범위라 쓰지 않습니다.
  - 참조: SPEC §5.9, ANALYSIS §2 「앱 아이콘」, ANALYSIS §5 DP11, ANALYSIS §5 DP16
