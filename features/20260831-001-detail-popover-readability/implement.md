- [x] task-001: 코어 수를 따라가는 격자 행·열 분할
  - 목적: 논리 코어 수가 몇이든 격자의 행이 고르게 나뉘어, 마지막 행만 짧고 나머지 행의 칸 수가 같습니다.
    특정 코어 수를 가정한 고정 배치가 남지 않습니다.
  - 접근: 코어 수 하나만 받아 행별 코어 인덱스 묶음을 돌려주는 순수 타입을 `MemoryCompositionLayout` 계열이 이미 있는 자리에 둡니다.
    행 수를 `⌈코어 수 ÷ 열 상한⌉`으로 먼저 정하고 열 수를 `⌈코어 수 ÷ 행 수⌉`로 되돌려 나누며,
    열 상한만 콘텐츠 폭에서 유도한 상수로 두고 가용 폭은 인자로 받지 않습니다.
  - 검증 조건:
    - 결과: 코어 8·10·14·16·24·64에서 행×열이 각각 1×8 · 2×5 · 2×7 · 2×8 · 3×8 · 8×8입니다.
      모든 행을 이어 붙이면 0부터 코어 수 − 1까지가 중복 없이 한 번씩 나오고 각 행 안에서 오름차순입니다.
      마지막 행을 뺀 모든 행의 길이가 같고 마지막 행은 그보다 길지 않습니다.
      어떤 코어 수에서도 열 수가 열 상한을 넘지 않습니다.
      코어 수 0이면 빈 배열이고 1이면 1×1입니다.
      함수 시그니처에 가용 폭 인자가 없습니다.
    - 확인: Swift Testing 단위 테스트로 코어 수를 인자로 넣어 단언합니다.
      다음 mutation이 각각 실패해야 합니다 —
      두 단계 유도를 한 단계(`열 수 = min(코어 수, 열 상한)`)로 되돌리면 코어 14가 8+6이 되어 2×7 단언이 실패해야 하고,
      행 수 계산의 올림을 내림으로 바꾸면 코어 10·24에서 인덱스 전수 단언이 빠진 코어를 잡아 실패해야 하며,
      열 상한을 10으로 올리면 코어 10의 2×5 단언이 1×10이 되어 실패해야 합니다.
      인덱스 채우는 순서를 열 우선으로 바꾸면 행 안 오름차순 단언이 실패해야 하고,
      코어 수 0에서 빈 행 하나를 만들면 빈 배열 단언이 실패해야 합니다.
      열 상한이 폭에서 온 유일한 값인지는 시그니처에 폭 인자가 없다는 것과 소스 `grep`으로 확인합니다.
  - 참조: SPEC §5.4, SPEC §5.3, DESIGN §1, DESIGN §3, DESIGN §5 DP1, DESIGN §5 DP4

- [x] task-002: 코어 칸을 막대·수치·번호로 그리는 격자
  - 목적: CPU 상세를 열면 논리 코어별 사용률이 쉼표로 이어 붙인 한 줄 텍스트 대신 격자로 보이고,
    칸마다 아래에서 차오른 막대의 높이로 어느 코어가 높고 낮은지를 값을 하나씩 읽지 않고 알 수 있습니다.
    같은 칸에 정수 퍼센트와 코어 번호가 함께 보여 정확한 값도 화면에서 도달됩니다.
  - 접근: task-001이 나눈 행을 받아 `VStack` + `HStack`으로 칸을 그리는 뷰를 새로 두고,
    `CPUDetailView`의 코어 줄 `Text`를 격자 머리글과 이 뷰로 바꿉니다.
    칸은 고정 높이 트랙 안에서 아래부터 차오르는 세로 막대 · 화면 수치 · 코어 번호 세 줄이고 칸 폭은 행 안에서 균등하게 나눕니다.
    마지막 행이 짧으면 같은 폭의 빈 자리를 채워 열을 맞추고, 값 0인 코어는 채움을 그리지 않으며 최소 채움 높이를 두지 않습니다.
    막대의 트랙·채움 색은 값에 따라 바뀌지 않는 배경 대비 색 상수 둘로 팔레트에 모읍니다.
    격자 뷰와 `CPUDetailView`의 접근 수준은 단위 테스트가 직접 렌더할 수 있는 만큼만 완화하고 사유를 주석으로 남깁니다.
  - 검증 조건:
    - 결과: 격자가 task-001이 정한 행·열대로 칸을 놓고 칸 안 순서가 막대 → 수치 → 번호입니다.
      칸의 채움 높이가 그 코어의 값에 비례하고 트랙 높이는 값과 무관하게 같습니다.
      같은 코어 수에서 값 분포만 다른 두 입력의 격자 그림이 서로 다릅니다.
      값이 0인 코어의 칸에 채움이 없고, 0%와 1%는 같은 칸의 화면 수치로 갈립니다.
      마지막 행의 칸 시작 x가 위 행의 같은 열과 같습니다.
      격자 전체 높이가 값 분포와 무관하게 같습니다.
      CPU 상세에 쉼표로 이어 붙인 코어 사용률 한 줄이 남아 있지 않습니다.
    - 확인: `DashboardCardLayoutTests`가 쓰는 것과 같은 수단(`NSHostingController.sizeThatFits`·`ImageRenderer` 픽셀 probe)으로
      격자 뷰를 직접 렌더해 잽니다 — 상수만 단언하는 테스트는 두지 않습니다.
      다음 mutation이 각각 실패해야 합니다 —
      막대를 지우고 수치·번호만 남기면 값 분포가 다른 두 입력의 그림이 같아져 픽셀 차이 단언이 실패해야 하고,
      채움 높이를 값과 무관한 고정값으로 바꾸거나 값에 반비례시키면 코어별 채움 픽셀 수 단언이 실패해야 합니다.
      화면 수치를 지우면 칸의 이상적 폭이 줄어 폭 단언이 실패해야 하고,
      코어 번호를 지우거나 칸 안 순서를 번호 → 수치로 뒤바꾸면 폭·높이 단언이 실패해야 합니다.
      트랙 높이를 값에 따라 바꾸면 격자 전체 높이 동일 단언이 실패해야 하고,
      값 0인 코어에 최소 채움을 주면 그 칸의 채움 픽셀 수 0 단언이 실패해야 합니다.
      마지막 행의 빈 자리 채우기를 지우면 코어 10·14에서 마지막 행 칸 시작 x 단언이 실패해야 합니다.
      **`CPUDetailView`가 격자 뷰 호출 자체를 지우는 mutation도 잡아야 합니다** —
      격자 뷰만 재는 단언으로는 통과하므로 `CPUDetailView`를 직접 렌더해 그 높이와 그림에 격자가 들어 있는지 함께 잽니다.
      앞 feature에서 `MemoryDetailView`가 `private`이고 `.popover` 콘텐츠가 크기 측정에서 평가되지 않아 회귀 그물이 0으로 남은 자리와
      같은 형태이므로, 접근 수준 완화 없이는 이 mutation이 열린 채로 남습니다.
      폭 등식 단언에는 그 요소만 뺀 기준 폭이 전체보다 작은지 보는 감도 자기점검을 붙여 항진명제가 아님을 확인합니다.
      단위 스위트 전체를 돌려 실패 0과 `** TEST SUCCEEDED **`를 확인합니다.

- [x] task-003: 격자가 팝업 첫 화면 안에 들어가는 세로 예산
  - 목적: 논리 코어 14개인 기기에서 코어 표현 전체가 스크롤 없이 한 화면에 보이고,
    코어 수가 그보다 적거나 많아져도 상세 팝업의 크기가 그대로이며 가로 스크롤이 생기지 않습니다.
  - 접근: 단위 테스트 계층입니다.
    CPU 상세를 production과 같은 콘텐츠 폭으로 렌더해 팝업 위끝(상단 여백 포함)에서 격자 아래끝까지의 높이를 코어 수별로 재고
    상세 팝업 콘텐츠의 실제 프레임과 나란히 봅니다.
    스크롤 막대가 폭을 가져가는 환경은 콘텐츠 폭을 그만큼 좁혀 다시 재는 것으로 대신합니다.
  - 검증 조건:
    - 결과: 코어 14개에서 격자 아래끝이 154pt이고 팝업 높이 480pt 안입니다.
      코어 8·10·16·24·32에서도 격자 아래끝이 480pt 안이고 64개에서 478pt로 마지막까지 들어갑니다.
      65개 이상에서는 격자 아래끝이 480pt를 넘고 팝업 프레임은 400×480 그대로입니다.
      어떤 코어 수에서도 격자의 필요 폭이 콘텐츠 폭 368pt를 넘지 않습니다.
      콘텐츠 폭을 스크롤 막대 몫(15pt)만큼 좁혀도 같은 결론이 유지되고 칸의 화면 수치가 잘리지 않습니다.
    - 확인: `NSHostingController.sizeThatFits(in:)`로 코어 수를 바꿔 가며 재고 다음 mutation이 각각 실패해야 합니다 —
      칸의 트랙 높이나 칸 간격을 키우면 14코어 154pt 단언과 64코어 480pt 이내 단언이 실패해야 하고,
      칸을 네 줄로 늘려도 같은 단언이 실패해야 하며,
      열 상한을 4로 낮춰 행 수가 두 배가 되면 64코어 단언이 실패해야 합니다.
      격자를 `LazyVGrid`로 바꿔 화면 밖 행을 실체화하지 않게 하면 코어 수별 높이 단언이 실패해야 합니다.
      칸 폭 하한을 없애 수치가 잘리게 하는 mutation은 좁힌 폭에서의 칸 이상적 폭 단언이 잡습니다.
      **스크롤 막대 「항상 표시」 설정은 콘텐츠 폭을 15pt 좁혀 재는 것으로 대신합니다** —
      레거시 스크롤러가 실제로 그만큼 가져가는지는 이 확인의 범위 밖이고 추정으로 남습니다.
      `SPEC §5.4`가 이 Task에서 닫히므로 `DashboardDetailPopoverUITests`를 함께 실행해 팝업 프레임이 400×480 그대로인지 봅니다.

## Section: 하위 프로세스 행

- [ ] task-004: 하위 프로세스 행의 두 줄 구조와 네 간격
  - 목적: 앱 행을 펼치면 하위 프로세스 행이 이름 줄과 값 줄 두 줄로 놓이고,
    이름 줄은 부모 앱 이름과 같은 자리에서, 값 줄은 그보다 한 단 더 들어간 자리에서 시작해 왼쪽 끝선만으로 어느 줄이 무엇인지 갈립니다.
    행 안 · 하위끼리 · 부모–첫 하위 · 마지막 하위–다음 앱 네 경계가 서로 다른 간격으로 벌어져
    한 앱의 하위가 어디서 시작해 어디서 끝나는지, 그리고 두 줄이 한 행인지 두 행인지가 보입니다.
    이름도 값도 줄이거나 자르지 않습니다.
  - 접근: `DisclosureGroup`을 그대로 두고 펼친 내용의 `ForEach`를 `VStack`으로 감싸 위아래 여백과 하위 행 간격을 겁니다.
    하위 행 자체는 `HStack { 이름 · Spacer · 값 }`에서 `VStack(alignment: .leading) { 이름 줄; 값 줄 }`로 바꾸고
    두 줄에 각각 다른 왼쪽 여백을 겁니다.
    두 시작선과 네 간격은 `ApplicationProcessRowLayout`에 두고, 시작선은 상수로 박지 않고 유도합니다 —
    이름 줄은 삼각형 폭 + `ApplicationRowIconLayout.detailPointSize` + 라벨 `HStack` 간격, 값 줄은 이름 줄 + `detailPointSize`입니다.
    마지막 경계는 목록 `VStack`의 `spacing: 2`를 뺀 몫만 펼친 내용 아래에 겁니다.
    목록 `VStack`의 `spacing: 2`와 `.padding(.leading, 8)`, 라벨의 `contentShape`·`onTapGesture`·행 식별자는 손대지 않습니다.
    값 `Text`에 `lineLimit`을 걸지 않습니다.
  - 검증 조건:
    - 결과: 펼친 하위 행의 이름 줄 시작 x가 같은 그룹 부모 행의 앱 이름 시작 x와 같고,
      값 줄 시작 x가 이름 줄보다 `ApplicationRowIconLayout.detailPointSize`만큼 오른쪽입니다.
      네 경계의 간격이 2 / 10 / 18 / 26pt이고 서로 같은 값이 하나도 없으며
      「행 안 < 하위끼리 < 부모–첫 하위 < 마지막 하위–다음 앱」 순서입니다.
      하위가 1·2·3개일 때 펼친 행의 높이가 그 규칙대로만 늘어납니다 —
      하위 1개에서 접힘 행 대비 +70.0pt, 하위가 하나 늘 때마다 +38.0pt입니다.
      **production 값 서식으로** 가장 긴 하위 행을 그렸을 때
      이름 줄(`"Google Chrome Helper (Renderer) (PID 12345)"`)과 값 줄(`ApplicationProcessValueFormatting.cpuProcessValueText`가 실제로 내는
      `"12% (코어 합산) · Rosetta"`)이 각각 앱 목록 안쪽 폭 360pt 안에 한 줄로 들어갑니다.
      구분에 색·구분선·배경·테두리를 쓰지 않습니다.
      접힌 앱 행 사이 간격이 변경 전과 같습니다.
      같은 결과가 CPU 상세와 Memory 상세 양쪽에서 나옵니다.
    - 확인: 펼친 앱 행을 직접 렌더해 픽셀 probe로 두 줄과 부모 이름의 시작 x를 재고 높이 측정으로 네 간격을 확인합니다.
      **값 서식을 리터럴로 주입하지 말고 production 함수에서 가져오세요** —
      앞 라운드에서 폭 스위트만 `"12.3% · Rosetta"` 리터럴을 주입하고 간격 스위트는 이름을 짧게 두어,
      production 조합이 어느 테스트에도 걸리지 않은 채 통과한 전례가 있습니다.
      **삼각형 폭 12pt가 이 macOS 버전에서 실제로 그런지는 이 시작 x 등식이 확인합니다** —
      OS가 삼각형 폭을 바꾸면 유도된 시작선과 부모 이름 시작선이 어긋나 단언이 실패하므로,
      상수 12pt를 단언하지 않고 렌더된 두 시작 x가 같은지를 단언합니다.
      다음 mutation이 각각 실패해야 합니다 —
      이름 줄 시작선을 0이나 12pt로 되돌리면 시작 x 등식이 실패해야 하고,
      값 줄 시작선을 이름 줄과 같게 만들면 두 줄의 시작 x 차이 단언이 실패해야 합니다.
      네 간격을 모두 같은 값으로 만들면 서로 다름 단언이, 행 안 간격을 하위끼리보다 넓게 하면 순서 단언이 실패해야 합니다.
      부모–첫 하위 여백을 지우면 하위 1개 행 높이 단언이, 마지막 하위 뒤 여백을 지우면 하위 3개 행 높이 단언이 실패해야 합니다.
      **두 줄 구조를 한 줄(`HStack`)로 되돌리는 mutation이 잡혀야 합니다** —
      시작 x 차이 단언과 행 높이 단언이 함께 잡습니다.
      **간격 상수만 단언하고 뷰가 그 상수를 쓰지 않게 하는 mutation은 렌더 높이 단언이 잡습니다** —
      `.padding` 호출을 통째로 지워도 상수 값은 그대로이므로 상수 단언만으로는 열려 있습니다.
      한 줄 구조가 성립하지 않는 것은 값을 같은 줄에 둔 조립의 이상적 폭이 360pt를 넘는지로 확인합니다(실측 390.0pt).
      색·구분선·배경·테두리 부재는 변경 diff와 소스 `grep`으로 확인합니다.
      단위 스위트 전체를 돌려 실패 0과 `** TEST SUCCEEDED **`를 확인합니다.

      식별자에서 번호를 빼 모든 칸이 같은 식별자를 갖게 하면, 하위 행 이름에서 소속 앱을 빼면 실패해야 합니다.
      화면 번호와 접근성 번호가 갈리는 mutation은 두 문자열이 같은 함수에서 나오는지 확인하는 단언이 잡습니다.

- [ ] task-007: 값 없음 상태에서 새 표시 요소가 자리를 만들지 않는 것
  - 목적: 수집 중·실패·중지 상태에서 상세 팝업이 안내 문구만 보여주고,
    네 상태를 오가도 상세 팝업의 크기와 카드의 위치가 변하지 않습니다.
  - 접근: 단위 테스트 계층입니다.
    이 feature가 더하는 표시 요소를 전수 목록으로 두고 상태 × 요소를 순회해,
    정상에서는 아홉 요소가 전부 그려지고 나머지 세 상태에서는 하나도 그려지지 않는지 잽니다.
    목록은 production 조립값에서 파생시켜 요소가 늘면 항목도 함께 늘게 합니다.
  - 검증 조건:
    - 결과: 상세 팝업 콘텐츠의 프레임이 네 상태 모두 400×480입니다.
      수집 중·실패·중지 세 상태의 렌더 결과가 서로 같고 안내 문구 하나만 담습니다.
      정상 상태에서는 격자 머리글 · 막대 트랙 · 막대 채움 · 화면 수치 · 코어 번호 · 마지막 행 빈 칸 자리 ·
      하위 행 이름 줄 시작선 · 하위 행 값 줄 시작선 · 네 경계 간격 아홉 요소가 전부 그려지고,
      어느 하나만 빠져도 그 요소를 재는 단언이 실패합니다.
      코어 사용률 배열이 빈 입력에서 격자가 행을 만들지 않고 0을 지어내지 않습니다.
      코어 배열을 만들 수 없는 다섯 경우에 수집이 `nil`을 돌려주어 빈 배열이 정상 상태로 들어오지 못합니다.
      두 카드의 렌더 높이가 이 feature 이전 기준값(CPU 243.0 / Memory 181.0)과 같습니다.
    - 확인: 상세 팝업 콘텐츠를 네 상태로 직접 렌더해 프레임과 픽셀을 비교하고,
      아홉 요소는 그 요소만 뺀 기준과 비교하는 감도 자기점검을 붙여 요소별로 잽니다.
      **「값 없음 자리표시를 새로 만들지 않아도 된다」가 실제로 성립하는지가 이 Task의 판정 대상입니다** —
      성립 조건 셋을 각각 실행으로 확인합니다.
      ① 팝업 크기가 상태와 무관한가 — `.frame(width:height:)`를 상태 분기 안쪽으로 옮기면 값 없음 세 상태의 프레임 단언이 실패해야 합니다.
      ② 아홉 요소가 전부 정상 분기 안쪽에만 있는가 — 격자나 하위 행을 상태 분기 밖으로 끌어내면 세 상태 렌더 동일성 단언이 실패해야 합니다.
      ③ 정상 상태에서 코어 배열이 비지 않는가 — 수집이 빈 배열을 돌려주도록 바꾸면 `SystemMetricsCollectorTests`의 기존 `nil` 단언이 실패해야 합니다.
      셋 중 하나라도 mutation이 잡히지 않으면 그 판단이 성립하지 않는 것이므로,
      자리표시를 새로 만들지 말고 그 사실을 기록해 판단을 다시 받습니다.
      아홉 요소를 전수로 두지 않고 지목된 자리만 닫으면 목록 밖 요소가 다음 라운드에 또 나오므로
      (앞 feature가 같은 형태의 전칭 조건에서 다섯 번 연속 reject된 원인),
      목록을 코드에 두고 순회하며 요소가 늘면 항목이 함께 늘어나는지 확인합니다.
      투명하게 칠해 자리만 남기는 부류(`opacity(0)`·`Color.clear`)는 폭·높이로 잡히지 않아 이 그물 밖에 남습니다.
