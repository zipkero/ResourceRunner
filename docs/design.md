# 기술 설계

## 문서 목적

이 문서는 ResourceRunner의 목표 기술 구조, 데이터 수집·계산 정책과 검증 전략을 정의합니다.

- [README.md](../README.md)는 제품 소개, 주요 기능과 프로젝트 문서 진입점을 제공합니다.
- [ROADMAP.md](../ROADMAP.md)는 제품 마일스톤과 출시 관문을 정의합니다.
- [product.md](./product.md)는 사용자에게 보여야 하는 상세 제품 동작을 정의합니다.
- feature별 구체적인 타입, API 선택, Task와 테스트 기준은 해당 feature 문서에서 확정합니다.

## 현재 구현과 목표 설계

### 현재 확인된 구현

M1까지 반영된 상태입니다.

- 앱 진입점은 `Settings { EmptyView() }`와 `@NSApplicationDelegateAdaptor`로 구성하고,
  생성 Info.plist의 `LSUIElement`로 Dock 아이콘 없이 실행합니다.
- `ApplicationCoordinator`가 메뉴바 항목·팝오버, 상태 표시 경로, 생명주기 관찰과 수집 기반을
  각각 한 번씩 만들어 종료까지 보유합니다.
- 메뉴바 항목은 `NSStatusItem.squareLength`와 `.transient` `NSPopover`를 사용하고,
  주입한 다섯 상태를 메뉴바 항목의 접근성 이름으로 구분합니다.
- 수집 일정, 최근 샘플 순환 버퍼와 생명주기 제어(팝오버 열림·닫힘, 저전력, 화면 잠금)가 동작합니다.
  실제 수집값 대신 자리표시 샘플을 사용합니다.
- Collector, 대시보드 카드, 캐릭터 애니메이션과 사용자 설정은 아직 구현되지 않았습니다.
- ResourceRunnerTests와 ResourceRunnerUITests 대상이 존재합니다.
- 세 대상 모두 macOS deployment target은 26.5, Swift language version 설정은 5.0이고,
  앱 실행 파일은 arm64 단일 슬라이스입니다. App Sandbox가 활성화돼 있습니다.

### 목표 설계

아래 구조와 정책은 1.0을 위한 목표 설계입니다. 코드에 반영되기 전에는 구현 사실로 간주하지 않습니다.

## 기술 방향

ResourceRunner는 macOS 네이티브 애플리케이션으로 개발합니다.

~~~text
Xcode
├─ Swift
├─ SwiftUI
│  ├─ 대시보드
│  ├─ 설정
│  └─ 그래프
├─ AppKit
│  ├─ 메뉴바 항목
│  ├─ 애니메이션
│  └─ 팝오버 제어
└─ macOS 시스템 API
   ├─ CPU · Memory
   ├─ Process
   ├─ Network
   └─ Disk
~~~

AppKit은 메뉴바 항목과 팝오버 생명주기의 세밀한 제어에 사용하고, SwiftUI는 대시보드, 카드,
그래프와 설정 화면에 사용합니다. 구체적인 API 선택, 최소 지원 macOS 버전과 Intel Mac 지원 여부는
menu-bar-foundation feature에서 함께 확정합니다.

공개 macOS API를 우선합니다. 비공개 API, 별도 Helper, 관리자 권한이나 시스템 확장이 필요한 기능은 1.0 필수 기능으로 가정하지 않습니다.

### 책임 경계

- Presentation은 시스템 API를 직접 호출하지 않습니다.
- Collector는 원시 시스템 정보를 읽고 조회 실패를 값이나 오류 상태로 반환합니다.
- Application은 샘플 차이, 속도, 평활화, 순위, 앱 집계와 전체 상태를 계산합니다.
- Presentation은 표시용 상태를 받아 카드, 그래프와 메뉴바 표현을 갱신합니다.
- 시스템 전체 수집과 프로세스별 수집을 분리합니다.
- 원시 누적값과 계산된 속도값을 구분합니다.
- Collector 하나의 실패가 다른 Collector와 전체 UI를 중단시키지 않아야 합니다.
- 자주 변하지 않는 프로세스 정보는 별도 캐시로 관리합니다.

## 데이터 흐름

~~~text
누적 카운터·현재 상태 조회
        ↓
시간 정보가 포함된 원시 샘플
        ↓
이전 샘플과 실제 경과 시간 비교
        ↓
사용률·속도·변화량 계산
        ↓
순환 버퍼·프로세스 이력 갱신
        ↓
TOP 5·앱 집계·전체 상태 계산
        ↓
메뉴바와 대시보드 표시 상태
~~~

### 샘플 원칙

- 누적 카운터를 제공하는 자원은 샘플 간 차이로 사용률이나 속도를 계산합니다.
- 속도 계산은 설정한 타이머 간격이 아니라 실제 샘플 시각의 경과 시간을 사용합니다.
- 이전 기준점이 없는 첫 샘플에서는 의미 없는 변화량을 표시하지 않습니다.
- 절전 복귀나 장시간 지연으로 허용 범위를 넘은 샘플은 새 기준점으로 처리합니다.
- 네트워크 인터페이스와 디스크 장치가 바뀌면 이전 장치의 누적값과 새 장치의 누적값을 연결하지 않습니다.
- UI가 소비하는 계산값에는 샘플 시각과 데이터 상태를 함께 전달합니다.

구체적인 시간 타입, 동시성 모델과 상태 전달 방식은 menu-bar-foundation feature에서 확정합니다.

## 수집 일정

### 기본 정책

| 데이터 | 대시보드 열림 | 대시보드 닫힘 |
| --- | ---: | ---: |
| 전체 CPU | 1초 | 2초 |
| 전체 Memory·Swap | 1초 | 2초 |
| Network RX·TX | 1초 | 2초 |
| 전체 Disk I/O | 1초 | 2초 |
| CPU TOP 5 | 2초 | 5초 |
| Memory TOP 5 | 2초 | 5초 |
| 선택한 프로세스 상세 | 1초 | 중지 |
| 디스크 여유 공간 | 30초 | 60초 |
| 인터페이스 주소·상태 | 변경 감지 또는 30초 | 변경 감지 또는 60초 |
| 정적 프로세스 정보 | 캐시 | 캐시 |

팝오버를 열면 캐시된 TOP 5를 먼저 표시하고, 최신 순위는 백그라운드에서 갱신합니다.

### 사용자 갱신 프로필

| 설정 | 전체 지표 | TOP 5 | 닫힌 상태 전체 지표 |
| --- | ---: | ---: | ---: |
| 빠름 | 0.5초 | 1초 | 1초 |
| 기본 | 1초 | 2초 | 2초 |
| 절전 | 2초 | 4초 | 5초 |
| 매우 절전 | 5초 | 5초 | 10초 |

기본값은 기본입니다. 이 수치는 성능 검증 결과에 따라 app-preferences feature에서 조정할 수 있습니다.

### 생명주기 반영

- 팝오버가 닫히면 전체 지표와 TOP 5 수집을 감속합니다.
- 선택한 프로세스 상세 수집은 상세 UI가 닫히면 중지합니다.
- 저전력 모드에서는 절전 프로필을 적용할 수 있습니다.
- 화면 잠금 상태에서는 수집을 중지하거나 최소화합니다.
- 절전 복귀 후 첫 샘플은 변화량 계산에서 제외합니다.
- 설정 변경은 타이머 중복 없이 다음 일정에 즉시 반영되어야 합니다.

사용자가 화면을 볼 수 없는 상태에서는 수집을 중지합니다. 해당하는 상태는 셋입니다.

| 상태 | 신호 |
| --- | --- |
| 화면 잠금 | `com.apple.screenIsLocked`·`screenIsUnlocked` (문서화되지 않음) |
| 디스플레이 슬립 | `NSWorkspaceScreensDidSleep`·`ScreensDidWake` |
| 빠른 사용자 전환 | `NSWorkspaceSessionDidResignActive`·`SessionDidBecomeActive` |

뒤의 둘은 공개 알림이 있어 화면 잠금 어댑터와 달리 문서화되지 않은 신호에 기대지 않습니다.
잠금 없이 화면만 꺼지는 설정과, 화면이 꺼진 뒤 잠금까지 지연을 둔 설정의 사이 구간이 디스플레이 슬립에 해당합니다.

중지한 구간은 최근 그래프에서 공백으로 남습니다. 그 구간을 채우거나 이어 붙이지 않습니다.

시스템 슬립은 성격이 다릅니다. 프로세스가 멈추므로 일정을 조절할 일이 없고,
복귀 첫 샘플의 경과 시간이 실제 수면 시간만큼 커지는 것이 문제입니다.
변화량으로 속도를 계산하는 Network와 Disk가 들어올 때 기준점 재설정이 필요하며,
`NSWorkspaceWillSleep`·`DidWake`로 복귀 시점을 알 수 있습니다.

M1이 구현한 생명주기 입력은 팝오버 열림·닫힘, 저전력 모드, 화면 잠금 셋입니다.
디스플레이 슬립과 빠른 사용자 전환은 core-resource-monitoring에서 함께 연결합니다.

## 최근 데이터 순환 버퍼

최근 그래프 데이터는 설정한 시간 범위와 실제 수집 주기를 기준으로 고정 크기 순환 버퍼에 보관합니다.

~~~text
버퍼 용량 = 그래프 시간 범위 ÷ 실제 수집 주기
~~~

| 그래프 범위 | 수집 주기 | 필요한 샘플 수 |
| ---: | ---: | ---: |
| 10분 | 0.5초 | 1,200개 |
| 10분 | 1초 | 600개 |
| 10분 | 2초 | 300개 |
| 10분 | 5초 | 120개 |

### 버퍼 규칙

- 새 샘플을 뒤에 추가합니다.
- 용량을 넘으면 가장 오래된 샘플을 제거합니다.
- 앱 시작 직후에는 실제로 수집된 구간만 제공합니다.
- 설정 변경 시 새 범위와 주기에 맞춰 용량을 다시 계산합니다.
- 존재하지 않는 과거를 현재값으로 채우지 않습니다.
- 시간 범위를 줄이면 범위를 벗어난 오래된 데이터를 제거합니다.
- 시간 범위를 늘리더라도 존재하지 않는 과거 데이터는 생성하지 않습니다.

버퍼 인덱싱, 용량 재계산과 시간 범위 변경은 자동 테스트로 검증합니다.

용량 계산은 샘플이 수집 주기마다 균등하게 쌓인다고 가정합니다.
수집이 중지되었다 재개되면 이 가정이 깨지고, 버퍼는 개수로만 축출하므로
시간 범위를 한참 벗어난 샘플이 남습니다.
M1의 1시간 잠금 관찰에서 잠금 직전 146개가 해제 뒤에도 그대로 남아 있었고,
그 샘플들은 10분 버퍼 안에 있으면서 실제로는 1시간 전 값이었습니다.

샘플은 시각을 함께 보관하고 시계로 `ContinuousClock`을 사용하므로,
시스템이 잠든 구간을 포함한 실제 경과 시간이 남아 있어 공백을 공백으로 판별할 수 있습니다.

최근 그래프는 샘플의 실제 시각을 기준으로 그리고, 수집하지 않은 구간은 비워 둡니다.
샘플을 순번대로 이어 붙이면 중지 구간이 사라져 오래된 값이 방금 값 옆에 붙으므로 그렇게 하지 않습니다.
표시 대상은 시간 범위 안에 든 샘플로 한정하며, 범위를 벗어난 샘플은 버퍼에 남아 있어도 그리지 않습니다.
용량 계산과 별개로 시간 기준 선별이 필요하다는 뜻이며,
구체적인 방식은 최근 그래프가 만들어지는 core-resource-monitoring에서 확정합니다.

## 데이터 저장과 캐시

| 데이터 | 저장 방식 |
| --- | --- |
| 최근 그래프 | 메모리 순환 버퍼 |
| 현재 TOP 5 | 메모리 계산 결과 |
| 프로세스별 짧은 이력 | 제한된 메모리 상태 |
| 앱 이름·아이콘·경로 | 메모리 캐시 |
| 사용자 설정 | macOS 기본 설정 저장소 |
| 로그인 시 실행 상태 | macOS 로그인 항목 상태 |
| 장기 통계 | 저장하지 않음 |

프로세스 종료 시 관련 이력을 제거하고, 캐시는 프로세스 정체성과 생명주기에 맞춰 무효화합니다. 장기 이력이 추가될 때만 집계 저장과 영구 저장소를 별도로 설계합니다.

## Collector 설계 기준

### CPU 시스템 지표

- 전체 CPU 사용률
- User, System과 Idle
- 논리 코어별 사용률
- Load Average
- 누적 CPU 카운터의 샘플 간 차이
- 첫 샘플과 잘못된 시간 간격 처리
- 최근 그래프용 샘플
- 상태 경계의 반복 전환을 줄이는 평활화 또는 히스테리시스
- 장시간 고부하 판정

CPU 사용률은 논리 코어를 합산하는 Activity Monitor 관례를 따릅니다.
논리 코어가 12개인 기기에서 모든 코어를 쓰는 프로세스는 1200%로 표시됩니다.
M5 정확성 검증이 Activity Monitor와 값을 비교하므로 같은 단위를 사용합니다.
비교 허용 오차는 core-resource-monitoring feature에서 확정합니다.

### 프로세스 CPU

- 실행 중인 PID 목록
- 프로세스별 CPU 시간과 샘플 간 변화
- 여러 코어 사용 시 100% 초과 값
- 최근 2~3개 샘플 평균에 의한 순위 안정화
- 앱 단위 집계와 하위 프로세스 연결
- 종료된 프로세스 제거
- 보호된 프로세스와 접근 실패 처리
- 앱 이름, 아이콘과 실행 정보 캐시

프로세스 조사 주기는 시스템 전체 CPU 수집과 분리합니다.

### Memory 시스템 지표

- 전체 물리 메모리
- App Memory
- Wired Memory
- Compressed Memory
- Cached Files
- Swap Used와 변화량
- Memory Pressure
- 최근 Memory와 Swap 그래프
- Warning과 Critical 상태
- 상태 경계의 반복 전환 방지

단순 캐시 증가를 메모리 부족으로 해석하지 않습니다. 공개 시스템 정보와 자체 계산 지표를 구분합니다.

Memory Pressure는 문서화된 3단계 신호를 그대로 사용하고 자체 수식으로 만들지 않습니다.
`DispatchSource.makeMemoryPressureSource`가 정상·경고·위험 전이를 이벤트로 알려주고,
`kern.memorystatus_vm_pressure_level`로 같은 값을 폴링할 수 있습니다.
2026-08-12에 macOS 26.5.2 Apple silicon에서 두 경로가 모두 동작함을 확인했습니다.

Activity Monitor의 연속적인 압력 곡선은 계산식이 공개돼 있지 않아 재현하지 않습니다.
압력은 3단계 상태로 표현하고, 연속 그래프가 필요한 자리에는
App Memory·Compressed·Swap처럼 값 자체가 정의된 지표를 사용합니다.

### 프로세스 Memory

- Resident Memory. App Sandbox를 유지하기로 확정했으므로 Physical Footprint를 얻을 수 없고
  Resident Memory가 주 지표입니다. Activity Monitor의 메모리 값과 절대값이 달라지므로
  표시 기준을 별도로 정합니다.
- 앱 단위 메모리 합산
- 현재 사용량 TOP 5
- 최근 1분·10분 증가량
- 증가량 TOP 5
- 프로세스 종료와 PID 재사용 처리
- CPU와 공유하는 앱 정체성·메타데이터 캐시

### Network

- 인터페이스별 누적 RX와 TX
- 실제 경과 시간에 따른 초당 다운로드·업로드

인터페이스 집합이나 누적 카운터 기준이 바뀌면 첫 샘플을 새 기준점으로 처리합니다. VPN과 복수 인터페이스 합산 정책은 extended-resource-monitoring feature에서 확정합니다.

### Disk

- 시스템과 외장 볼륨의 전체, 사용 중과 사용 가능한 공간
- 볼륨 연결과 해제
- 전체 읽기·쓰기 누적값과 속도
- 가능한 경우 장치별 통계와 IOPS

장치 전체와 프로세스별 합계가 일치한다고 가정하지 않습니다. 볼륨 정보와 실시간 I/O 데이터의 책임과 갱신 주기를 분리합니다.

## 프로세스 식별과 앱 집계

PID만으로 프로세스 이력을 식별하지 않습니다.

가능한 식별 정보는 다음과 같습니다.

- PID
- 프로세스 시작 시각
- 실행 파일 경로
- 번들 식별자
- 부모 프로세스
- 감사 토큰이나 공개 API가 제공하는 안정적인 실행 식별 정보

구체적인 식별 키는 접근 가능성과 비용을 검증한 뒤 확정합니다.

### 집계 원칙

- 앱 번들에 속한 프로세스는 가능한 경우 같은 앱으로 집계합니다.
- Chrome Renderer, Electron Helper와 IDE 하위 프로세스처럼 복합 앱의 일반적인 관계를 처리합니다.
- CPU와 Memory가 같은 앱 정체성 규칙을 공유합니다.
- 앱으로 묶을 수 없는 명령행·시스템 프로세스는 확인 가능한 실행 정보로 표시합니다.
- 접근할 수 없는 필드는 전체 샘플 실패로 처리하지 않습니다.
- 종료된 프로세스의 이력을 제거하고 같은 PID의 새 프로세스에 연결하지 않습니다.
- 앱 이름과 아이콘 조회 실패는 수집값 자체를 무효화하지 않습니다.

집계 규칙의 비용과 예외는 대표적인 브라우저, Electron 앱, IDE와 명령행 프로세스로 검증합니다.

## 상태 통합과 애니메이션

애니메이션 프레임 갱신과 시스템 데이터 수집을 별도 일정으로 관리합니다.

~~~text
Collector 샘플
    ↓
Application 상태 판정
    ↓
우선순위와 지속 시간 적용
    ↓
메뉴바 표시 상태
    ↓
해당 상태의 독립 애니메이션 타이머
~~~

- CPU 값은 움직임 속도를 결정합니다.
- Memory Pressure는 캐릭터 상태를 우선 변경할 수 있습니다.
- 상태 전환에는 평활화, 지속 시간 또는 히스테리시스를 적용해 임계치 부근의 흔들림을 줄입니다.
- 프레임 캐시는 반복 디코딩과 불필요한 할당을 피합니다.
- 메뉴바 프레임의 캔버스 크기와 기준 위치를 고정합니다.
- 저전력 모드, 화면 잠금과 동작 줄이기에서 애니메이션을 감속하거나 정지합니다.
- 애니메이션을 꺼도 데이터 수집과 정적 상태 표현은 독립적으로 동작해야 합니다.

## 실패와 데이터 상태

각 Collector는 최소한 다음 상태를 표현할 수 있어야 합니다.

- 정상 데이터
- 첫 샘플 또는 데이터 부족
- 일시적 접근 실패
- 지원되지 않는 지표
- Collector 중지 또는 앱 생명주기에 따른 대기
- 오래된 캐시 데이터

UI는 일시적 실패를 0으로 표시하지 않고 데이터 상태를 구분합니다. Collector 하나의 실패는 다른 Collector 일정, 전체 상태와 팝오버 상호작용을 중단시키지 않습니다.

오류의 재시도, 로그 수준과 사용자 메시지는 feature별 접근 실패 특성에 맞춰 확정합니다.

## 주요 기술 위험과 대응

### 프로세스 조사 비용

- 위험: 전체 프로세스를 지나치게 자주 조사하면 앱 자체 CPU 사용량이 증가합니다.
- 대응: 시스템 전체와 TOP 5 주기 분리, 닫힌 상태 감속, 정적 정보 캐시와 선택한 프로세스만 상세 수집합니다.

### PID 재사용

- 위험: 종료된 프로세스와 같은 PID를 받은 새 프로세스가 이전 이력을 이어받을 수 있습니다.
- 대응: PID에 시작 정보와 실행 정보를 결합하고 종료 시 관련 이력을 제거합니다.

### 절전 복귀

- 위험: 긴 수집 간격으로 Network나 Disk 속도가 비정상적으로 계산될 수 있습니다.
- 대응: 실제 경과 시간을 사용하고 허용 범위를 넘은 간격과 복귀 첫 샘플을 새 기준점으로 처리합니다.

### 화면 잠금 신호

- 위험: 화면 잠금 여부를 알려주는 공개 API가 없어 문서화되지 않은 알림과 세션 사전 키에 의존해야 하며,
  OS 갱신으로 이름이나 동작이 바뀔 수 있습니다.
- 대응: 알림 이름과 세션 키 문자열을 어댑터 하나에 두고 나머지 계층은 주입 가능한 계약에만 의존합니다.
  신호를 해석하지 못하면 잠금 상태를 알 수 없음으로 두고, 메뉴바와 팝오버는 계속 동작합니다.

2026-08-06과 2026-08-11에 macOS 26.5.2 Apple silicon에서 확인한 사실입니다.
menu-bar-foundation의 어댑터는 이 관찰을 전제로 합니다.

- `com.apple.screenIsLocked`와 `com.apple.screenIsUnlocked` distributed notification은
  App Sandbox 앱에도 배달되며, object에 현재 GUI 세션 사용자 ID가 문자열로 실려 옵니다.
  세션 사전의 같은 값은 숫자 타입이므로 비교 전에 정수로 정규화해야 합니다.
- 세션 사전의 `CGSSessionScreenIsLocked` 키는 잠금 상태에서만 나타납니다.
  키 부재는 정보 없음이 아니라 잠기지 않은 상태를 뜻합니다.
- 해제 알림이 도착한 시점에도 세션 사전이 아직 잠김을 보고하는 경우가 실제로 발생합니다.
  사전이 알림보다 늦게 갱신되므로 둘이 충돌하면 알림 이름을 신뢰해야 하며,
  알림 처리 경로에서 사전을 다시 읽으면 짧은 잠금·해제 순환에서 해제를 놓칩니다.
- `com.apple.screensaver.didstart`와 `didstop`은 화면 잠금에서 발화하지 않아 대체재가 되지 못합니다.

### Memory Pressure

- 위험: macOS 내부 계산과 완전히 같은 압력 수준을 공개 정보만으로 재현하지 못할 수 있습니다.
- 대응: 공개 시스템 정보를 우선하고 단순 메모리 사용률을 압력으로 해석하지 않으며 자체 지표를 구분합니다.

### 애니메이션 전력 소비

- 위험: 메뉴바 애니메이션이 불필요한 Wake-up과 Energy Impact를 만들 수 있습니다.
- 대응: 최대 12 FPS, 낮은 부하의 낮은 FPS, 저전력·잠금 대응과 비활성화 옵션을 제공합니다.

### 권한과 배포

- 위험: 프로세스 상세 정보와 App Sandbox의 접근 범위가 제품 요구사항과 충돌할 수 있습니다.
- 대응: App Sandbox 상태에서 필요한 시스템·프로세스 정보의 접근 범위를 실측했고, Sandbox를 유지하기로
  확정했습니다. 프로세스별 Physical Footprint를 포기하며, 대신 Resident Memory와 압축·Swap 지표로
  메모리 사용을 설명합니다.

2026-08-06에 macOS 26.5.2 Apple silicon에서 App Sandbox를 적용한 GUI 앱과 적용하지 않은 GUI 앱으로
접근 범위를 확인했습니다. 이 결과를 근거로 App Sandbox를 유지하기로 확정했습니다.
직접 배포 기준과 Mac App Store 제출 여부는 release-readiness에서 정합니다.

| 항목 | App Sandbox 결과 |
| --- | --- |
| CPU 전체·코어별·Load Average | 사용 가능 |
| Memory 통계·물리 메모리·Swap·Memory Pressure | 사용 가능 |
| 인터페이스별 누적 RX·TX | 사용 가능 |
| 볼륨 용량·마운트 목록·블록 장치 I/O 통계 | 사용 가능 |
| `proc_listallpids` 프로세스 열거 | **차단**, `sysctl(KERN_PROC_ALL)`로 대체 가능 |
| 아는 PID의 실행 경로·이름 | 사용 가능 |
| 아는 PID의 CPU 시간·Resident Memory·스레드 수 | 사용 가능 |
| 아는 PID의 uid·시작 시각·부모 PID | 사용 가능 |
| 프로세스별 Physical Footprint | **차단** |
| 앱 번들 식별자·이름·아이콘 | 사용 가능 |

Sandbox와 무관한 제약도 함께 확인했습니다. root 소유 프로세스의 CPU 시간과 메모리는 Sandbox 여부와
관계없이 읽을 수 없으며, 전체 프로세스 중 약 40%가 여기 해당합니다. 관리자 권한과 별도 Helper를
두지 않는 1.0 정책에서는 TOP 5가 사실상 사용자 소유 프로세스로 한정됩니다. 시스템 프로세스 포함
설정의 표시 방식은 core-resource-monitoring에서 확정합니다.

## 미확정 기술 결정

다음 항목은 관련 feature를 시작하기 전에 확정해야 합니다.

- 앱 단위 프로세스 식별 키와 집계 예외
- VPN과 복수 인터페이스 합산 방식
- Disk 장치 통계와 프로세스별 I/O의 공개 API 제공 수준
- 정확성 검증의 비교 도구, 허용 오차와 반복 횟수
- 업데이트, 서명과 공증 방식: release-readiness에서 확정

core-resource-monitoring SPEC 작성 전에 확정한 항목은 다음과 같습니다.

- App Sandbox를 유지합니다. 포기하는 것은 프로세스별 Physical Footprint 하나이며,
  Mac App Store 배포 가능성을 열어 둡니다.
  root 소유 프로세스를 읽지 못하는 제약은 Sandbox와 무관하므로 이 결정으로 달라지지 않습니다.
- CPU 사용률은 논리 코어를 합산하는 Activity Monitor 관례를 따릅니다.
- Memory Pressure는 문서화된 3단계 신호를 그대로 사용하고 연속 곡선을 재현하지 않습니다.
- 최근 그래프는 실제 시각을 기준으로 그리고 수집하지 않은 구간을 비워 둡니다.
- 화면 잠금에 더해 디스플레이 슬립과 빠른 사용자 전환에서도 수집을 중지합니다.

menu-bar-foundation에서 확정한 항목은 다음과 같습니다.

- 최소 지원 macOS 버전은 26.5이고 Apple silicon 전용으로 제공합니다.
- 메뉴바와 팝오버는 `NSStatusItem`, `.transient` `NSPopover`와 `NSHostingController`를 사용합니다.
- 수집과 UI 상태 전달의 동시성 모델은 생명주기 입력을 직렬화하는 store,
  단일 수집 Task를 소유하는 scheduler, 최근 샘플만 다루는 store로 actor를 나누고,
  상태 전달에는 최신 조합 하나만 보존하는 `AsyncStream`을 사용합니다.
