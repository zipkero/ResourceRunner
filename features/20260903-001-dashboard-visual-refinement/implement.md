# 대시보드 시각 정리 구현

- [x] task-001: 색 램프를 두 색조 두 단계로 교체
  - 목적: CPU의 User·System 두 계열과 Memory 구성 네 구간이 두 색조 각 두 단계로 그려지고, 색을 지운 화면에서도 어느 계열·구간인지 구분된다.
  - 접근: 색 상수 여섯 개를 두 색조 × 두 단계 램프와 그 램프의 슬롯 지정으로 재구성하고 라이트·다크 여덟 값을 각각 확정해 넣는다.
    CPU 밴드는 아래(User)에 밝은 단계·위(System)에 진한 단계를 주고 채움 불투명도를 0.55 / 0.20으로 옮긴다.
  - 검증 조건:
    - 결과: Memory 바·도넛·범례가 App → Wired → Compressed → Cached 순서로 진함·밝음을 번갈아 쓰고, CPU 아래 밴드가 밝은 단계·위 밴드가 진한 단계로 그려진다.
      요약 줄 스와치는 밴드와 같은 유도 함수(채움 불투명도·경계선 모양)를 계속 쓰고, 격자 그리기 순서와 격자 색은 그대로다.
      구분 대상이 아닌 배경 대비 요소(격자선, 코어 막대 트랙·채움, 구성 바 트랙)는 시스템 색으로 남는다.
    - 확인:
      - sRGB↔CIELAB 변환·WCAG 명도대비·Machado 2009 severity 1.0 색맹 시뮬레이션(protan·deutan·tritan)·CIEDE2000 검증기를 여덟 값에 대해 실행해,
        배경 근사(라이트 `#ECECEC` / 다크 `#2E2E2E`)에서 여덟 값 모두 대비 3:1 이상이고 Memory 인접쌍 최소 ΔE가 8 이상임을 출력으로 확인한다.
      - 같은 검증기로 CPU 두 밴드의 합성 후 ΔL\*가 라이트·다크 모두 변경 전(라이트 9.3 / 다크 9.0)보다 크다는 것을 확인한다.
      - `DashboardPresentationTests`의 `fillOpacity(.lower) == 0.5` / `fillOpacity(.upper) == 0.28` 단언을 새 값으로 갱신하고,
        `HistoryGraphView.drawOrder`와 `HistoryGraphGridline.placeholderDrawOrder` 배열 단언은 그대로 통과한다.
      - `DashboardCardLayoutTests`의 스와치 색조 범위 단언(User `0.52...0.68`, System `0.0...0.12`)을
        「두 스와치의 색조가 같고 밝기가 갈린다」는 불변형으로 다시 쓰고 통과시킨다. 단언을 지우거나 완화하지 않는다.
      - 범례 조립(스와치 뒤에 이름이 반드시 따라오는 계약)과 CPU 값 없음 요약 줄의 두 스와치 단언이 그대로 통과한다.
  - 참조: SPEC §5.6 / DESIGN §5 DP8, DP9

- [x] task-002: 본체 제목 줄 제거와 UI 앵커 이동
  - 목적: 팝오버 최상단의 「ResourceRunner」 제목이 화면에서 사라지고 두 카드가 그만큼 위로 올라오며, 팝오버 열림 판정과 선택 해제 클릭이 제목 없이도 동작한다.
  - 접근: 본체 세로 스택에서 제목 텍스트를 지우고 본체 컨테이너에 안정적인 접근성 식별자를 새로 붙인다.
    제목을 팝오버 앵커·클릭 대상으로 쓰던 UI 테스트를 카드 식별자와 컨테이너 프레임 기준 좌표로 옮긴다.
  - 검증 조건:
    - 결과: 화면과 접근성 계층에서 `DashboardTitle` 식별자와 `"ResourceRunner"` 제목 텍스트 요소가 사라지고, 본체 컨테이너 식별자가 그 자리를 대신한다.
      카드 두 개는 본체 위쪽 여백 바로 아래에서 시작하고, ⌘1·⌘2 등록 자리는 본체 한 곳 그대로다.
    - 확인:
      - `ResourceRunnerUITests`의 팝오버 열림·닫힘 판정(`app.staticTexts["ResourceRunner"]`, `:28`·`:45`)을 `CPUCard` 식별자 조회로 바꾸고 두 테스트가 통과한다.
        라벨 조회를 쓰지 않는다 — 상세 팝업의 앱 자신 프로세스 행이 같은 문자열을 나른다.
      - `DashboardCardSelectionUITests`의 자기 해제 클릭 대상(`DashboardTitle`, `:137` 부근)을 본체 컨테이너 프레임에서 계산한 카드 밖 좌표로 바꾸고,
        선택 → 재선택 해제 → 자기 해제 → 다른 카드 전환 5단계와 그 사이 프레임 불변 단언이 전부 통과한다.
      - 키보드 탐색 설정이 꺼진 기본 환경에서 ⌘1·⌘2로 두 카드를 선택하고 복귀하는 UI 테스트가 통과한다.
      - `DashboardPresentationTests`의 카드 접근성 이름 단축키 포함 단언(`"⌘1"`·`"⌘2"`, `:1500`·`:1504`와 카드 라벨 스위트)이 그대로 통과한다.
  - 참조: SPEC §5.5, §5.11 / DESIGN §5 DP7

- [x] task-003: 카드 단축키 줄 제거와 초점 타이포·묶음 여백 도입
  - 목적: 두 카드에서 상시 단축키 줄이 사라지고 CPU 전체 사용률과 Memory 사용 중/전체가 같은 카드의 다른 텍스트보다 큰 글꼴로 읽히며, 카드 하나의 높이가 변경 전보다 커지지 않는다.
  - 접근: 타이포 역할 넷(초점 / 값 / 라벨 / 머리글)과 여백 단계 넷(2 / 4 / 8 / 16pt), 카드 표면 상수를 뷰 밖 순수 상수 한 자리로 모으고 두 카드가 그 자리를 참조하게 한다.
    단축키 줄을 지우고 카드 슬롯을 세 묶음으로 묶어 묶음 사이 8pt·묶음 안 2pt를 건다.
  - 검증 조건:
    - 결과: CPU 카드는 `[제목·초점·계열 요약]` / `[그래프]` / `[순위]`, Memory 카드는 `[제목·구성 바]` / `[Pressure·Swap 줄, 구성 범례 줄]` / `[순위]` 세 묶음으로 그려진다.
      초점 줄의 상태 접두는 라벨 역할, 값은 초점 역할로 한 줄 안에서 이어 붙어 상태가 바뀌어도 줄 수가 갈리지 않는다.
      표시 항목의 순서·개수와 순위 자리 5줄 정원은 그대로다.
    - 확인:
      - `DashboardCardLayoutTests`의 카드 높이 기준값(`:657`·`:658`·`:677`·`:692`의 243.0 / 181.0, `:586`의 181.0)을 새 조립의 실측값으로 갱신하되,
        변경 전 상한 CPU 243.0 / Memory 181.0을 함께 남겨 「새 높이 ≤ 변경 전 상한」을 단언한다.
      - 수집 중·정상·실패·중지 여섯 상태에서 카드 높이가 하나로 같고, 순위 항목 수·조사 실패·아이콘 유무·계열 비율 극단값에서도 같다는 기존 단언이 그대로 통과한다.
      - 묶음 사이 간격 > 묶음 안 줄 간격을 여백 단계 상수에서 유도해 단언하고, 같은 위계 자리가 같은 단계를 쓰는지 상수로 단언한다.
      - 초점 역할의 줄 높이가 같은 카드에 쓰이는 다른 역할들의 줄 높이보다 크다는 것을 `NSHostingController.sizeThatFits` 측정으로 단언한다(리터럴 비교가 아니라 역할끼리 비교).
      - Memory 초점 줄이 128GB 기기 최악 입력과 수집 실패·중지 문자열에서도 카드 콘텐츠 폭 안에 들고 구성 누적 바에 폭이 남는지 이상적 폭 측정으로 단언한다.
      - Pressure·Swap 병합 줄과 구성 범례 줄이 좁은 폭에서 줄바꿈 대신 잘리는 기존 단언이 그대로 통과한다.
      - `DashboardCardLayoutTests`의 카드 픽셀 영역 좌표(`:150-153`의 `cpuPlaceholderSummary`·`cpuPlaceholderGraph`·`memoryPlaceholderTrack`·`cpuFirstRankingIcon`)를 새 슬롯 순서로 다시 계산해 갱신하고,
        값 없음 세 상태의 새 표시 요소 감도 자기점검이 그대로 통과한다.
      - `ApplicationRowIconTests`의 카드 아이콘 자리 크기 ≤ 그 줄 글꼴의 실측 줄 높이 단언이 새 값 역할 기준으로 통과한다.
      - 수동 확인: 팝오버를 연 화면에서 각 카드의 초점 수치가 가장 먼저 읽히는지 — 글꼴 크기 비율 단언으로 대체되지 않는 잔여 판단이다.
  - 참조: SPEC §5.1, §5.4, §5.5, §5.10 / DESIGN §5 DP1, DP2, DP6, DP7

- [x] task-004: 카드 표면을 불투명 채움에서 테두리로 교체
  - 목적: 카드가 회색 블록이 아니라 팝오버 표면 위의 구획으로 보이고, 카드의 빈 곳을 눌러도 그 카드가 선택된다.
  - 접근: 카드 배경의 불투명 채움을 지우고 같은 모서리 반경의 채움 없는 테두리로 바꾼다.
    채움이 만들어 주던 클릭 대상을 같은 도형의 `contentShape`로 되살린다.
  - 검증 조건:
    - 결과: 카드 안쪽에는 불투명 채움 픽셀이 없고 테두리 자리에만 잉크가 남으며, 카드 사이 간격은 16pt다.
      테두리는 도형 안쪽에 그려지고 배경 수정자가 크기에 관여하지 않아 카드 높이가 표면 변경 전과 같다.
      선택 상태는 지금처럼 자식 팝오버로만 표현하고 테두리에 선택 표시를 겹치지 않는다.
    - 확인:
      - `DashboardCardLayoutTests`의 카드 배경 알파 임계 단언(`:157`)을 「카드 안쪽에 불투명 채움 픽셀이 없고 테두리 자리에만 잉크가 있다」는 판정으로 다시 쓰고 통과시킨다.
      - 표면 변경 전후 카드 높이가 같음을 단언하고, task-003이 잡은 「새 높이 ≤ 변경 전 상한」 단언이 그대로 통과한다.
      - `DashboardMemoryCardUITests`의 카드 클릭으로 상세가 열리는 시나리오와 `DashboardCardSelectionUITests`의 카드 클릭 선택 단계가 통과한다.
      - 수동 확인: 라이트·다크 두 모드에서 두 카드가 서로 구분되고 카드 경계가 팝오버 표면과 구분되는지 — 테두리 잉크·카드 사이 간격 단언으로 대체되지 않는 잔여 판단이다.
  - 참조: SPEC §5.3 / DESIGN §5 DP3

- [x] task-005: 값 우측 정렬과 바이트 표시 규칙 통합
  - 목적: 카드 순위 행·상세 앱 목록 행·상세 범례 행·상세 증가량 순위 행의 수치가 각 목록 안에서 같은 세로선에 놓이고, 앱 이름 길이나 자릿수가 달라져도 단위와 소수점 자리가 흔들리지 않으며, 코어 격자의 칸 안 수치도 칸마다 같은 자리에서 읽힌다.
  - 접근: 값 종류(percent / bytes / signedBytes)마다 소수 자리 수·단위 선택 규칙·두 열 폭을 함께 갖는 자리를 뷰 밖에 두고, `(숫자, 단위)` 쌍을 두 고정 폭 열에 그리는 뷰 하나를 네 자리가 공유하게 한다.
    코어 칸은 열을 나누지 않고 칸 폭 안 오른쪽 정렬만 걸며, 카드와 Memory 상세가 각자 만들던 바이트 서식을 이 자리 하나로 합친다.
  - 검증 조건:
    - 결과: 바이트는 1024 기반·단위 하한 KB·소수 한 자리 고정·로케일 소수 구분자로 표시되고(`16 GB` → `16.0 GB`, `Zero KB` → `0.0 KB`), 퍼센트는 정수 0자리를 유지한다.
      숫자를 나르는 글꼴 역할에 폭 고정 숫자가 걸리고, 두 열 뷰는 두 텍스트를 한 접근성 노드·한 문자열로 묶는다.
      하위 프로세스 값 줄은 우측 정렬 대상이 아니어서 지금의 두 줄 들여쓰기 구조와 문자열을 그대로 쓴다.
    - 확인:
      - 값 종류마다 그 종류의 가장 넓은 문자열의 이상적 폭 ≤ 그 종류의 열 폭임을 측정 비교로 단언한다(리터럴 비교가 아니다).
      - 한 목록 안 여러 행의 숫자 열 오른쪽 끝과 단위 열 시작 x가 모두 같음을 렌더 측정으로 단언하고, 네 자리(카드 순위, 상세 앱 목록, 상세 범례, 상세 증가량 순위) 각각에서 확인한다.
      - 코어 칸 수치가 칸 폭 안에서 오른쪽 정렬되어 칸마다 같은 x에 `%`가 놓임을 단언하고, 칸 수치의 이상적 폭이 8열 칸 폭과 스크롤러로 좁아진 폭 안에 든다는 유도형 단언이 통과한다.
      - `CPUCoreUsageGridTests`의 칸 이상적 폭 등식·칸 안 잉크 띠 순서·격자 보고 폭 단언이 상수 변경을 따라 그대로 통과한다.
      - `DashboardProcessListDisplayUITests`의 `AppRow-<앱 키>` 아래 `StaticText` 정확히 2개, 앱 행 라벨이 앱 이름과 `"%"`를 함께 포함, 하위 행 값에 `"(PID"` 포함 단언이 그대로 통과한다.
      - `CPUCoreAccessibilityUITests`의 코어 칸 라벨 `"코어 N"`·값 `^[0-9]+%$`·하위 요소 0개 단언이 그대로 통과한다.
      - `DashboardMemoryCardUITests`의 바이트 값 정규식(`:138`)이 `0.0 KB`를 통과하고, 앞 3개 행 라벨에 `KB|MB|GB`가 있고 `"bytes"`가 없다는 단언(`:173-180`)이 그대로 통과한다.
      - `DashboardPresentationTests`의 카드 접근성 이름 바이트 문자열 기준을 새 서식으로 갱신하고, 단위 라벨 `"%"`·`"% (코어 합산)"` 단언은 그대로 유지한다.
      - `ApplicationProcessRowLayoutTests`의 `"12% (코어 합산) · Rosetta"` 값 문자열 단언과 두 줄 폭 ≤ 목록 안쪽 폭 단언이 그대로 통과한다.
      - `MemoryCompositionDetailTests`의 범례 행 단언을 쌍 반환 형태로 갱신하되 값 없음 `"-"` 규칙과 네 행 유지 단언은 그대로 남긴다.
      - 이 변경 전후로 카드 높이가 같고 task-003이 잡은 높이 상한 단언이 그대로 통과한다.
  - 참조: SPEC §5.2, §5.8, §5.11 / DESIGN §5 DP4, DP5, DP13

- [x] task-006: 상세 섹션 위계와 상세 여백 리듬 적용
