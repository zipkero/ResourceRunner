# CPU·Memory 대시보드 시각화와 순위 표시 분석

## 근거

### 확인 사실

- [spec.md](./spec.md) 전문을 읽었습니다. 승인 전 확인 섹션은 없고 완료 조건 10개가 설계 기준입니다.
  범위는 표시 계층으로 한정되고, 프로세스 종료 조작, 그래프 시간 범위 선택과 그 설정, 표시 항목·정원·시스템 프로세스 포함 여부의 사용자 설정,
  Network·Disk 시각화, 수집 주기·이력 링 용량·평활화 창 변경, 「사용 중」 정의 변경이 제외 범위입니다.
- spec.md §1 「관찰된 출발점」이 상세 팝업의 순위 표시 방식을 확정해 두었습니다.
  전체 프로세스 목록이 사용량순으로 정렬되고 앱 행에 합계값이 표시되면서 그 목록 자체가 이미 순위이므로,
  순위 섹션을 따로 두면 상위 항목이 한 화면에 두 번 나타납니다.
  그래서 목록 하나에 정원을 걸어 순위와 하위 프로세스 확인을 같은 자리에서 하고,
  Memory 상세에 이미 있던 「현재 사용량 순위」와 전체 목록의 중복도 이 통합으로 함께 해소합니다.
  증가량 순위는 현재 사용량과 다른 지표라 별도로 남습니다.

  구간 합을 「사용 중」에 맞추는 두 방식(정의 되돌리기, 「사용 중」을 채운 길이로 삼기)이 접혔고 둘을 별개 지표로 분리하는 방향이 채택됐습니다.

### 추정

- 구성 네 항목의 합이 전체 물리 메모리를 넘을 수 있다고 봅니다.
  `MemorySystemMetricsCollector` 주석이 compressor가 물고 있는 페이지가 이미 internal 쪽에 계상된다고 기록하고 있어,
  `app + wired + compressed + cached`가 같은 페이지를 두 번 셀 여지가 있습니다.
  실측으로 초과를 관찰한 것은 아니지만, 초과했을 때 바가 트랙을 넘거나 도넛이 한 바퀴를 넘는 것은 눈에 보이는 오류이므로 구조에서 처리합니다(§5 DP5).
- `NSWorkspace.shared.icon(forFile:)`는 디스크 접근을 수반한다고 봅니다.
  Sandbox 접근 가능성은 `docs/design.md` 실측 표로 확인됐지만 호출 비용은 이 프로젝트에서 측정한 적이 없습니다.
  그래서 비용 가정에 기대지 않고 갱신 주기마다 다시 호출하지 않는 구조로 못박습니다(§5 DP11).
- 카드 한 줄에 들어가는 텍스트가 폭을 넘으면 줄바꿈으로 카드 높이가 늘어난다고 봅니다.
  `DashboardView`가 카드에 주는 폭이 248pt이고 그 안에서 다시 8pt padding이 들어가 실제 콘텐츠 폭이 약 232pt이므로,
  합친 줄과 새 범례 줄에는 줄 수를 하나로 묶는 제한이 필요합니다(§5 DP4).
- 카드 순위(`compute`)와 상세 목록(`sortedForDisplay`)은 같은 평활화 값과 같은 tie-break를 쓰지만 합산 경로가 달라
  부동소수·반올림 오차만큼 값이 다를 수 있다고 봅니다.
  Memory 쪽은 `compute`가 평활화 값을 실수로 합산하고 `sortedForDisplay`는 프로세스별로 반올림한 정수를 합산합니다.
  두 앱의 합계 차이가 그 오차보다 작을 때만 순서가 갈릴 수 있어 실제로 관찰될 여지는 매우 작지만, §5 DP3이 이 여지를 명시적으로 다룹니다.

## 1. 구조

### 이 feature가 건드리는 경계

변경은 표시 경계 안에서 끝나는 것이 원칙이고, 예외가 하나 있습니다.
CPU 그래프의 2계열 표현(SPEC §5.5)은 시각별 User 값을 요구하는데 이력 링에 그 필드가 없으므로,
이력 항목 계약에 필드 하나가 늘어납니다.
수집 주기·링 용량·평활화 창은 그대로이고, Collector와 일정·생명주기 경계는 건드리지 않습니다.
순위 계산 규칙(평활화 창, 앱 키 합산, 값 내림차순, 앱 키 사전순 tie-break)도 그대로이며 정원 상한만 바뀝니다.
Memory 구성 시각화는 최신 스냅샷만 쓰므로 이력 계약을 요구하지 않습니다.

### 상세 순위 경계 — 목록 하나가 순위를 겸함

상세 팝업에는 지표당 순위 목록이 하나만 있습니다(SPEC §5.1).

- CPU 상세: 앱 목록 하나. 사용량 합계 내림차순으로 정렬된 상위 정원까지를 보여주고, 각 행을 펼쳐 하위 프로세스를 확인합니다.
- Memory 상세: 현재 사용량 목록 하나(같은 형태, 펼침 가능)와 최근 증가량 순위 하나.
  두 목록은 서로 다른 지표이므로 함께 있습니다(SPEC §5.1).

같은 순위가 두 번 나타나지 않는 것을 표시 값 모델에서 보장합니다.
지표당 순위를 담는 필드를 하나만 두면 뷰가 두 번 그릴 자리가 없습니다 —
Memory 상세 값에서 현재 사용량 순위 전용 필드를 없애고 앱 목록 필드가 그 역할을 흡수하며,
CPU 상세 값에도 순위 전용 필드를 새로 만들지 않습니다(§5 DP1).
카드 순위 자리는 정원 5의 고정 슬롯으로 그대로 남습니다(SPEC §5.1).

정원 상수는 둘입니다 — 카드 표시 정원 5와 순위 계산·상세 표시 정원 20.
계산은 상세 정원까지 만들고, 카드 목록은 그 앞부분을 잘라 씁니다.
상세 목록에 정원을 거는 자리는 순서 고정 규칙과 같은 순수 함수 안이고(§5 DP2),
뷰에는 정원을 정하는 판단이 남지 않습니다.

### 구성 시각화 경계

구간 계산을 뷰에서 뺍니다.
전체 물리 메모리와 네 항목 바이트에서 「항목 · 바이트 · 트랙 대비 비율 · 누적 시작 위치」 목록을 만드는 순수 계산을 두고,
카드의 수평 누적 바(SPEC §5.3)와 상세의 도넛(SPEC §5.4)이 그 하나를 함께 씁니다.
도넛은 그 비율을 각도로 바꾸는 얇은 변환만 더합니다.
범례 문자열도 같은 경계에 두고, 값이 없을 때 `-`로 남기는 규칙은 `ApplicationProcessValueFormatting`이 이미 쓰는 관례를 따릅니다.
카드와 상세는 같은 구간 결과를 쓰지만 서식이 다릅니다 — 카드는 폭이 좁아 축약 서식을, 상세는 기존 바이트 서식을 씁니다(§5 DP4).
「사용 중」은 이 계산의 입력이 아닙니다 — 구성 합계와 「사용 중」이 서로 다른 지표로 읽히려면(SPEC §5.3)
둘이 같은 계산에 섞이지 않는 것이 출발점입니다.

### CPU 그래프 경계

그래프 점이 전체 사용률과 함께 하위 계열(User) 값을 들고 다니게 합니다.
연속 구간 분리와 버킷 다운샘플링은 지금과 같은 함수가 계속 담당하고,
대표 표본을 고르는 기준도 전체 사용률 하나로 유지합니다 — 고른 표본의 하위 계열 값이 그 표본에 딸려 나갑니다(§5 DP8).
격자 기준선 값 목록과 값→세로 좌표 변환도 뷰 밖 상수·함수로 둡니다(SPEC §5.6).
뷰는 격자를 깔고 두 밴드를 채우고 경계선을 긋는 그리기만 합니다.

### 아이콘 경계

앱 아이콘 획득을 어댑터 하나로 격리합니다.
앱 키를 받아 표시용 이미지를 돌려주는 캐시 타입을 표시 계층에 두고, 시스템 호출은 그 타입에 주입되는 로더 하나에만 둡니다.
뷰는 캐시에만 묻고 시스템을 직접 부르지 않습니다.
`docs/design.md`의 「Presentation은 시스템 API를 직접 호출하지 않습니다」는 지표 조회를 표시 계층으로 끌어오지 말라는 요구이고,
아이콘은 지표가 아니라 경로에 딸린 정적 자산이며 `StatusBarController`가 이미 표시 계층에서 AppKit을 쓰고 있으므로,
어댑터 하나로 모으는 것이 그 경계의 뜻에 맞습니다.
캐시 수명은 앱 수명이고 상한은 고정이며, 아이콘을 얻지 못한 결과도 함께 기억합니다(§5 DP11).
소유자는 `DashboardView`를 만드는 `ApplicationCoordinator` 한 곳이고, 뷰 계층에는 생성자로 전달합니다.

### 접근성 노출 자리

카드는 `Button`에 `.accessibilityElement(children: .ignore)`가 걸려 있어 카드 안의 새 요소가 독립 노드가 되지 않습니다.
그래서 그래프의 계열·기준선과 구성 항목의 수치는 카드 접근성 이름 조립 함수에 더합니다(SPEC §5.10).
상세 팝업은 children을 무시하지 않으므로 도넛에만 자체 요소와 이름을 주고, 범례·목록 행은 텍스트로 그대로 도달됩니다.
아이콘은 같은 행의 앱 이름이 이미 같은 정보를 주므로 접근성 계층에서 감춥니다 — 이름을 하나 더 만들면 행마다 중복 낭독이 생깁니다.

### 카드 슬롯 구성

카드 높이가 이 feature 때문에 달라지지 않아야 하므로(spec.md §3, SPEC §5.3), 슬롯 수와 각 슬롯의 글꼴을 유지합니다.

- CPU 카드: 제목 줄 · 요약 2줄(둘째 줄이 User·System 수치와 계열 스와치를 겸함) · 그래프 60pt · 순위 자리 · 단축키 줄
- Memory 카드: 제목 줄(오른쪽 남는 폭에 구성 바) · Pressure·Swap 병합 줄 · 구성 범례 줄 · 순위 자리 · 단축키 줄

Memory 카드는 줄 하나(Swap 줄)를 병합으로 비우고 그 자리를 구성 범례 줄로 채우므로 슬롯 수가 그대로입니다(§5 DP4).
새로 들어가는 그림 요소(구성 바, 계열 스와치, 순위 행 아이콘)는 모두 자기가 놓인 줄의 텍스트 높이를 넘지 않는 크기로 잡습니다.

### 상세 팝업 구성

팝업 크기는 고정(400×480)이고 내부 `ScrollView`이므로 새 요소가 팝업 크기를 바꾸지 않습니다(SPEC §5.8).

- CPU 상세: 요약 3줄(User·System·Idle, 코어별 사용률, Load Average) · CPU 사용량 앱 목록 하나
- Memory 상세: 구성 도넛과 범례, 구성 합계와 「사용 중」을 각각 라벨을 달아 나눈 수치(SPEC §5.4) · Swap 줄 ·
  현재 사용량 앱 목록 · 최근 증가량 순위

앱 목록의 머리글은 그 목록이 어떤 지표의 순위이고 정원이 얼마인지 알리는 문구로 바뀝니다.
Memory 쪽 머리글에는 「현재 사용량」이 들어가 증가량 순위와 지표가 구분됩니다(SPEC §5.1).
목록의 순서 고정 규칙, 행 구조, 행 식별자, 클릭 히트 영역과 왼쪽 여백 규칙은 그대로 두고 행 앞에 아이콘 자리만 더합니다(SPEC §5.7).
증가량 순위는 지금처럼 펼치지 않는 평면 목록이고 각 행에 아이콘이 붙습니다.

## 2. 데이터 흐름

### 순위 정원과 통합된 목록

1. `ProcessHistoryStore`가 정체성별 이력을 그대로 내보냅니다(변경 없음).
2. `ApplicationRanking.compute`가 앱 키로 합산하고 값 내림차순 · 앱 키 사전순으로 정렬한 뒤 계산 상한(20)까지 자릅니다.
   세 목록(CPU 현재값·Memory 현재값·Memory 증가량)이 같은 상한을 씁니다.
3. `ApplicationRanking.groupByApplication`이 같은 이력을 앱 키로 묶고, `sortedForDisplay`가 같은 규칙으로 정렬해 그룹 합계를 `sortValue`에 담습니다.
4. `ApplicationCoordinator`가 두 결과를 카드 갱신 진입점에 넘깁니다(배선 변경 없음).
5. 카드 표시 값 조립이 카드 순위 목록을 앞 5개로 자르고, 증가량 순위를 정원까지 자르고, 앱 목록은 정렬된 전체를 그대로 담습니다.
6. 카드는 정원 5의 고정 슬롯으로 그립니다.
   상세 앱 목록은 순서 고정과 정원을 함께 적용하는 순수 함수를 거쳐 상위 정원까지만 그립니다(§5 DP2).

카드 순위와 상세 목록의 상위 5개가 같은 항목·같은 순서가 되는 것은
두 계산이 같은 평활화 자리와 같은 tie-break를 쓰기 때문이며, 그 일치는 회귀 테스트로 고정합니다(SPEC §5.2, §5 DP3).
조사 실패 tick에서는 순위 배열이 아니라 실패 표시가 흐르고, 카드는 정원 안에서 실패를 나타내며 상세 목록은 비어 보입니다.
이 경로는 core-resource-monitoring이 정한 것을 그대로 씁니다.

### CPU 그래프 2계열

1. CPU Collector가 한 tick에서 전체·User·System·Idle을 같은 분모로 만듭니다(변경 없음).
2. `MonitoringSampleStore`가 이력 항목에 전체 사용률과 함께 User 값을 담습니다.
   항목을 만드는 조건(CPU 값과 Memory 값이 모두 있는 tick)은 그대로이므로 빈 구간 규칙이 변하지 않습니다.
3. 카드 표시 값 조립이 10분 창으로 거른 뒤 그래프 점에 전체 사용률과 하위 계열 값을 함께 담습니다.
4. 뷰가 `connectedSegments`로 빈 구간을 먼저 끊고, 각 구간에서 렌더 폭 기준 버킷 수로 다운샘플링합니다.
   버킷마다 전체 사용률의 최솟값·최댓값 표본을 시각 순서로 남기고, 그 표본의 User 값이 함께 남습니다.
5. 뷰가 격자 기준선을 깔고, 0부터 User까지를 아래 밴드, User부터 전체 사용률까지를 위 밴드로 채우고,
   두 경계선을 서로 다른 선 모양으로 긋습니다.

위 밴드의 높이는 전체 사용률에서 User를 뺀 값이므로 두 밴드의 합이 전체 사용률과 항상 같습니다(SPEC §5.5).
System을 따로 저장해 더하는 대신 빼서 만드는 이유는 §5 DP7에 있습니다.
값이 없으면 격자만 있는 자리표시가 같은 높이를 지킵니다(SPEC §5.8).

### Memory 구성

1. Memory Collector가 네 구성 항목과 전체 물리 메모리를 한 tick에 함께 만듭니다(변경 없음).
2. 카드 표시 값 조립이 그 값들을 그대로 옮깁니다 — 구성 항목은 이미 상세 값에 있고, 카드 요약도 같은 값을 씁니다.
3. 구간 계산이 전체 물리 메모리를 트랙으로 삼아 항목별 비율과 누적 시작 위치를 만들고,
   누적이 트랙을 넘으면 그 자리에서 잘라 넘침 사실을 함께 돌려줍니다.
4. 카드는 그 결과를 제목 줄의 남는 폭에 수평 누적 바로 그리고, 항목 이름과 수치는 아래 범례 줄에 한 줄로 씁니다(SPEC §5.3).
5. 상세는 같은 결과를 도넛 각도로 바꿔 그리고, 항목별 수치를 범례 행으로 쌓으며,
   구성 합계와 「사용 중」을 각각 라벨을 붙여 따로 보여줍니다(SPEC §5.4).

값이 없는 상태에서는 바가 트랙만, 범례가 `-`만 보여줍니다. 구간을 0으로 그리지 않습니다(SPEC §5.8).

### 앱 아이콘

1. 카드 순위 행, 상세 앱 목록 행, 증가량 순위 행이 그려질 때 그 행의 앱 키로 캐시에 묻습니다.
2. 캐시에 있으면 그대로 씁니다. 없으면 주입된 로더를 한 번 부르고 결과를 기억합니다 —
   아이콘을 얻지 못한 결과도 함께 기억하므로 같은 키가 매 갱신마다 다시 시스템을 부르지 않습니다.
3. 상한을 넘으면 가장 오래전에 쓰인 항목을 버립니다.
4. 행은 아이콘이 있으면 그것을, 없으면 같은 크기의 중립 기호를 그립니다.
   두 경우 모두 자리 크기가 같아 행 높이와 정렬이 흔들리지 않습니다(SPEC §5.7).

정원 통합으로 한 화면에 그려지는 행이 앱 목록 20행과 증가량 순위 20행, 카드 5행으로 한정되므로
아이콘을 얻어야 하는 키의 수도 그만큼으로 줄어듭니다.
정상 상태에서 관찰되는 키 집합은 tick마다 거의 같으므로 첫 조회 뒤에는 시스템 호출이 없습니다(SPEC §5.9).

### 상태 전이에서의 새 요소

도달 가능한 카드 상태는 그대로 수집 중·정상·실패·중지 넷이고, 이 feature는 상태를 늘리지 않습니다.
새 요소가 각 상태에서 차지하는 자리는 다음과 같습니다(SPEC §5.8).

| 요소 | 캐시된 값이 있을 때 | 캐시된 값이 없을 때 |
| --- | --- | --- |
| CPU 그래프 격자·2계열 | 격자 + 두 밴드 + 경계선 | 같은 높이에 격자만 |
| 계열 스와치 줄 | 스와치 + User·System 수치 | 스와치 + `-` |
| Memory 구성 바 | 트랙 + 구간 | 트랙만 |
| 구성 범례 줄 | 항목 이름과 수치 | 항목 이름과 `-` |
| 순위·목록 행 아이콘 | 아이콘 | 같은 크기의 중립 기호 |

상세 팝업은 정상 값이 없으면 지금처럼 안내 문구만 보여주고, 팝업 프레임은 어느 경우에도 고정입니다.

## 3. 인터페이스

### 이력과 표시 값

- `SystemMetricsHistoryPoint`: 시각 · 전체 CPU 사용률 · Swap 사용 바이트에 **User 비율**이 더해집니다.
  항목을 만드는 조건은 그대로이며, 이 필드가 CPU 그래프 2계열의 유일한 새 입력입니다.
- `HistoryPoint`: 시각 · 값에 **하위 계열 값(선택적)** 이 더해집니다.
  `nil`이면 1계열 그래프라는 뜻이고, CPU 조립 경로는 항상 채웁니다.
  연속 구간 분리·버킷 다운샘플링·가로축 정규화 함수의 시그니처와 선택 규칙은 그대로입니다.
- `MemoryCardDetail`: 현재 사용량 순위 전용 필드가 **없어집니다**.
  앱 목록 필드가 그 역할을 겸하고, 증가량 순위 필드는 그대로 남아 정원만 늘어납니다.
  이 필드 제거가 「같은 순위가 두 번 나타나지 않는다」(SPEC §5.1)의 구조적 보장입니다.
- `CPUCardDetail`: 필드 구성이 그대로입니다. 앱 목록 필드가 순위를 겸하므로 새 필드를 만들지 않습니다.
- `ApplicationRankingSampling`: 상수가 둘로 나뉩니다 — 카드 표시 정원(5)과 순위 계산·상세 표시 정원(20).
- `ApplicationProcessGroupOrdering.displayedGroups(...)`: 정원 인자가 더해집니다.
  순서를 정한 뒤 정원까지 자르는 한 함수이며, 기본값은 상세 표시 정원 상수입니다.

### 구성 시각화 계산

- 구성 구간 계산: 네 항목 바이트와 전체 물리 메모리를 받아
  「항목 종류 · 바이트 · 트랙 대비 비율 · 누적 시작 비율」 목록과 넘침 여부를 돌려주는 순수 함수.
  입력에 「사용 중」이 없습니다.
- 도넛 각도 변환: 위 결과의 비율을 시작·끝 각도로 바꾸는 순수 함수. 시작 방향과 회전 방향을 고정합니다.
- 구성 범례 서식: 항목 이름과 값 문자열을 만드는 순수 함수 둘 — 카드용 축약 서식과 상세용 서식.
  바이트 서식 함수는 호출부에서 주입받아 `ApplicationProcessValueFormatting`과 같은 관례를 씁니다.
- Pressure·Swap 병합 줄 서식: 기호 이름과 본문 문자열을 만드는 순수 함수.
  잘림 우선순위가 문자열 순서로 표현되므로 그 순서 자체가 검증 대상입니다(§5 DP4).
- CPU 격자: 기준선 값 목록 상수와, 값을 그래프 높이 안의 비율로 바꾸는 순수 함수.
- CPU 계열 밴드: 전체 사용률과 하위 계열 값에서 위 밴드 값을 만드는 순수 함수(0에서 자릅니다).

### 아이콘

- 앱 아이콘 제공 계약: 앱 키를 받아 표시용 이미지 또는 `nil`을 돌려주는 최소 인터페이스.
  뷰는 이 계약만 보고, 시스템 호출은 구현에 주입되는 로더 하나에 있습니다.
- 구현은 고정 상한 LRU이고, 아이콘을 얻지 못한 결과도 캐시에 남깁니다.
  관찰 가능한 성질은 「같은 키에 로더를 한 번만 부른다」와 「상한을 넘지 않는다」이며, 로더를 대체해 검증합니다.
- 관찰 가능 객체가 아닙니다. 캐시 적중이 뷰 갱신을 유발하면 매 tick 목록 전체가 다시 무효화되므로,
  조회는 값을 돌려주는 동기 호출로 두고 갱신 알림을 만들지 않습니다.

### 접근성 이름

- `cpuAccessibilityLabel`: 기존 문구에 그래프가 두 계열을 겹쳐 그리고 있다는 사실과 기준선 값이 더해집니다.
- `memoryAccessibilityLabel`: 기존 문구에 구성 네 항목의 수치와 구성 합계가 더해지고,
  구성 합계와 「사용 중」이 서로 다른 지표임이 문구에서 갈립니다.
- 상세 도넛: 항목별 수치와 구성 합계, 전체 물리 메모리를 담는 자체 이름 하나.

### 하위 호환

수집한 값은 메모리에만 있고 영구 저장·외부 전송·재시작 복원 경로가 없으므로,

`SystemMetricsHistoryPoint`를 참조하는 저장소 밖 네 자리(두 `assemble`, 테스트 생성 도우미 둘)만 함께 고치면 됩니다.
공개 계약이나 외부 연동은 없습니다.

### 프로젝트 설정과 문서

App Sandbox·deployment target·arm64 전용 산출물·단일 대상 구성을 그대로 유지하고 새 entitlement를 만들지 않습니다.
`docs/design.md`의 실측 표가 앱 번들 이름·아이콘 접근을 Sandbox에서 「사용 가능」으로 기록하고 있어 아이콘 표시에 새 권한이 필요하지 않습니다.
`docs/product.md`는 두 자리가 이 spec과 어긋난 상태입니다 —
`TOP 5 정책`이 상한을 5로 적고 있어 상세 정원 확장을 담지 못하고,
`Memory > 기본 카드`에 그래프 항목이 없어 구성 시각화를 담지 못합니다.
spec.md §1이 예고한 갱신이며 이 문서는 그 갱신을 수행하지 않습니다.

### 이 feature가 다루지 않는 인접 요구

`docs/product.md`의 `Memory > 상세 정보`에 있는 최근 1분 증가량 순위와 프로세스 스레드 수,
`CPU > 상세 정보`의 현재값·최근 평균 비교는 spec.md §5 완료 조건에 없어 범위 밖입니다.
그래프 시간 범위 선택과 표시 항목·정원의 사용자 설정은 spec.md §4가 제외했습니다.

## 5. Decision Points

### DP1. 상세 순위와 앱 목록을 하나로 통합하는 방식

상세 팝업에는 이미 사용량 내림차순으로 정렬되고 앱 행에 합계값이 표시되는 앱 목록이 있어 그 자체가 순위입니다(§근거 확인 사실).
Memory 상세에는 그 위에 같은 지표의 「현재 사용량 순위」 섹션이 따로 있어 상위 항목이 두 번 나타납니다.

- 옵션 A: 순위 섹션과 앱 목록을 둘 다 두고 순위 섹션에만 정원을 겁니다.
  두 목록이 서로 다른 질문에 답한다고 볼 수 있지만, SPEC §5.1이 「같은 순위가 한 화면에 두 번 나타나지 않습니다」를 명시해 기각됩니다.
- 옵션 B: 순위 섹션을 남기고 앱 목록을 없앤 뒤, 순위 섹션에 펼침을 붙입니다.
  화면 결과는 채택안과 같지만 `TopApplicationsView` 기반 평면 섹션에 펼침·순서 고정·행 식별자·클릭 히트 영역을 새로 세워야 합니다.
  그 규칙들은 core-resource-monitoring이 실기기 결함을 고쳐 가며 확정한 것이라 다시 만들면 그 회귀를 다시 살 위험이 있습니다.
- 옵션 C: 기존 앱 목록 하나에 정원을 걸어 순위 역할을 겸하게 하고, Memory 상세의 현재 사용량 순위 섹션을 없앱니다.
  증가량 순위는 다른 지표이므로 평면 섹션으로 남깁니다.
  기존 목록의 규칙을 그대로 쓰고 새 뷰가 늘지 않지만, 목록이 전체가 아니게 되어 정원 밖 앱이 상세에서 사라집니다.
- 채택안: 옵션 C.
  spec.md §1이 이 통합을 이미 확정했고, 그 목록이 왜 이미 순위인지도 같은 자리에 적혀 있습니다.
  옵션 B와 C의 화면 결과가 같으므로 선택 기준은 어느 쪽이 검증된 규칙을 유지하느냐이고, 그 답이 C입니다 —
  순서 고정(`ApplicationProcessGroupOrdering`), 행 식별자(`AppRow-<앱 키>`), 라벨 전체 탭, 클립 경계 여백이 모두 그 목록에 붙어 있습니다.
  중복이 다시 생길 경로는 표시 값 모델에서 막습니다.
  `MemoryCardDetail`의 현재 사용량 순위 필드를 지우면 뷰가 그 순위를 두 번 그릴 자리가 아예 없어지고,
  CPU 상세 값에도 순위 전용 필드를 만들지 않아 같은 상태를 유지합니다 —
  뷰의 관례가 아니라 값 모델의 형태가 SPEC §5.1의 「두 번 나타나지 않습니다」를 보장합니다.
  이 제거는 core-resource-monitoring analyze.md DP15가 세운 「검증할 수 없는 중복을 두지 않는다」와 같은 방향입니다.
  정원 밖 앱이 사라지는 대가는 §4 「표시에서 사라지는 정보」에 적었습니다 —
  spec.md가 남은 문제로 지목한 것이 개수 상한이므로 이것이 요구된 결과이고, 목록 머리글이 정원을 밝혀 전체가 아님을 알립니다.

### DP2. 정원을 거는 자리와 펼침 중 목록 구성의 안정성

정원을 어디서 자르느냐에 따라 「펼친 행이 있는 동안 순서를 고정한다」는 기존 규칙과의 관계가 달라집니다.

- 옵션 A: 뷰 본문에서 자릅니다.
  변경이 가장 작지만 정원 정책이 뷰 안에 숨어 단위 테스트로 직접 확인할 수 없고,
  순서 고정 함수와 자르기의 순서 관계가 뷰 본문에만 존재합니다.
- 옵션 B: 표시 값 조립에서 자릅니다.
  값이 작아지고 조립 테스트로 확인되지만, 순서 고정보다 먼저 자르게 되어
  정원 경계를 넘나드는 앱이 펼친 행이 있는 동안에도 목록에 들어오고 나갑니다.
  그 앱이 펼친 행보다 위에 있으면 행이 위아래로 밀려, 매초 재정렬이 클릭을 어긋나게 하던 결함이 다른 형태로 돌아옵니다.
- 옵션 C: 순서 고정 함수에 정원 인자를 더해 「순서를 정한 뒤 자른다」를 한 순수 함수 안에서 처리합니다.
  펼친 행이 있는 동안에는 고정된 순서를 자르므로 목록 구성까지 그대로 멈추고,
  새로 나타난 앱은 고정 순서 뒤에 붙어 정원 밖에 머물러 화면을 밀지 않습니다.
  대가는 표시 값이 여전히 정렬된 전체 목록을 담는 것입니다.
- 채택안: 옵션 C.
  정원과 순서 고정은 둘 다 「사용자가 보는 목록의 구성」을 정하는 규칙이라 같은 자리에서 결정되어야 하고,
  그 자리를 순수 함수로 두면 정원이 뷰 판단이 아니게 되면서 단위 테스트가 직접 확인할 수 있습니다(SPEC §5.1, SPEC §5.8).
  표시 값이 전체 목록을 담는 것은 지금과 같아 새 비용이 아니며,
  실제로 줄어드는 비용(수백 행에서 정원만큼으로 줄어드는 렌더와 접근성 노드)은 그대로 얻습니다.
  기본값을 상세 표시 정원 상수로 두어 호출부가 정원을 고르지 않게 합니다.
  카드 쪽 정원은 이 함수와 무관하게 고정 슬롯 정원(5)이 담당합니다.

### DP3. 카드 순위와 상세 목록의 상위 5개 일치를 보장하는 방식

카드 순위는 `compute`가, 상세 목록 순서는 `sortedForDisplay`가 만듭니다.
두 계산은 같은 평활화 자리와 같은 tie-break를 쓰지만 합산 경로가 달라 값이 오차만큼 다를 수 있습니다(§근거 추정).

- 옵션 A: 상세 목록에서 카드 순위를 유도해 단일 출처로 만듭니다.
  일치가 구조로 성립하고 카드 값·행 값·하위 프로세스 합이 정확히 같아지지만,
  `compute`의 CPU·Memory 현재값 순위와 표시 진입점의 순위 인자가 쓰이지 않게 되어 함께 지워야 합니다.
  검증된 Application 계층 출력과 그 테스트를 없애는 일이고,
  spec.md §3이 「카드 TOP 5와 상세 목록이 같은 값·같은 순서를 쓰는 관계가 유지되어야 한다」고 적은 것을 재구성으로 바꿉니다.
- 옵션 B: 두 계산을 그대로 두고, 일치를 회귀 테스트로 고정합니다.
  변경이 없고 기존 그물을 잇지만, 일치가 「같은 입력에서 같은 규칙을 쓴다」는 성질에 의존합니다.
- 옵션 C: 카드 값을 상세 행 값으로 덮어써 표시만 맞춥니다.
  화면은 맞춰지지만 카드 순위 배열의 순서와 값이 서로 다른 출처가 되어 무엇이 참인지 흐려집니다.
- 채택안: 옵션 B.
  이 일치는 이미 이 저장소의 회귀 그물이 두 테스트로 고정하고 있습니다 —
  순간값과 평활화 값이 갈리는 입력과 동률 입력에서 두 계산의 결과 배열을 통째로 비교합니다(§근거 확인 사실).
  spec.md §3이 「유지되어야 합니다」로 기존 관계를 전제하므로 구조를 바꾸는 옵션 A는 요구를 넘습니다.
  옵션 B의 약점(오차만큼 값이 다를 수 있음)은 정원 통합으로 오히려 관찰 범위가 넓어졌으므로,
  기존 두 테스트를 정원 경계까지 확장해 상위 5개뿐 아니라 정원 경계 앞뒤 항목의 순서도 함께 고정합니다(SPEC §5.2).
  두 계산이 같은 평활화 자리(`smoothedRecentValues`)를 공유하는 구조는 이 일치의 원인이므로 그대로 유지하고,
  어느 한쪽에 다른 평활화·다른 tie-break를 넣으면 그 테스트가 실패해야 합니다.

### DP4. Memory 카드에서 구성 시각화가 차지할 자리와 잘림 완화

카드 높이는 이 feature 때문에 커질 수 없고(spec.md §3, SPEC §5.3), 본체 팝오버 높이 488pt에 여유가 없습니다.
카드의 다섯 슬롯은 모두 core-resource-monitoring의 완료 조건이 요구하는 표시를 담고 있어 그대로 없앨 수 있는 줄이 없습니다.

- 옵션 A: 카드에 줄을 하나 더합니다. 가장 단순하지만 spec.md §3을 정면으로 어깁니다.
- 옵션 B: 순위 자리를 5줄에서 4줄로 줄여 한 줄을 만듭니다.
  높이는 지켜지지만 SPEC §5.1이 카드 순위 자리를 5로 유지하라고 명시합니다.
- 옵션 C: 바를 그리고 항목 수치는 카드에 두지 않습니다.
  자리 문제가 사라지지만 SPEC §5.3이 카드에서 수치를 확인할 수 있어야 한다고 요구합니다.
- 옵션 D: Pressure 줄과 Swap 줄을 한 줄로 합쳐 한 줄을 비우고,
  바는 제목 줄의 남는 폭에 넣고 비워진 줄을 구성 범례 줄로 씁니다.
  슬롯 수와 글꼴이 그대로라 높이가 유지되고 네 항목의 이름과 수치가 카드에 남습니다.
  대가는 두 줄이 폭이 부족한 환경에서 끝이 잘리는 것입니다.
- 채택안: 옵션 D. 사용자 확인을 받아 확정했습니다.
  요구를 어기지 않고 성립하는 유일한 배치입니다 — A는 크기 제약, B는 SPEC §5.1, C는 SPEC §5.3에 각각 걸립니다.
  바를 제목 줄에 넣을 수 있는 이유는 제목 텍스트가 카드 폭을 다 쓰지 않기 때문이고,
  바 높이를 제목 텍스트 높이 이하로 잡으면 그 줄의 높이가 바뀌지 않습니다.
  두 합친 값은 카드에 그대로 남으므로 core-resource-monitoring SPEC §5.1의 표시 항목과 SPEC §5.5의 단계 표시가 유지됩니다.

**잘림을 줄이는 규칙**

카드 콘텐츠 폭은 약 232pt입니다(§근거 추정). 두 줄에 다음을 적용합니다.

- 병합 줄의 요소 순서를 「Pressure 기호 → Pressure 라벨 → 구분자 → Swap 사용량 → Swap 변화량」으로 고정합니다.
  줄 수를 하나로 묶고 잘림을 끝에서 일으키면 잘리는 순서가 이 순서의 역순이 되어,
  변화량이 먼저 사라지고 사용량이 그다음이며 기호와 단계 라벨은 마지막까지 남습니다.
  기호가 맨 앞에 있어야 Pressure를 색 없이 구분하는 수단(spec.md §3, core SPEC §5.5)이 어떤 폭에서도 지켜집니다.
- 범례 줄의 항목 순서는 바의 구간 순서(App → Wired → Compressed → Cached)와 같게 고정합니다.
  순서가 같아야 색 없이도 범례와 구간이 대응되고, 잘릴 때 사라지는 항목이 바에서 가장 오른쪽 구간이라는 것이 예측됩니다.
- 카드 범례의 값은 축약 서식을 씁니다 — 소수 한 자리와 단위 붙여쓰기.
  상세 범례는 기존 바이트 서식을 그대로 쓰므로 정확한 값은 상세에서 확인됩니다.
- 그래도 넘치면 글자 크기를 소폭 줄이는 것을 잘림보다 먼저 적용합니다.
  다만 그 처리가 줄 높이를 바꾸면 카드 높이 불변이 깨지므로, 렌더 높이 측정 테스트로 확인하고
  높이가 달라지면 축소를 쓰지 않고 잘림에만 의존합니다.
- 위 규칙으로도 값이 사라질 수 있으므로, 병합 줄과 범례 줄의 모든 수치를 카드 접근성 이름에 함께 둡니다(§5 DP13) —
  화면에서 잘린 값이 접근성 계층에서는 남습니다.
- 순서 규칙이 서식 함수의 관찰 가능한 성질이므로, 문자열 조립 순서를 단위 테스트로 고정합니다(§5 DP15).

높이가 실제로 유지됐는지는 변경 전 두 카드의 렌더 높이를 `NSHostingController.sizeThatFits(in:)`로 재어 기준값으로 기록하고
변경 뒤 같은 값이 나오는지, 가장 긴 값에서도 같은지를 단언해 확인합니다(SPEC §5.3, §5 DP15).
같은 이유로 순위 행 아이콘과 계열 스와치의 크기도 그 줄의 텍스트 높이를 넘지 않게 잡습니다.

### DP5. 구성 구간의 기준과 「사용 중」의 분리

- 옵션 A: 네 항목의 합을 100%로 보고 각 구간이 합계에서 차지하는 비율로 그립니다.
  바와 도넛이 빈 곳 없이 채워지지만 구간 길이가 전체 물리 메모리 대비 실제 바이트에 비례하지 않아 SPEC §5.3을 어깁니다.
- 옵션 B: 「사용 중」을 채운 길이로 삼고 그 안을 네 항목의 비율로 나눕니다.
  두 지표가 한 그림에 담기지만 spec.md §1이 값 왜곡을 이유로 이미 접은 방식입니다.
- 옵션 C: 전체 물리 메모리를 트랙으로 삼고 각 구간을 실제 바이트에 비례하게 그리며,
  남는 부분은 이름 없는 트랙으로 둡니다. 구성 합계와 「사용 중」은 각각 라벨을 달아 따로 보여줍니다.
  트랙의 남는 부분이 무엇인지 묻게 되는 대가가 있지만 어떤 값도 왜곡되지 않습니다.
- 채택안: 옵션 C.
  SPEC §5.3이 「전체 물리 메모리를 기준으로 실제 바이트에 비례」와 「구성 합계와 사용 중을 서로 다른 지표로 구분」을 함께 요구하므로,
  기준을 전체 물리 메모리로 두고 두 수치를 각자 라벨과 함께 보여주는 것만 남습니다.
  남는 부분에 이름을 붙이지 않는 이유는 그것이 여유 메모리와 같은 값이 아니기 때문입니다 —
  이름을 붙이면 확인되지 않은 범주를 만들어 spec.md §3의 값 왜곡 금지에 걸립니다.
  구성 합계가 트랙을 넘을 가능성(§근거 추정)은 구간 계산이 누적 위치를 트랙 끝에서 잘라 처리하고,
  잘렸다는 사실을 결과에 함께 담아 표시가 트랙을 넘거나 도넛이 한 바퀴를 넘지 않게 합니다.
  범례에 적히는 수치 자체는 자르지 않으므로 값은 언제나 실제 바이트입니다.
  「사용 중」은 구간 계산의 입력이 아니고, 카드에서는 제목 줄에, 상세에서는 자기 라벨을 단 줄에 남습니다.

### DP6. Memory 상세 구성 시각화의 형태

- 옵션 A: 카드와 같은 수평 바를 크게 그립니다.
  계산을 그대로 재사용하지만 카드와 형태가 같아 상세를 여는 값이 수치 범례 하나뿐입니다.
- 옵션 B: 도넛과 범례로 그립니다.
  spec.md §1이 참고 앱에서 받아들인 형태이고, 각 항목의 수치를 행으로 쌓을 수 있어 SPEC §5.4의 「범례로 함께 보이는 수치」가 자연히 성립합니다.
  각도 변환이 한 겹 늘어납니다.
- 옵션 C: 항목별 막대를 나란히 세운 형태로 그립니다.
  값 비교가 쉽지만 구성이 하나의 전체를 나눈 것이라는 관계가 약해지고, 전체 물리 메모리 기준도 표현하기 어렵습니다.
- 채택안: 옵션 B.
  spec.md §1이 카드는 수평 누적 바, 상세는 도넛과 범례로 이미 확정했고,
  도넛의 링 전체가 전체 물리 메모리라는 기준을 카드 바와 공유하므로 두 화면의 눈금이 같아집니다.
  구간 비율은 카드와 같은 계산에서 나오고 도넛은 그 비율을 각도로 바꾸는 변환만 더하므로,
  같은 시점의 카드와 상세가 서로 다른 그림을 보여줄 경로가 없습니다.
  도넛 가운데에는 구성 합계를 라벨과 함께 둡니다 — 「사용 중」을 가운데 두면
  링의 합과 같은 값으로 읽혀 SPEC §5.3이 요구한 구분이 무너집니다.

### DP7. CPU 그래프 2계열의 데이터 표현

이력 링에는 시각·전체 CPU 사용률·Swap만 있고 User·System 값이 없습니다(§근거 확인 사실).

- 옵션 A: 이력에 손대지 않고 최신 스냅샷의 User·System 비율을 전체 구간에 적용합니다.
  스키마가 그대로지만 과거 시각에 현재 비율을 씌우는 것이라 값을 지어내는 것이고 spec.md §3을 어깁니다.
- 옵션 B: 이력 항목에 User와 System을 모두 담고 두 계열을 각각 그립니다.
  두 값이 다 남지만 두 계열의 합과 별도로 저장된 전체 사용률이 서로 다른 값이 될 여지가 있어
  SPEC §5.5의 「합이 전체 사용률과 일치」를 저장 시점의 성질에 의존하게 만듭니다.
- 옵션 C: 이력 항목에 User만 더하고 System 밴드는 전체 사용률에서 User를 뺀 값으로 만듭니다.
  필드가 하나만 늘고, 두 밴드의 합이 전체 사용률과 같다는 것이 계산 구조에서 나옵니다.
  System 값을 이력에서 직접 읽을 수 없다는 대가가 있습니다.
- 채택안: 옵션 C.
  Collector가 전체·User·System을 같은 분모로 만들어 전체가 두 계열의 합과 같으므로(§근거 확인 사실),
  셋 중 둘만 저장해도 정보가 줄지 않습니다.
  그 둘로 전체와 User를 고르면 그래프 위쪽 경계가 지금 그리는 것과 같은 전체 사용률 계열로 남아,
  스파이크 보존을 고정한 기존 회귀 그물이 대상 값을 그대로 유지합니다(§4 테스트 대상).
  또 SPEC §5.5의 합 일치가 뺄셈으로 성립하므로 저장·조립 어느 단계에서도 어긋날 자리가 없습니다.
  뺀 값이 음수가 되지 않도록 0에서 자르고, 그 성질을 단위 테스트로 고정합니다.
  System 계열의 시계열을 직접 저장하지 않는 대가는 이 feature 범위에서 드러나지 않습니다 —
  System만 따로 그리는 요구는 spec.md §5에 없습니다.

### DP8. 2계열에 다운샘플링을 적용하는 방식

버킷 하나에서 전체 사용률의 최댓값이 있는 시각과 User의 최댓값이 있는 시각이 다를 수 있습니다.

- 옵션 A: 계열마다 따로 다운샘플링합니다.
  각 계열의 극값이 모두 남지만 두 계열의 점이 서로 다른 가로 위치에 놓여
  같은 가로 좌표에서 두 밴드를 쌓을 수 없고, 밴드 경계가 그 시각의 실제 값이 아닌 그림이 됩니다. SPEC §5.5를 어깁니다.
- 옵션 B: 두 계열의 최솟값·최댓값 표본을 모두 남깁니다.
  극값을 다 지키고 점마다 짝이 맞지만 버킷당 남는 점이 최대 4개로 늘어
  방금 확정한 최소 간격 기준(버킷 폭 4pt, 선 두께 1.0)이 무너져 그래프가 다시 뭉개집니다.
- 옵션 C: 대표 표본을 전체 사용률 기준으로 고르고, 고른 표본의 User 값을 함께 남깁니다.
  버킷당 점 수와 선택 규칙이 지금과 같고 남은 점마다 두 계열이 같은 시각의 실제 값입니다.
  전체 사용률은 그대로인데 User와 System의 비중만 바뀐 순간은 버킷 안에서 사라집니다.
- 채택안: 옵션 C.
  이 그래프가 먼저 답해야 하는 질문은 「언제 얼마나 썼는가」이고 그것을 지키는 계열이 전체 사용률입니다.
  그 계열의 선택 규칙을 건드리지 않으므로 스파이크·dip·전역 극값 보존을 고정한 기존 단언들이 그대로 유효하고,
  버킷 폭 4pt·선 두께 1.0의 관계도 유지됩니다.
  남은 점이 모두 같은 표본의 두 값이라 두 밴드가 같은 가로 좌표를 공유하고,
  그 덕분에 밴드 사이 경계가 그 시각의 실제 User 값이 됩니다.
  대가인 「합은 같고 구성만 바뀐 순간」의 손실은 버킷 폭(10분 창에서 약 10초)만큼의 해상도 문제이며,
  User와 System의 현재 비율은 같은 카드의 요약 줄이 매 tick 정확히 보여줍니다.

### DP9. 두 계열을 색 없이 구분하는 수단

- 옵션 A: 두 계열을 색만 다르게 채웁니다.
  가장 단순하지만 색상만으로 정보를 전달하지 말라는 spec.md §3과 `docs/product.md` 접근성 요구를 어깁니다.
- 옵션 B: 채우지 않고 두 선만 그립니다.
  격자가 가려지지 않지만 어느 선이 무엇인지가 선 모양에만 남아, 겹쳐 그린 두 계열의 관계(쌓임)가 보이지 않습니다.
- 옵션 C: 아래를 User, 위를 System으로 쌓아 채우고, 두 밴드의 채움 밀도를 다르게 하고,
  밴드 경계선을 서로 다른 선 모양으로 긋고, 요약 줄의 User·System 수치 앞에 밴드와 같은 모양의 스와치를 둡니다.
  색을 지워도 쌓임 순서·채움 밀도·선 모양·스와치 네 가지로 구분되지만 그리는 요소가 늘어납니다.
- 채택안: 옵션 C.
  쌓임 순서 자체가 색과 무관한 정보이고, 스와치가 그 순서를 요약 줄의 수치와 묶어 줍니다 —
  같은 줄에 이미 User·System 수치가 있어 새 줄이 필요하지 않습니다(§5 DP4의 높이 제약).
  Hover에 의존하지 않는다는 `docs/product.md` 요구도 그대로 지킵니다.
  채움은 반투명으로 두어 뒤에 깔린 격자가 부하가 높은 구간에서도 읽히게 합니다(§5 DP10).

### DP10. 격자 기준선의 값과 그리는 순서

- 옵션 A: 값 라벨을 붙인 축을 왼쪽에 둡니다.
  읽기가 가장 정확하지만 카드 폭 248pt에서 라벨이 그래프 폭을 잠식하고, 카드가 커지지 않는다는 제약과 부딪힙니다.
- 옵션 B: 50% 한 줄만 둡니다.
  가장 조용하지만 60pt 높이에서 절반보다 아래쪽 값들을 어림할 단서가 없습니다.
- 옵션 C: 25·50·75%에 선을 두고 라벨은 두지 않으며, 그 값을 카드 접근성 이름에 담습니다.
  60pt를 네 등분해 15pt마다 선이 놓여 높이를 어림할 수 있고 폭을 쓰지 않습니다.
  화면에서 선의 값을 문자로 확인할 수는 없습니다.
- 채택안: 옵션 C.
  SPEC §5.6이 요구하는 것은 값의 높이를 어림할 수 있는 기준선이고 눈금 라벨을 지정하지 않습니다.
  그래프의 세로 범위가 0~100%로 고정돼 있어 등분선만으로 어림이 성립하며,
  세 값은 메뉴바 표시 상태 경계(core-resource-monitoring analyze.md §5 DP8)와 같은 값이라 카드 안에서 뜻이 어긋나지 않습니다.
  선은 밴드 뒤에 깔고 밴드 채움을 반투명으로 두어 부하가 높은 구간에서도 선이 보이게 합니다 —
  선을 밴드 위에 올리면 계열 경계가 선에 잘려 보이고, 불투명 채움 뒤에 깔면 높은 구간에서 선이 사라져 SPEC §5.6이 그 구간에서 성립하지 않습니다.
  값이 없는 상태의 자리표시에도 같은 격자를 그립니다.
  격자는 값이 아니라 눈금이므로 core-resource-monitoring SPEC §5.11의 「값을 지어내지 않는다」와 충돌하지 않습니다.

### DP11. 앱 아이콘의 획득 경계와 캐시

`NSWorkspace.shared.icon(forFile:)`는 디스크 접근을 수반하고(§근거 추정),
아이콘이 필요한 행은 카드 순위 5행, 상세 앱 목록 정원만큼의 행, 증가량 순위 정원만큼의 행입니다.
갱신 주기마다 이 행들이 다시 그려집니다.

- 옵션 A: 행이 그릴 때마다 시스템을 부릅니다.
  캐시가 없어 구조가 단순하지만 매 tick 수십 번의 디스크 접근이 반복되어 spec.md §3의 자기 사용량 제약과 SPEC §5.9를 어깁니다.
- 옵션 B: 프로세스 조사 축에서 아이콘까지 함께 얻어 표시 값에 담습니다.
  획득이 수집 계층에 모이지만 이미지가 `Sendable`·`Equatable` 표시 값에 들어가고,
  조사 actor가 AppKit을 만지게 되며, 카드 표시 값의 동등성 비교가 이미지 비교를 포함하게 됩니다.
- 옵션 C: 표시 계층에 앱 키를 키로 하는 고정 상한 LRU 캐시를 두고, 시스템 호출은 주입 가능한 로더 하나에만 둡니다.
  아이콘을 얻지 못한 결과도 캐시에 남겨 실패한 키가 매 tick 다시 시스템을 부르지 않게 합니다.
  표시 계층이 시스템 호출 경로를 하나 갖는 대가가 있습니다.
- 채택안: 옵션 C.
  `docs/design.md`가 앱 이름·아이콘을 메모리 캐시로 두고 성능 최적화 수단에도 같은 캐시를 적어 둔 것과 같은 방향이고,
  `ApplicationIdentityResolver`가 이미 같은 자리에서 고정 상한 LRU 관례를 쓰고 있습니다.
  「Presentation은 시스템 API를 직접 호출하지 않는다」는 경계는 지표 조회를 표시 계층으로 끌어오지 말라는 뜻이고,
  아이콘은 지표가 아니라 경로에 딸린 정적 자산이며 호출을 어댑터 하나로 격리하므로 뷰에는 시스템 호출이 남지 않습니다.
  부정 결과까지 캐시하는 것이 이 선택의 필수 조건입니다 — 그것이 없으면
  아이콘을 얻을 수 없는 키가 정확히 매 tick 다시 디스크를 두드려 SPEC §5.9가 무너집니다.
  캐시에는 원본 아이콘이 아니라 표시 크기로 한 번 축소한 이미지를 담습니다.
  원본은 여러 해상도 표현을 물고 있어 상한만큼 들고 있으면 메모리가 예측되지 않고,
  `docs/design.md` 성능 설계의 메모리 목표(100MB 미만)에 영향을 줄 수 있습니다.
  상한은 `ApplicationIdentityResolver`와 같은 규모로 두어 정상 상태에서 축출이 반복되지 않게 합니다 —
  정원 통합으로 실제로 조회되는 키가 수십 개로 줄어들어 상한이 그 집합을 넉넉히 덮습니다.
  캐시는 관찰 가능 객체로 두지 않습니다. 조회가 뷰 갱신을 유발하면 목록 전체가 매번 다시 무효화되어
  아끼려던 비용이 다른 형태로 돌아옵니다.

### DP12. 아이콘 자리 크기와 얻지 못한 경우의 표시

- 옵션 A: 아이콘이 있는 행에만 아이콘을 그립니다.
  구조가 단순하지만 행마다 앞쪽 여백이 달라져 정렬이 흔들리고 SPEC §5.7을 어깁니다.
- 옵션 B: 아이콘을 얻지 못하면 같은 크기의 빈 자리를 둡니다.
  높이와 정렬이 지켜지지만 그 자리가 왜 비어 있는지 알 수 없습니다.
- 옵션 C: 아이콘을 얻지 못하면 같은 크기의 중립 기호를 둡니다.
  자리와 정렬이 지켜지고 「아이콘 없음」이 표시로 드러납니다.
- 채택안: 옵션 C.
  core-resource-monitoring이 Pressure 자리표시에 실제 세 단계 중 어느 것도 아닌 기호를 둔 것과 같은 관례이며,
  `docs/design.md`의 「앱 이름과 아이콘 조회 실패는 수집값 자체를 무효화하지 않습니다」와도 맞습니다.
  자리 크기는 카드와 상세에서 다르게 잡습니다 —
  카드는 그 줄의 텍스트 높이를 넘지 않는 크기여야 카드 높이가 유지되고(§5 DP4),
  상세는 팝업 크기가 고정이고 내부가 스크롤이라 알아보기 좋은 크기를 쓸 수 있습니다.
  두 크기 모두 하나의 캐시 이미지에서 그립니다.

### DP13. 새 표시 요소의 접근성 노출 자리

- 옵션 A: 그래프·바·도넛·아이콘에 각각 접근성 요소와 이름을 줍니다.
  요소마다 이름이 붙지만 카드 쪽은 `Button`이 children을 무시하고 있어 그 이름이 계층에 나타나지 않고,
  무시를 풀면 카드 하나가 여러 노드로 쪼개져 기존 카드 접근성 이름 규약이 깨집니다.
- 옵션 B: 카드의 새 요소는 카드 접근성 이름 조립에 수치를 더하고, 상세의 그림 요소에만 자체 이름을 줍니다.
  카드가 지금처럼 하나의 노드로 남고 상세는 요소별로 도달됩니다. 카드 이름 문자열이 길어집니다.
- 옵션 C: 상세 팝업의 수치로만 도달을 만족시킵니다.
  변경이 가장 적지만 SPEC §5.10이 카드와 상세 양쪽을 요구합니다.
- 채택안: 옵션 B.
  카드가 하나의 버튼이고 그 이름이 상태·수치·단축키를 모아 전달하는 구조는
  core-resource-monitoring이 세운 것이며 UI 테스트가 그 이름으로 카드를 판정합니다.
  그 규약을 유지하면서 SPEC §5.10을 만족시키는 방법은 이름에 새 수치를 더하는 것입니다 —
  그래프는 두 계열과 기준선 값을, 구성 바는 네 항목의 수치와 구성 합계를 더하고,
  구성 합계와 「사용 중」이 다른 지표임을 문구에서 갈라 SPEC §5.3의 구분이 낭독에서도 유지되게 합니다.
  카드 폭 때문에 화면에서 잘릴 수 있는 값(§5 DP4)이 이름에는 온전히 남는 것도 이 선택의 값어치입니다.
  아이콘은 같은 행의 앱 이름과 정보가 겹치므로 계층에서 감춥니다.
  이름 조립이 순수 함수라 새 수치가 들어갔는지는 단위 테스트로 직접 확인됩니다.

### DP14. 새 요소가 상태 전이에서 차지하는 자리

- 옵션 A: 값이 없으면 새 요소를 그리지 않습니다.
  분기가 적지만 값이 도착하는 순간 요소가 생기며 카드가 부풀어 SPEC §5.8을 어깁니다.
- 옵션 B: 값이 없으면 0으로 그립니다.
  자리가 유지되지만 없는 값을 그리는 것이라 core-resource-monitoring SPEC §5.11과 충돌합니다.
- 옵션 C: 값이 없으면 같은 크기의 자리표시를 둡니다 —
  그래프는 격자만, 구성 바는 트랙만, 범례와 스와치 줄은 수치 대신 중립 기호, 아이콘은 중립 기호입니다.
- 채택안: 옵션 C.
  core-resource-monitoring analyze.md §5 DP17이 세운 「상태와 무관하게 같은 슬롯 집합」 규칙의 연장이고,
  새 요소마다 「눈금·트랙은 값이 아니다」와 「구간·점·수치는 값이다」를 가르는 선이 명확합니다.
  이 규칙이 SPEC §5.8을 담당하고, 카드 높이가 상태에 따라 달라지지 않는지는
  기존 렌더 높이 측정 테스트가 새 요소가 들어간 뒤에도 그대로 지킵니다.

### DP15. 새 표시 요소를 단위 테스트로 덮는 구조

이 프로젝트의 검증 기준은 mutation testing이고, 표시 계층에 그물이 없어 반려된 이력이 있습니다.
그래프·바·도넛은 `Canvas` 그리기라 그림 자체를 단언할 수 없습니다.

- 옵션 A: 표시 검증을 UI 테스트로 덮습니다.
  실제 화면을 보지만 한 번에 4~5분이 들고 각 테스트가 앱 실행·수집 대기 고정비를 따로 내며,
  그림의 기하는 접근성 계층에 나타나지 않아 애초에 단언할 수 없습니다.
- 옵션 B: 그리기 직전 단계를 모두 뷰 밖 순수 함수로 빼고 그 함수들을 단위 테스트로 덮습니다.
  뷰에는 순수 함수의 결과를 좌표로 옮기는 코드만 남고, 그 코드의 회귀는 렌더 높이 측정과 접근성 이름으로 잡습니다.
  뷰 본문 안에서만 성립하는 실수는 여전히 남습니다.
- 옵션 C: 스냅샷 이미지를 비교합니다.
  그림을 직접 검증하지만 폰트·해상도·시스템 설정에 따라 흔들리고, 무엇이 왜 틀렸는지 알려주지 않습니다.
- 채택안: 옵션 B.
  이 프로젝트에는 이미 같은 방향의 관례가 있습니다 —
  다운샘플링·연속 구간·가로축 정규화가 `HistoryPoint`의 정적 함수이고,
  값 서식이 `ApplicationProcessValueFormatting`이며, 순서 고정이 `ApplicationProcessGroupOrdering`입니다.
  이 feature가 그 관례에 더하는 순수 함수는 구성 구간 계산, 도넛 각도 변환, 구성 범례 서식,
  병합 줄 서식, 격자 값과 세로 좌표 변환, 계열 밴드 값 유도, 순서 고정과 정원, 아이콘 캐시 정책입니다.
  뷰에 남는 부분은 두 수단으로 덮습니다 —
  카드 뷰의 렌더 높이 측정(`NSHostingController.sizeThatFits(in:)`, 기존 테스트가 이미 쓰는 방법)이 슬롯 구성과 자리표시를 고정하고,
  접근성 이름 단언이 카드가 실제로 내보내는 수치를 고정합니다.
  UI 테스트는 늘리지 않고, 통합으로 바뀐 판정 문자열을 고치는 데까지만 손댑니다(§4).
  각 순수 함수에는 「무엇을 되살리면 실패해야 하는가」가 분명한 단언을 둡니다 —
  구간이 합계 기준으로 정규화되면, 대표 표본과 짝이 아닌 User 값이 붙으면,
  정원을 순서 고정보다 먼저 적용하면, 병합 줄의 요소 순서가 뒤바뀌어 기호가 먼저 잘리면,
  카드와 상세의 상위 5개가 어긋나면, 아이콘이 키당 두 번 로드되면 실패해야 합니다.

### DP16. 정원 통합과 아이콘이 자기 사용량에 주는 부담

SPEC §5.9는 새 요소가 더해진 뒤에도 팝오버를 열어 둔 채 관찰한 자기 CPU 사용량이 지속적으로 오르지 않기를 요구합니다.

- 옵션 A: 아무 제한 없이 더합니다. 관찰로만 확인하며, 회귀가 생겨도 원인을 좁힐 근거가 없습니다.
- 옵션 B: 새 비용이 tick마다 반복되는지를 항목별로 미리 갈라 두고, 반복되는 것만 구조로 막습니다.
- 채택안: 옵션 B.
  항목별 판단은 다음과 같습니다.
  순위 정원 확대는 정렬이 이미 전체 앱 키를 대상으로 하고 자르는 위치만 바뀌므로 반복 비용이 늘지 않습니다.
  상세 목록의 정원 통합은 오히려 비용을 줄입니다 —
  실행 환경에서 수백 개(관측 381개)였던 앱 행이 정원만큼으로 줄어 매 갱신의 행 조립·레이아웃과 접근성 노드가 함께 줄어듭니다.
  그래프는 버킷 수와 갱신 주기가 그대로이고 경로 하나와 격자 세 줄이 늘어납니다.
  구성 바·도넛은 항목이 넷인 산술입니다.
  실제로 반복될 수 있는 비용은 아이콘 획득 하나이며, 캐시와 부정 결과 캐시로 정상 상태의 시스템 호출을 0으로 만듭니다(§5 DP11).
  남는 비용은 표시되는 행들이 아이콘을 함께 그리는 것이고, 정원 통합 덕분에 그 행 수 자체가 작습니다.
  관찰에서 상승이 보이면 줄일 자리는 캐시 이미지 크기와 행 그리기 비용입니다 —
  행 수를 더 줄이는 방향은 SPEC §5.1의 정원과 SPEC §5.7의 행별 아이콘 요구가 정한 범위라 쓸 수 없습니다.
